## 1. バイカラージェムの交換所

### 1-1. シートから NPC へ辿れない

バイカラージェムを使う `SpecialShop` は **42 件**。そのすべてが、
通常の経路（`ENpcData` 直接 / PreHandler / TopicSelect / InclusionShopSeries）
から **1 件も辿れない**（実測）。

### 1-2. **`FateShop` シートに答えが直接ある**

遠回りした末に見つけた。**次はこれを最初に見る。**

```
FateShop シート（17 行）
  RowId    = NPC 番号（ENpcResident の RowId）そのもの
  列 0〜2  = ランク1 / 2 / 3 の枠。その ランクで開く SpecialShop が入る
  列 3 以降 = DefaultTalk（セリフ）
```

例：

```
ラルルック（ヤクテル樹海）… 1770743 | 1770744 | 1770745   ← 3 つとも別
マヴェーダ（サベネア島）  … 1770460 | 1770461 | 1770461   ← 2 と 3 が同じ
ベリル（都市）            … 1770746 |    0    |    0      ← 段階なし
```

**同じ番号が続く枠を「重複」として落としてはいけない。**
「そのランクで品が増えない」という意味で、落とすとランクが 1 つずれる。
（実際にこれで暁月のランクを取り違えた）

ただし**漆黒の 8 ショップ（1769957〜1769964）は FateShop に無い**。
全シート総当たりでも番号として現れないので、下の方法でしか特定できない。

### 1-3. FateShop に無いときの特定方法（報酬の品揃えから逆に引く）

| 決め手 | 内容 | 件数 |
|---|---|---|
| 1 | 報酬の「詳細地図:〇〇」→ そのエリアの交易商 | 24 |
| 2 | 素材の完全一致（あるエリア専用ショップと 100%・他は 0%） | 12 |
| 3 | 報酬の「ポートレート教材:〇〇」→ 都市名が明記されている | 6 |

広域交易商は各エリアにちょうど 1 人なので、いずれも一意に決まる。

### 1-4. 結果：24 人・42 ショップ

| 拡張 | マップの交易商 | 都市の交易商 |
|---|---|---|
| 漆黒 | 6 人 | クリスタリウム / ユールモア |
| 暁月 | 6 人 | オールド・シャーレアン / ラザハン |
| 黄金 | 6 人 | トライヨラ / ソリューション・ナイン |

**都市の交易商は、その拡張の 6 マップ全部が達成度最大でないと使えない。**
逆に全部最大なら、マップの交易商を使う理由はなくなる（都市で全部買える）。

保管先：`AutoCollector\Data\npc_shop_links.json`（根拠つき）
検証：`tools\bicolor_shop_verify.cs`（42 件・重複と漏れも数える）

### 1-5. 外した思い込み

- **「100% 被覆しないから扱っていない」は誤り。**
  「漆黒の都市は素材を扱わない（0/6）」と報告したが、実際は 14 件扱っていた。
  *マップ専用ショップの品を全部含むか*という厳しすぎる条件で見ていた。
  **「扱うか」と「全部扱うか」は別の問い。** 素材かどうかは
  `ItemUICategory`（48〜58 が素材帯）で直接数えるほうが正しい。
- **被覆が 1 件だけ足りないときは、ゲーム側の仕様を疑う。**
  黄金の「ウトォーム隕鉄」はヤクテル樹海専売だった。表の漏れではない。

## 2. F.A.T.E達成度（シェアF.A.T.E）

### 2-1. どこから読むか

```csharp
// FFXIVClientStructs/FFXIV/Client/UI/Agent/AgentFateProgress.cs
[Agent(AgentId.FateProgress)]                        // AgentId = 77
public partial struct AgentFateProgress {
    [FieldOffset(0x2A)] public byte TabIndex;
    [FieldOffset(0x30), FixedSizeArray] internal FixedSizeArray3<FateProgressTab> _tabs;
}
public partial struct FateProgressTab {
    [FieldOffset(0x00), FixedSizeArray] internal FixedSizeArray6<FateProgressZone> _zones;
}
public partial struct FateProgressZone {
    [FieldOffset(0x00)] public uint TerritoryTypeId;
    [FieldOffset(0x70)] public byte CurrentRank;   // 読める
    [FieldOffset(0x71)] public byte MaxRank;       // ★ 0 のことがある
    [FieldOffset(0x72)] public ushort FateProgress;
    [FieldOffset(0x74)] public ushort NeededFates;
    [FieldOffset(0x78)] public Utf8String RankText;
}
```

**3 タブ × 6 ゾーン = 18 マップ。** 画面の「1 2 3」タブと一致。漆黒 / 暁月 / 黄金の順。

### 2-2. **罠：`MaxRank` が 0 のまま埋まらない**

実機で全マップ COMPLETE（黄金 RANK4）なのに「0/6 マップ」と誤判定した。
`CurrentRank` は正しく読めていて、**上限だけ 0**。

- 構造体の定義は本家と**完全に一致**（オフセットの誤りではない）
- **上限はシートからも取れない。** `FateProgressUI` の列 1 はどのマップも 6 だが、
  実際の上限は 漆黒3 / 暁月3 / 黄金4 で合わない

**回避策**：`MaxRank` が読めないときは
「その拡張で到達している最高 `CurrentRank`」を上限とみなす。
全マップが同ランクで未到達のときだけ誤る（都市へ行って空振りする。逆よりは軽い）。

→ 根本原因は**未解明**。IDA 解析の依頼事項 (1)。

### 2-3. シートから取れるもの

`FateProgressUI`（18 行）… マップの顔ぶれ（列 0 = TerritoryType）と拡張の区切り。
**上限ランクは取れない**（列 1 は全マップ 6）。

拡張の区切りは、TerritoryType の番号が大きく飛ぶところで切る
（813 台 / 956 台 / 1187 台）。件数で決め打たない。

### 2-4. 都市そのものは 18 マップに入らない

クリスタリウム(819)・ラザハン(963) などは `FateProgressUI` に無い。
**都市の territory で拡張を判定しようとすると必ず失敗する。**
同じ拡張のマップを 1 つ借りて判定する。

## 3. ランクごとの交換品

### 3-1. 2 つの手がかりを組み合わせる

**(a) `FateShop` の枠の位置 = ランク**（§1-2）

**(b) `SpecialShop.Item[].AchievementUnlock` の説明文にランクが書いてある**

```
3023「広域交易商の味方：サベネア島」
     説明 = サベネア島のF.A.T.E.達成度をRANK3にする
3564「広域交易商の味方：リビング・メモリー」
     説明 = リビング・メモリーのF.A.T.E.達成度をRANK4にする
```

`RANK` の直後の数字を読む。**枠の位置より確かなので、こちらを優先する。**
これが無いと、暁月のランク 2/3（同じショップ）と
黄金のランク 4（枠は 3 つしかない）を出せない。

### 3-2. 拡張ごとの実態

| 拡張 | 最大ランク | 枠の使い方 | ランク 4 |
|---|---|---|---|
| 漆黒 | 3 | 1 ショップ + `Quest` 列の印（80〜91） | なし |
| 暁月 | 3 | 列1 と列2 が同じショップ → Ach で 3 を判別 | なし |
| 黄金 | 4 | 列0/1/2 が別ショップ → Ach で 4 を判別 | Ach 3559〜3564 |

**漆黒だけ方式が違う。** `SpecialShop.Item[].Quest` に
Quest シートに存在しない小さな値（80〜91）がマップごとに 2 つずつ入っている。
Q0（印なし）=ランク1 / 小さい順に 2・3。

印を持つショップは他にもある（チョコボ教本の交換など）が、
そちらの印はランクと無関係。**`FateTokenType` シートの通貨を使うショップだけに限る。**

### 3-3. 検証

交換サイトの表を HTML から全行取得し、**ランクが明記された 96 件すべてと一致（不一致 0）**。

- 漆黒 <https://itumononeko.com/ff14-jet-black-fate-trader/>
- 暁月 <https://itumononeko.com/ff14-00070/>
- 黄金 <https://itumononeko.com/ff14-00485/>

**WebFetch の要約は「抜粋」しか返さない。** それを信じて誤った結論を 2 回出した。
**HTML から表を直接取ること**（`tools\fetch_rank_tables.py`）。

### 5-2. **エリア・座標は LGB から取れる**

「Lumina で LGB を開けない」と報告したが**誤りだった**。
原因は**パスの組み立てミス**。

```csharp
var bg   = territoryType.Bg.ExtractText();  // "ffxiv/fst_f1/fld/f1f1/level/f1f1"
var dir  = bg[..bg.LastIndexOf('/')];       // 末尾セグメントはベース名。落とす
var path = $"bg/{dir}/planevent.lgb";       // ★ 先頭の "bg/" を忘れていた

if (!gd.FileExists(path)) return;           // GetFile は見つからないと null を返す
var lgb = gd.GetFile<LgbFile>(path);        // null のまま .Layers に触ると NullReference
```

要点 4 つ：
1. `Bg` の**末尾セグメントを落とす**（ディレクトリではなくベース名）
2. **先頭に `bg/` を付ける**
3. `FileExists()` で確かめてから `GetFile()`
4. `planevent.lgb` のほか `planmap.lgb` / `bg.lgb` も見る

`InstanceObject.InstanceId` → 座標 の索引を作り、`Fate.Location` で引く。

実測：**LGB 1788 ファイル・インスタンス 2,241,913 件**を索引化し、
**1581 / 1712 件**を解決（残り 131 件は `Location` が 0 か、LGB に該当なし）。

ワールド座標 → マップ座標（画面に出る値）の換算：

```csharp
static float ToMap(float world, short offset, ushort sizeFactor) {
    var c = sizeFactor / 100f;
    return (41f / c) * (((world + offset) * c + 1024f) / 2048f) + 1f;
}
// マップX = ToMap(worldX, Map.OffsetX, Map.SizeFactor)
// マップY = ToMap(worldZ, Map.OffsetY, Map.SizeFactor)
```

なお `Level` シート（Type=6）は `Object` が全部 0 で使えない。
シートに橋渡しは無く、**橋渡しは LGB にあった**。

## 6. 道具・手順の知見

### 6-1. **埋め込みデータを直しても反映されない罠**

補助データを「初回起動時に設定ディレクトリへ展開し、以後はそちらを読む」
作りにしていると、**こちらがデータを直しても古いまま使われ続ける**。

DLL は最新・ビルド成功・配置もハッシュ一致——**それでも動作が変わらない。**

実際に起きたこと：`npc_shop_links.json` を 1 人 → 24 人に増やしたのに、
設定ディレクトリの古い版（1 人）が読まれ、**新しい画面が何も出なかった**。

**対処**：`verifiedGameVersion` を比べ、同梱のほうが新しければ入れ替える。
手で書き換えた人の内容を消さないよう、古いものは `〜.backup-版.json` に残す。

**確認方法**：DLL の埋め込みだけでなく、**展開先の中身も数えて突き合わせる**。

```powershell
Get-ChildItem "$env:APPDATA\XIVLauncher\pluginConfigs\<Plugin>" -Recurse -Filter "*.json" |
  ForEach-Object { "$($_.FullName) $($_.LastWriteTime)" }
```

### 6-2. EstellUtils：プルダウンが選べない

`EuWindow` の余白ドラッグが原因だった。
ドラッグ開始時に `ImGui.SetWindowFocus` を呼ぶと、ImGui は開いているポップアップを閉じる。
そのため項目を押した瞬間に一覧が閉じ、選べなくなっていた。

```csharp
// 生の ImGui のウィジェットが反応している場所では掴ませない
if (!isDragging && (ImGui.IsAnyItemHovered() || ImGui.IsAnyItemActive())) return;
// ポップアップが開いている間は掴ませない
if (!isDragging && ImGui.IsPopupOpen(string.Empty,
        ImGuiPopupFlags.AnyPopupId | ImGuiPopupFlags.AnyPopupLevel)) return;
```

### 6-3. 配置は DLL 1 本ではなく丸ごと写す

`AutoCollector.dll` だけコピーしていたため、共有先の `EstellUtils.dll` が
**10 時間古いまま**だった。`tools\deploy.ps1`（robocopy /MIR + SHA256 検証）を用意した。

### 6-4. TSV を作るときの罠

説明文には改行が入っている。**`\n` だけ消すと `\r` が残り、1 件が複数行に割れる**
（実際に 1712 → 5815 行になった）。CR も潰すこと。

`EventItem` の名前は **Lumina の `Name` では取れない**（空文字が返る）。
生の列 0 に入っているので `RawRow.ReadColumn(0)` で読む。

### 6-5. UI を出せないときの調べ方

早期 return が複数あると、どこで抜けたか推測では分からない。
**「出せません」の分岐に、判断材料の数を全部ログへ出す**（定義数・座標つき件数・
対象の人数・その居場所）。推測でコードを読み返すより速い。

## 7. IDA 解析でさらに分かったこと（2026-09-27 追記）

相談した 5 件すべてに回答をもらった。**すべて手元で再現・検証済み。**

### (1) `MaxRank` は追う必要がなかった → **実装済み**

`FateProgressUI` の列 1〜3 は `ReqFatesToRank2/3/4`。
**0 でない列を数えれば上限ランクが出る**（漆黒3 / 暁月3 / 黄金4）。

近似（最高ランクを上限とみなす）をやめたことで、
「全マップ RANK3（黄金は上限4）」「全マップ RANK2」の**誤判定 2 件が消えた**。

### (4) `HandInCount` は「FATE 単位の累計」が有力

IDA でクライアント側に**加算命令もリセット命令も無い**ことが確認された。
`Progress`(0x3B7) と同じ 16 バイト一括ゼロ（0x3AE から）に含まれる。
BMR も `HandInCount >= 10 && Progress >= 100` を完了判定に使っており、整合する。

**確定は実機 1 回**：10 個渡した直後に読む。0 に戻れば今回分、10 のままなら累計。

### (2) SpecialShop — 外部データは正しい対処だった

```
ENpcData が SpecialShop を直接指す参照   635 件  ← 仕組みは機能している
  うちバイカラー交易商                     0 件  ← ここだけ結線されていない
```

**`npc_shop_links.json` は回避策ではなく必要な補完。**

実装に使える構造体（すべて実在を確認）：

```csharp
AddonShopExchangeItemDialog.ExchangeButton   // 交換の確定ボタン
ShopEventHandler.VisibleItemsCount           // 実際に並ぶ品の数
ShopEventHandler.WaitingForTransactionToFinish
```

**`VisibleItemsCount` で「実機で品が並ぶか」を目視せず確認できる。**

### (5) BMR の線引き

BMR が実機から読むのは **6 つだけ**（FateId / Location / Radius / Progress /
HandInCount / ObjectiveNpc）。納品 NPC は `ObjectiveNpc` をそのまま使い、推論していない。

| | BMR | AutoCollector |
|---|---|---|
| FATE 内の納品・収集 | ○ | — |
| どの FATE をやるか / マップ間移動 / 交換 / `MotivationNpc` | — | ○ |

### 副産物：**`MapIcon` で NM 判定ができる**

`Rule=1` の 1156 件は、`MapIcon` で分けられる。

```
討伐（通常）  624 件   MapIcon 60501
討伐（NM）    436 件   MapIcon 60502   ← Rule では区別できない
```

**名前で裏を取った**（NM は「〜」と鉤括弧が付く慣習）。

| MapIcon | 「」を含む割合 |
|---|---|
| 60501（通常） | **5%**（34/624） |
| 60502（NM） | **81%**（355/436） |

**TSV の `大型` 列（`Unknown8`）を NM 判定に使ってはいけない。**
BMR の判定と **1712 件中 489 件で食い違う**（両方 true はわずか 75 件）。
`Unknown8` は通常討伐にも 14 件付き、エウレカ NM 76 件を全部含む。
「大型」というより特殊出現枠の印に見えるが、正体は未確定。

→ `FATE一覧_全件_座標付き_MapIcon付き.tsv`（28 列）の **`NM判定` 列**を使う。
