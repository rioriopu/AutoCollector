## 3. 修正を要する具体的な問題

### P1：CollectFATE=Enabledの常時設定は納品前の討伐も抑える

AutoCollector `FateCombatPreset.cs:74,157` はCollectFATEを常時Enabledにした。
一方、BMR `Autorotation/MiscAI/AutoTarget.cs:162–171` は、納品用アイテムのあるF.A.T.Eでこの設定がEnabledなら `targetFateMobs = false` とする。10個所持かどうかを見て切り替える設定ではない。

結果は次のとおり。表は通常の未交戦敵の自発的選定についてで、既に敵視を持つ敵・特殊優先敵まで全排除する意味ではない。

| 所持数 | 自発的に通常のF.A.T.E敵を拾う | FateUtilsの納品開始 |
|---|---|---|
| 0 | 抑止される | しない |
| 9 | 抑止される | しない |
| 10 | 抑止される | する |

地面の拾得物もCollect=Disabled。敵が襲ってこなければアイテム収集が進まない可能性がある。さらにBMR AutoTarget.cs:224は既存の敵視等による優先対象を拾うため、**この設定は「納品中は被弾を無視する」ことの実装にもなっていない。**

修正：討伐中と納品中を分ける。討伐用のCollectFATEはDisabledとし、10個到達時に納品専用制御へ切り替える。具体案は6章。

### P2：NoTargetだけでは「F.A.T.E敵のみ・撃破後最近傍」を満たさない

BMR AutoTarget.cs:244のNoTarget条件は `currentTarget == null`。生存中に勝手に切り替えない改善はあるが、死亡したオブジェクトがまだ存在する場合、無効対象・味方・非F.A.T.E敵を持った場合の解除を実装していない。ゲームがターゲットを消すケースだけに依存する。

AIHintsBuilder.cs:148で敵視のある敵はFateIdに関係なく優先度0。AutoTarget.cs:224もそれを選定対象に含める。Everything=DisabledはF.A.T.E外の敵の完全除外ではない。さらに順位はShouldBeTargeted・Priority・ヒットボックス距離・現在対象の順であり、要求した厳密な最近傍ではない。

修正：対象ID保持・無効化・FateId限定・接近先を一つの管理にまとめる。既存BMRの一般設定だけで表現できない条件を「表現できた」と報告しない。

### P3：退避が地上のまま／外へ出た確認ができない

FateRunner.cs:2746 `RetreatFromCircle` は `BeginMove(outside, 5f, MountService.IsFlying, ...)` を呼ぶだけ。騎乗準備は呼ばないので、戦闘後に徒歩のプレイヤーを新たに騎乗・離陸させない。

さらに以下の問題がある。

- 退避目標は半径+10mだが、移動許容距離は5m。一例として半径50mなら目標60m、55mで経路が終わり得る。`TickLeaving` は中心から60m以上を要求するため、円外に出ていても最大15秒待つ。
- メッシュへの最大30mの補正後に、その点がまだ円外か再確認していない。内側へ補正される可能性がある。
- `TickLeaving` は退避先ではなくF.A.T.E中心をNavigationService.Tickへ渡している（2715行）。距離監視が実際の移動先と異なり、スタック再探索も中心へ向かう可能性がある。
- 失敗・15秒超過時はFinishRetreatしてWaitingへ戻す。脱出成功ではないのに、後続の待機へ進む。
- 次候補ありでは退避状態を通らずBeginMoveToへ進む。移動だけで出られる場合はあるが、重なった円や近距離候補では前の円を出た保証がない。

修正：退避目標を保存してその同じ点を監視する。円外成功基準を `distance > radius + 小余裕` に統一し、移動許容距離を考慮してさらに外へ目標を置く。騎乗可能なら騎乗・離陸を行い、戦闘中は徒歩退避→戦闘解除後に飛行へ移る。失敗時は別退避点を有限回試し、失敗を成功として扱わない。

### P4：失敗・中断したF.A.T.Eも100％完了として記録される

FateRunner.cs:1067–1077は `Progress >= 100 || State != Running` でLeaveFateを呼ぶ。同2598以降は条件を分けずCompletedを加算し「100％」とログに書き、納品なら報酬待ちを追加する。

修正：終了結果をSuccess／Failed／Aborted／DisappearedUnknownなどに分ける。100％または確認可能な成功状態だけを完了として数える。FateIdだけでなくエリア・開始時刻の一致を確認する。消失と読取失敗も区別する。

### P5：周回中の選択変更と待機の問題

- A/B/C/D順でBを周回中、Aのチェックを外すとリストはB/C/DになるがzoneIndex=1が残る。次のAdvanceZoneはindex=2となりDへ飛び、Cを飛ばす。空リスト対策だけでは不十分。
- メッシュ未準備はBusyになったが、TickMovingのBusy分岐は時間制限判定より先にreturnする。メッシュが利用可能にならない場合の上限がない。
- NavigationService.BeginMoveの入口でBusyをfalseへ戻していない。以前Busyだった後、IPC失敗等で早期returnすると古いBusyを引き継ぎ得る。
- テレポ拒否のログは5秒間隔だが、TryTeleportTo呼出し自体は各Tickで再試行する。失敗の種類に応じた間隔を設ける。
- 選択が一つだけでテレポ不能の場合、AdvanceZoneはwaitingSinceUtcを書き換えるだけ。停止や明示的な回復方針に移らない。
- 報酬待ちが1件でもあるとTickStuckWatchdogを全面的に無効にする（631行付近）。同時に次のF.A.T.Eへ移動中の場合まで監視を止めないこと。

### P6：プリセット検査が実際の意味を検証していない

FateCombatPresetの文字列検索はモジュールを限定せず、必要モジュールもSAM一つの代表確認。独自名ならStartでEnsureを通らない。作り直し失敗でも既存があればtrueを返す。

NoTargetはBMR enumの0番。プリセットエディタは既定値を設定一覧から省略できる（UIPresetEditor.cs:267–272）。省略しても有効なNoTargetだが、現在のRequiredは明示文字列を必須とする。JSON読込→書出しでは明示エントリーが残るため「毎回必ず壊れる」とは言えないものの、正しい既定値の省略を不備と誤判定し得る。

修正：JSONを解析し、モジュールごとのトラック・既定値・修飾条件を解釈して検査する。保証に必要な戦闘／移動／納品モジュールを検査し、欠落を修復できなければ明示停止。ユーザー指定プリセットでも保証条件を確認する。

## 4. Cが未達成であるコード上の理由

1. FateStepにあるのはMovingToFateとLandingで、離陸・外周・降下の独立状態はない。
2. TickMoving（1433行以降）の目的地は最寄り敵または中心付近。外周点を算出していない。
3. BeginMoveはLiftForFlightで持ち上げた点に依頼（1553–1572行）するが、Tickは地上のlandingを監視（1640行）する。Tickに新しい点を渡しても通常の経路差替えにはならない。
4. `moveIssued && flyingWhenIssued && !IsFlying` で停止・再探索する（1500行）。離陸する前の「まだ飛んでいない」と、飛行後の「接地した」を区別しない。離陸待ちにもこの分岐が働き得る。
5. ShortOfTargetでもEnterFateへ進む（1646–1649行）。地表まで下りたことを証明していない。
6. TickCoreは現在参加中のF.A.T.EがあればTickInFateへ入る（1122行）。新しい飛行段階を追加するだけでは、この横入りで移動目標や降車判断を上書きされる。
7. ResolveLandingTarget（2520行）は動く最寄り敵を着地点にする。移動指示時と監視時で点が変化し得る。
8. MountServiceは未変更。20m未満は徒歩を許し、観測済み最大Yを高度上限のように扱う。C専用の明確な離陸確認にはなっていない。

**解決の要点：F.A.T.Eへの進入を担当する一つの状態機械を用意し、目的地を固定し、状態ごとに実際の経路を発行し直す。BMRに空中移動を任せない。**

### 5.1 利用できる実在の連携機能

`C:/ソース/ffxiv_navmesh/vnavmesh/IPCProvider.cs` で登録を確認した。

| IPC | 実際の型・性質 | 用途 |

| Nav.Pathfind | `(Vector3 from, Vector3 to, bool fly) -> Task<List<Vector3>>` | 経路だけ取得。自動で移動は開始しない |
| Nav.PathfindCancelable | 上記引数+CancellationToken、戻り値は同じTask | 自分の経路探索を取り消せる形で取得 |
| Path.MoveTo | `(List<Vector3>, bool fly) -> action` | 渡した経路を追従。障害物を避ける経路計算はしない |
| Path.Stop | action | 経路点を消す。SimpleMoveの未完了探索までは止めない |

AutoCollectorのVnavmeshIpcにはMoveAlong等はあるが、通常のPathfind／PathfindCancelableラッパーはまだない。必要分を実在するシグネチャに合わせて追加する。

根拠：NavmeshManager.cs:150–184のQueryPathBasicはList<Vector3>を返すだけ。FollowPath.cs:144付近は、fly経路で次の点が高く、騎乗中かつ未飛行ならジャンプして離陸する。Path.MoveToはflyを反転してIgnoreDeltaYへ渡す。

BMR NormalMovement.cs:125–128は飛行中にreturnする。BMRのプリセット調整で飛行進入を解決しようとせず、地上戦闘開始後に制御を渡す。

### 5.2 実装単位と状態

FateRunnerに既存分岐を積み増すより、例として `FateTravelController` を切り出す。既存のFateStepに追加してもよいが、同等の状態と責任を持たせる。

```text
PlanEntry → Mounting → TakingOff → FlyToEntry
    → Descending → GroundConfirm → Dismounting → ReadyForCombat

どの状態からも：Stop／Death／対象終了 → Cancel → 離脱または待機
失敗時：有限回の候補再選択 → 理由付き失敗（着地成功にしない）
```

保持するデータ：TerritoryId、FateId、StartTime、中心・半径、固定した着地点L、外周上空点E、状態開始時刻、要求世代番号、キャンセル元、保留Task、実行中経路の目的地・fly、最後に飛行を確認した時刻、再計画回数。

FateRunner.TickCoreは、安全判定・死亡・対象の消失／100％確認のあと、進入中なら必ずこのコントローラーへ渡してreturnする。CurrentFateが立っても、ReadyForCombatまでは旧TickInFate・EnterFateによる割込みを禁止する。旧TickMovingと新コントローラーで同時に経路を発行しない。

### 5.3 着地点Lと外周点Eを決める

1. 中央付近の床を探し、Lを固定する。中心が不適切なら中心の近傍リングから選ぶ。対象円内で余裕を持つ点、適切な階層、地表近傍であることを確認する。敵の移動でLを更新しない。
2. CをF.A.T.E中心、Pを現在地として、水平単位ベクトル `u = normalize(P.xz - C.xz)`。ゼロ長なら固定方向を初期候補にする。
3. `E.xz = C.xz + u * (radius + margin)`。初期marginは10mを試験値とする。前回指示の「外周の空中」をこの点で具体化する。
4. 高さは外周付近の床とLを基準に決める。例：`E.y = max(entryFloorY + clearance, L.y + tan(angle) * horizontalDistance(E,L))`。角度20度、clearance8m程度を初期試験値とし、固定されたゲーム仕様として扱わない。
5. 外周に床がない、空間が塞がる、到達高度が不適切なら、uを±30度、±60度等回して別の進入側を試す。すべて不適なら安全に失敗を返す。現在位置と中心が近くても外周を経由する。
6. 観測済み最大Yは高度上限ではない。KnownCeilingで低い観測値を一律上限にしない。未到達高度は飛行可否と実際の上昇量で監視し、頭打ちなら低い候補・別方向を有限回試す。公式上限を読めていないなら保証しない。

数値例：半径50m、中心と床を原点とするとE=(60,21.84,0)、L=(0,0,0)、角度20度。
下降の目安は `(60,21.84) → (45,16.38) → (30,10.92) → (15,5.46) → (0,0)`。
これはX/Yの幾何例であり、ゲーム内で障害物がないことの証明ではない。

### 5.4 経路計算と追従を分離する

推奨方式：**Nav.PathfindCancelableで計算 → 結果を検査 → Path.MoveToで追従**。

PlanEntryで地形候補を作り、騎乗後に離陸用の短い上昇経路を計算する。Takeoff候補は現在地から少し上（例3〜5m）の到達可能な空間。未検証の点へ直接MoveAlongしない。飛行解放・騎乗・ActionStatusを確認し、遠近にかかわらず騎乗を試す。時間切れ時は「飛行不可／離陸失敗」を示す。

TakingOffではfly=trueの経路を一度開始し、InFlightを複数更新で確認するまで待つ。「まだInFlightでない」ことを理由に毎フレームStopしない。既に飛行中ならこの段階を省略してよい。

飛行確認後、実際の現在地からEへの経路を計算し、Eへ移動する。到着は経路が空かどうかだけでなく、水平・垂直差（初期試験値それぞれ2m程度）と飛行状態で確認する。

Eまでの経路が途中で円を横切ってしまう場合、進入側を再選定するか、円の外を回る中継点を置いて区間ごとに探索する。各線分の水平距離も検査する。開始時から円内にいる場合は一度外周へ出る例外を明示してから通常進入へ移る。

**Eに着いたら、実現在地からLへの新しいfly=true経路を依頼する。監視点だけ変更しない。**

### 5.5 斜め降下を成立させる方法と限界

まずE→Lをvnavmeshで飛行探索し、返った経路の形を確認する。空間が開けていれば斜めの経路になり得る。ただしvnavmeshは指定角度や単調降下を保証するAPIではない。

返った経路が「中央上空まで水平→垂直落下」になる場合は、EからLへ補間した数点を下降の中継候補にする。例ではt=0.25、0.5、0.75、1.0の点。**各区間をvnavmeshで探索し、得た経路を検査したうえで連結する。補間点だけを直接Path.MoveToしてはいけない。**

検査するもの：非空、有限座標、区間開始・終点の整合、Lへの距離、降下の進行、過大な上昇や横道、円への進入位置。同一点ばかりの結果や経路失敗を合格にしない。ゲーム座標Yを任意に書き換えた経路も使わない。

vnavmeshのPathfindVolumeは最終点toを最後に追加している（NavmeshQuery.cs:228付近）。従って「末尾=Lだった」だけでは有効な着地の証明にならない。床候補検査と実際の到達確認が必要。

障害物が斜面通過を妨げる場合は、下降点を増やして無理に貫通させず、外周側を変える。自由空間で斜め進入を達成することと、岩・建物越しでも同じ角度を強制することは別。後者は保証しない。計画可能な別方向もない場合は理由付きで見送る。

### 5.6 地表接近・着地・降車の競合を防ぐ

Descendingはvnavmeshだけが移動を担当。途中でMountService.TickDismountを呼ばない。

Lの近傍（初期試験値：水平1.5〜2m、床からの高さ2m程度）まで来たら経路を止め、GroundConfirmへ移す。**上方差だけの `height <= 8` 判定は使わない。床より大きく下でも真になるため、階層と高さ差を検査する。**

InFlight=falseだけでも接地確定にしない。降下アニメーション中の可能性を考え、床との高さ差・位置の安定・取得可能な接地関連状態を合わせる。接地状態の正確な取得方法は使っているClientStructs版で確認する。

地表近傍に残る短い最終降下が必要な場合だけゲームの降下操作へ渡し、その間はvnavmeshを発行しない。これは最後の短い降下であり、上空からの長い垂直落下を合格にするものではない。

Dismountingは降車操作を間引いて発行し、Mounted=falseを確認する。レベルシンク・BMR戦闘開始はこの確認後。騎乗中に被弾したからといって旧実装のようにFightingへ飛ばさない。降車不可の回復は専用の失敗分岐にする。

### 5.7 非同期経路の古い結果を捨てる

各計画に `generation` と `spawnKey=(territory,id,start)` を付ける。

```text
計画発行：世代を更新し、キャンセル元とTaskを保持
各Tick：完了していなければ戻る（Wait/Resultでブロックしない）
完了時：成功・キャンセル・例外を区別
        世代・エリア・発生キー・実行状態が違えば結果を破棄
        出発点から大きく移動していたら再計画
        検査合格の経路だけをゲーム更新スレッドからMoveTo
停止時：世代更新 → 自分の探索をCancel → 保持経路をStop
```

この方式なら古い探索が終わっても自動でMoveToされない。SimpleMoveはAsyncMoveRequest.Updateが完了時に勝手にMoveを呼ぶ（AsyncMoveRequest.cs:47–56）ので、同じ進入で併用しない。

ただしvnavmeshのOnStuck→AsyncMoveRequestのRetryOnStuck設定によって、Path.MoveToで始めた経路でも自動再探索が生じ得る（AsyncMoveRequest.cs:24付近）。状態切替・停止時にはSimpleMove.PathfindInProgressも確認し、遅れて入った経路を抑止する既存StopGuardを統合する。外部プラグインの経路を無断で奪わない運用にする。

CancellationToken版IPCが実際の導入版にない場合は、Nav.Pathfind＋世代番号で結果を捨てる代替が使える。探索自体は止まらないので頻繁に積まない。Nav.PathfindCancelAllはこの手元版ではNav.Reload(true)の別名であり、通常の状態切替に使わない。

### 5.8 他のプラグインから参考にする部分

- GatherBuddyのAutoGather.Movement.cs:283–382：Taskと状態を保持し、完了後に経路を渡す。409行以降のFindCombinedPathは飛行と地上の区間構成例。ただし「外周上空→中央」はそのまま実装されているわけではない。
- AutoFATEGrindのAutoCommon.Landing.cs：床の候補列挙、最大試行数、飛行と降車の別タイムアウト、降下キャンセルを参考にする。既定は現在地の下への着地なので、そのままコピーしてもCを満たさない。
- BMR NormalMovementは空中を扱わない。着地完了後の接近・戦闘・納品に役割を限定する。

## 6. D・Eの修正案：討伐と納品を切り替える

Cと並行して次を修正する。常時CollectFATE=Enabledによる代用は撤回する。

```text
Fighting：F.A.T.E敵を限定・対象固定、イベントアイテム数を監視
  10個以上 → HandInMoving → HandInInteracting → HandInConfirming
  納品成立・進捗100％未満 → Fighting
  どの状態でも100％ → Leaving
```

納品専用のBMRプリセットを別に用意する案が小さく実装しやすい。FateUtils（Handin有効、Collect無効、Sync有効、Chocobo無効）とNormalMovementを含め、AutoTargetとジョブ攻撃モジュールは含めない。移行時に敵ターゲット・オートアタック・残っている追尾を止める方法を確認して実装する。主ターゲットがなくてもFateUtilsが実行されること、モジュール順序も実機・ログで確認する。

納品中はBMRへ移動を任せ、AutoCollectorから敵接近経路を出さない。NPC識別子はBMRの `Hints.InteractWithTargetOID` 読取IPC（Framework/IPCProvider.cs:195）で観測できる。必要なら数量・NPCとの距離・相互作用要求の変化を納品状態に対応付ける。リクエストを観測しただけで納品成立扱いにはしない。

成立はイベントアイテム減少やHandInCountの増加を観測する。Progressだけの上昇は他人の納品かもしれない。数量読取失敗を0としない。NPC不在・移動停止・反映なしには期限・有限再試行を設ける。10未満になった瞬間に戦闘へ戻して会話を中断しないよう反映確認段階を通す。

厳密なF.A.T.E敵限定は、既存AutoTargetの設定だけでは不十分。AutoCollectorの対象管理とBMRの自動対象選定を二重に動かさない。方法は、BMR側に専用モジュール／対応IPCを設けるか、AutoCollector側で対象を一元管理してBMRに再選定させない構成を検証する。汎用ジョブモジュールが独自に別敵を拾わないことまで確認して採用する。BMR本体への変更が必要になったら、専用機能として他プリセットから分離する。
