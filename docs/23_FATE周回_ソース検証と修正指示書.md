## 1. 結論

F.A.T.Eを選び、マップ間を移動し、騎乗移動・戦闘・次のF.A.T.Eへの移行を繰り返す骨格は実装済み。ただし、ユーザーの①〜⑫をそのまま満たす状態ではない。

特に修正が必要なのは次の6点。

1. 巡回順は画面の上からではなく、設定リストに追加された順。
2. 最寄りF.A.T.Eよりも、パーティ・ボーナス・達成度等が優先される。
3. 「外周上空を経由して中央地上へ斜めに降下」という経路段階がない。
4. F.A.T.E外の敵への反撃を許し、生存中の敵からもターゲットを変更する。
5. 納品10個以上の自動移動・接触はあるが、納品中の戦闘を確実に抑止する構造ではない。
6. 100％で戦闘制御を解除しても、次の候補がなければ、その場から範囲外へ逃げる処理がない。

**【確認1】への回答：10個で納品NPCへ向かいアクセスする機能は、BossMod Rebornに委任する形で組み込まれている。ただし「被弾を無視して納品を完遂し、100％なら必ず即脱出する」という一連の保証は未完成。**

## 2. プラグイン全体の把握

中核は、通貨の条件を監視し、稼働中の処理を区切りで中断して交換所へ移動し、交換後に戻す機能。`MonitorService` が開始条件、`ExchangeExecutor` が交換の進行、`EarnerRegistry` が稼ぎ方の中断・復帰を束ねる。F.A.T.Eは `FateEarner` と `FateRunner` が担当する。

ほかに、収集品納品（`CollectableDeliveryRunner`）、納品と交換の反復（`CollectableCycleRunner`）、製作（`CraftRunner`）、素材取り出し（`RetainerRestockRunner`）、目標に応じた進行管理（`GoalRunner`）がある。F.A.T.Eの納品NPC処理と、収集品窓口への納品処理は別物。

F.A.T.Eの担当範囲は以下。

| 処理 | 担当 |
|---|---|
| マップ選択画面と候補一覧 | FateTab / FateZoneCatalog |
| F.A.T.E列挙・条件判定・選択 | FateScanner |
| 周回の状態遷移 | FateRunner |
| 騎乗と降車 | MountService |
| 移動経路と追従 | NavigationService → vnavmesh |
| テレポ先の解決・実行 | AetheryteService → Lifestream |
| ターゲット選択、攻撃、近距離移動、シンク、納品 | 専用プリセット → BossMod Reborn |
| 通貨交換との中断・復帰 | FateEarner |

### 巡回順の具体例

全解除から「黄金をまとめて選ぶ」だけを実行すれば、その時の表示順で追加される。しかし先にコザマル・カだけ選び、その後に黄金一括選択をすると、コザマル・カがリスト先頭に残る。オルコ・パチャを外して再度チェックしても末尾に移る。現在のコードに表示順へ正規化する処理は見つからない。

今回の受入順序は、ユーザーの指定を基に、オルコ・パチャ → コザマル・カ → ヤクテル樹海 → シャーローニ荒野 → ヘリテージファウンド → リビング・メモリー → オルコ・パチャとする。実行時のゲームシートとUI上で6件・順序・IDを確認すること。今回ゲームシートそのものから6件のIDを抽出したわけではない。

### 降下処理の具体的な問題

`TickMoving` は `BeginMove(destination, ..., flying)` で実際の経路を依頼する。その目的地には `LiftForFlight(ground)` を使う。

その後に `navigation.Tick(landing, ...)` に地上座標を渡しているが、**Tickは通常、経路を変更せず距離と進行状態を監視するだけ**。初回に騎乗中・まだ飛行していない状態で高くした目的地へ依頼すると、離陸しただけでは地上終点へ差し替わらない。経路終了後の `ShortOfTarget` でも `EnterFate` を呼ぶため、上空や不適切な位置で降車段階に進む可能性がある。

既に飛行中なら `LiftForFlight` は地上座標を返すので、地上へ向かう経路になる場合もある。ただし外周を経由する保証、中心へ降りる保証、一定の斜めの進入になる保証はない。コメントの「斜めに降りる」をそのまま実装完了の根拠にしてはいけない。

## 4. 納品F.A.T.E【確認1】の詳細

### 確認できた実装

- AutoCollectorの自動生成プリセットはFateUtilsを組み込み、HandinをEnabled、CollectをDisabledにしている。地面の拾得物を拾う代わりに討伐を続ける意図。
- `FateScanner.HasHandInItems`（248行）はFateシートのEventItemを使って10個以上を判定する。これはAutoCollector側の接近処理を止めるための判定であり、納品実行そのものではない。
- BMR `FateUtils.cs:89–105` は、シンク済み・Handin有効等を前提として、所持イベントアイテム数が10以上ならHandInを選ぶ。
- BMRは `ActiveFate.ObjectiveNpc` を引き、`InteractWithTarget` を設定する（同48–54行）。NormalMovementがNPC付近を移動目標に加える（NormalMovement.cs:169）。接触可能距離では実際に `InteractWithObject` を呼ぶ（Framework/Plugin.cs:396–405）。
- BMRの数量同期には `InventoryType.KeyItems` の読み取りがある（WorldStateGameSync.cs:1155–1183）。通常の鞄の枠の増減だけで判定する構成ではない。
- AutoCollectorは100％を読むと戦闘プリセットを解除し、同一マップの次候補があれば移行する。

したがって、自動納品は「コメントだけの未実装」ではない。ただしNPCアクセスで実際に納品が成立すること、対象F.A.T.Eごとの会話・反映遅延は実機確認が必要。

### 被弾を無視する保証が不足する理由

BMR AutoTarget.cs:162–171の実コードは概ね次の形。

```csharp
targetFateMobs = Progress < 100;
targetFateMobs |= HandInCount < 10 && heldItems < 10;
```

進捗50％・所持10個なら、最初の式がtrueなので、OR後もtrue。**「10個持ったら新しい敵を選ばない」というコメントと一致しない。** 現行プリセットはCollectFATEを指定しておらず既定Disabled。さらに通常の敵視対象もAutoTargetの候補に残り、ジョブの攻撃モジュールも有効なまま。

FateUtils側には戦闘中だから納品を取りやめる条件はなく、NPCを優先する移動はある。そのため「必ず敵へ引き返す」とまでは断定できない。しかし「被弾しても攻撃・追尾へ戻らず、NPCへ進み続ける」という排他的な納品モードは確認できない。移動と攻撃の競合を検証・修正する必要がある。

### 10個・23個・100％の扱い

- 10個以上で納品する閾値は実装済み。
- 「倒したら必ず1個」「合計約23個で100％」「猶予約1分」はユーザーから提示されたゲーム挙動。今回のソース調査だけではゲーム側の正しさを確定していない。
- 合計23個で終了する固定判定はない。100％の実測値で完了判定する現方針は維持すること。他プレイヤーの納品もあるため23固定に変更してはいけない。
- 10個単位なので、20個納品後に残り3個で足りる場面でも、現在は原則さらに10個貯める。これは「10個で納品」という要望には沿う。端数の早期納品は別の追加仕様とする。

### 100％後の待機と脱出

`LeaveFate` は納品F.A.T.Eに `pendingReward` を立てる。次の候補があれば同じマップ内で移動するが、なければ現在地でWaitingになる。`TickWaiting` と `TickTraveling` はpendingRewardがある間マップ変更を止める。最大90秒、またはF.A.T.E消失等で待機が解除される。

**「F.A.T.Eの円から脱出」と「マップからテレポで退出」は別々に扱う必要がある。** ユーザーの確認1は円からすぐ脱出して次へ進むことなので、同一マップで報酬を待つことと両立できる。次候補がない場合でも円の外へ出て待てるように修正すること。

次候補がゼロでも即他マップへ飛ぶという⑪の厳密解釈と、現行の報酬保護は衝突する。指示書では既存の報酬保護を維持する方針を暫定採用する。画面に「範囲外へ退避済み／報酬待ちのためマップ移動待機」を明示し、報酬が残る条件を実機で検証する。根拠なく待機を削除しない。

なお `RefreshPendingReward` は通貨の増加を測らず、F.A.T.E消失を「報酬が入りました」と記録している。これは受領の直接確認ではない。読取不能・エリア移動・同ID再出現等を区別し、ログも事実に合わせること。

## 6. 修正指示

以下を①〜⑫と確認1の受入条件として実装すること。コメント修正だけで完了にせず、制御の競合と状態遷移を直す。既存の交換・製作・緊急停止を壊さない。

### A. 巡回ルートを画面順に固定する

1. FateZoneCatalogの画面表示順からチェック済みマップを抽出し、実行用ルートを構築する。クリック順・全選択前の選択履歴に依存させない。
2. 開始時はルート先頭へ、枯渇時は現在ルート位置の次へ、末尾は先頭へ。
3. 既存設定も同じ順へ正規化するか、開始時に実行ルートへ変換する。IDの重複を除去し、存在しないID・移動できないエリアを検出する。
4. 周回中の選択変更で添字や空リストが壊れないよう、ルートを開始時に固定するか、明示的に安全な再構築を行う。交換復帰は元マップのルート位置を復元する。
5. 実際の巡回順を画面とログに表示する。

### B. 最寄りを第一基準にする

1. 要求されたモードでは距離を第一順位とし、パーティ追従・ボーナス・進捗による割込みを無効にする。既存機能を残すなら「最寄り順」と「従来の優先順」を区別する。
2. 距離の定義を統一する。暫定仕様はプレイヤーとF.A.T.E中心の水平距離、同距離は安定したID順。飛行経路長を意味するなら別仕様として説明する。
3. 70％時点のprefetchedを出発時にそのまま採用しない。出発位置で候補の存続・同じ湧き・条件・最近傍を再評価する。
4. マップ上の存在数、参加可能数、設定により除外した数を区別する。「FATEなし」と「条件に合うFATEなし」を表示し分ける。既定の残120秒・進捗90％制限は、厳密な全F.A.T.E周回と衝突することを明示する。

### C. 飛行と進入を明示的な段階にする

1. 騎乗 → 離陸確認 → 外周上空到達 → 中央付近地上へ降下 → 着地確認 → 降車確認 → 戦闘、を状態として分ける。
2. F.A.T.E中心C、進入方向の単位水平ベクトルu、半径rから、外周より少し外側の `C + u*(r+余裕)` を進入点として作る。高さは地形・飛行可否・到達可能性を考慮し、値と理由をログに残す。中心と同座標等でuが求まらない場合の代替方向も用意する。
3. 外周上空に到達してから、中央付近の歩行可能な床へ実際の経路を新規依頼する。NavigationService.Tickに別座標を渡すだけでは経路変更にならない。
4. 着地点は中央付近を基本とし、湖・崖等では参加範囲内の到達可能な代替床を選ぶ。動く最寄り敵を毎回着地点にしない。
5. 障害物回避を優先しつつ水平距離と高度が減る進入を作る。直線が地形を貫通する場合は迂回する。ShortOfTargetを着地成功に読み替えず、範囲・高さ・床・騎乗状態を検証する。
6. 飛行可能なのに短距離だから徒歩へ省略する挙動は要求モードでは行わない。飛行未解放等は「飛行不可」を示し、無言で理想動作に合格としない。

### D. 対象限定と撃破までの固定

1. 現在参加中のFateIdに一致する、生存・攻撃可能な戦闘敵だけを新規候補にする。非F.A.T.E敵への反撃も対象選定から除く。
2. 選んだ敵の識別子を保持し、生存・有効な間は別の近い敵が出現しても切り替えない。撃破・消失・攻撃不能になったときに解除し再探索する。
3. 再探索は最近傍。距離定義・同距離時のルールを決める。到達不能時の例外処理はログを出す。
4. BMRのRetarget=Hostilesを継続使用しない。NoTarget等だけで十分かを実装で検証し、敵視対象の除外と距離順位まで含めて要件を満たすようにする。外部プラグインとターゲットを毎フレーム奪い合う方式は避ける。
5. 移動先と攻撃対象を同じ保持対象から決める。FindNearestMobの座標検索だけでは攻撃対象の固定にならない。

### E. 納品中の制御を排他的にする

1. 10個以上を確認したら「納品へ移動」「NPCアクセス」「納品反映待ち」を明示する。新規敵選択・敵への追尾・攻撃を抑止し、被弾してもNPCへの移動方針を維持する。
2. BMRへの委任を残してよい。ただし現行FateUtils/AutoTargetの組合せだけで要件を満たすと判断しない。必要な一時方針・専用プリセット・対応IPCを検証し、取得できない制御を仮定しない。
3. 納品成立はイベントアイテム減少、HandInCount変化、Progress変化等から確認する。NPCに触れた回数を納品数にしない。相手の納品による進捗上昇とも区別する。
4. 数量取得失敗と0個を区別する。NPC不在・範囲外・会話が閉じない・反映遅延には期限と再試行制限を設ける。同じNPCへ無制限にアクセスしない。
5. 納品後100％未満なら戦闘へ復帰、100％なら直ちに離脱へ移る。23個固定条件は追加しない。
6. プリセット既存・ユーザー指定の場合も、FateUtils、NormalMovement、Handin有効等の必要条件を検証する。現状はHandin=Disabledが残っていてもEnsureが検出しない。`ApplyFateStrategies` も有効時にはHandinを明示修復しないため、既定値への一時方針を送れない制約を踏まえた解決が必要。

### F. 次候補の有無に関係なく100％で脱出する

1. 戦闘・納品・降下中も含め、対象F.A.T.Eの100％を優先処理する。現在はLandingがTickInFateより先であり、その間は100％判定を通らない。
2. 攻撃と追尾を解除し、円外の退避点へ移動する独立したLeaving処理を作る。次のF.A.T.Eがない場合も必ず円の外へ出る。
3. 騎乗可能なら即騎乗・離陸。戦闘状態でゲームが騎乗を受け付けない場合は、攻撃せず地上で退避を開始し、戦闘解除後すぐ騎乗・離陸する。「即時」は離脱判断の開始を意味し、ゲーム側で不可能な即騎乗を保証しない。
4. 納品報酬待ちは円外・同一マップで行い、同一マップに候補があれば周回を続ける。マップ移動だけ保留する方針を画面に説明する。
5. pendingRewardを単一値で上書きせず、短時間で複数の納品F.A.T.Eを完了しても全件を追跡できるようにする。キーにTerritoryId・FateId・開始時刻を含める。
6. F.A.T.E消失と報酬受領を同一視しない。確認可能な報酬情報と突き合わせ、確認不能なら「終了検知・受領未確認」と記録する。
7. 発生識別子と完了処理を統一し、100％を毎フレーム拾って再入場したり、Completedを重複加算しない。

### G. 連続運転を止める失敗分岐を修正する

1. TickTravelingのタイムアウト判定を、テレポ要求拒否のreturnより前でも実行する。現状は拒否が続くと60秒判定に一度も届かない。再試行間隔・最大待機・行き先を飛ばす条件を明確にする。
2. 開始時にLifestreamの使用可否と選択マップへのテレポ先を確認する。解放済みエーテライトがない場合はマップ名付きで説明する。
3. メッシュ読込み中を到達不能として即座に2回数えて見送りにしない。読込み待ちと経路失敗を区別する。
4. NavigationServiceのスタック再試行は現在 `fly=false` 固定。F.A.T.E飛行で使う際は元の移動モードを維持する。
5. 交換復帰、緊急停止、BMRプリセット解除、vnavmeshの遅れて完成した経路を止める既存処理を回帰確認する。
