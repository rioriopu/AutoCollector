# S5 実装仕様: 交換ショップで 1 個だけ交換する

対象: `AutoCollector` / FFXIV Dalamud プラグイン Auto Collector
前提資料: `docs/03_実装中の発見.md` F-6〜F-9、`docs/02_MVP実装計画.md` §3
位置づけ: S5 は「手動で開いたショップに対し、UI のボタンから 1 個だけ交換する」までを対象とする。移動・対話・タブ切替・複数個交換・自動実行は S5 の範囲外。

**この仕様の設計原則: 通貨の消費は取り消せない。判断材料が 1 つでも欠けたら撃たない。撃った後は、成功が確認できなくても二度と撃たない。**

## 0. 実装前に必ず直す既存コードの欠陥

S5 の実装に着手する前に、以下を修正する。いずれも「撃つ判断」に直接影響する。

### 0-1. `IsConfident` が「特定できない」状態で true になる（実バグ・最優先）

`AutoCollector/Automation/ShopService.cs:241-248`

```csharp
if (perfectMatches > 1)
{
    return new ShopIdentification(
        best,               // ← ShopId が非 null のまま返る
        bestScore,          // ← :232 を通過済みなので bestScore == entries.Count が確定
        entries.Count,
        $"内容が完全一致するショップが {perfectMatches} 件あり、どれか特定できません");
}
```

これが `ShopService.cs:315` の

```csharp
public bool IsConfident => this.ShopId is not null && this.TotalEntries > 0 && this.MatchedEntries == this.TotalEntries;
```

に渡ると **必ず `true`** になる。Detail は「特定できません」なのに、実行ゲートを `IsConfident` に置くと通過する。

**修正:**

```csharp
public sealed record ShopIdentification(
    uint? ShopId, int MatchedEntries, int TotalEntries, string Detail, bool Ambiguous = false)
{
    public bool IsConfident =>
        this.ShopId is not null && this.TotalEntries > 0
        && this.MatchedEntries == this.TotalEntries && !this.Ambiguous;
}
```

`perfectMatches > 1` の分岐では `ShopId` に **`null`** を入れ、`Ambiguous: true` を立てて返す。呼び出し側が ShopId を使える状態にしない。

### 0-2. `Match` がショップ非依存

`ShopService.cs:259` の `Match(ExchangeDefinition, IReadOnlyList<ShopEntry>)` の本体（:261-306）に `definition.ShopId` の参照が 1 つも無い。比較対象は `entry.ItemId`（:266）と `found.CostAmount`（:297）だけで、`IdentifyShop` の結果と構造的に結び付いていない。

**修正:** シグネチャを変え、冒頭でショップ同一性を必須条件にする。

```csharp
public ShopMatchResult Match(
    ExchangeDefinition definition,
    ShopIdentification identification,
    IReadOnlyList<ShopEntry> entries)
{
    if (!identification.IsConfident || identification.ShopId != definition.ShopId)
    {
        return new ShopMatchResult(ShopMatchKind.ShopMismatch, null,
            $"開いているショップを特定できないか、定義のショップ {definition.ShopId} と一致しません（{identification.Detail}）");
    }
    // 以下、既存の ItemId / コスト照合
}
```

`ShopMatchKind` に `ShopMismatch` / `CurrencyMismatch` / `IndexOutOfRange` / `EntryCountMismatch` を追加する。

`AutoCollector/Ui/MainWindow.cs:179-188` の

```csharp
if (identification.ShopId is { } shopId && def.ShopId != shopId) { continue; }
```

は `ShopId == null` のとき条件が短絡してフィルタが無効化される。**この書き方を交換の実行経路に流用しない。** UI 側も `identification.IsConfident` が false なら照合表そのものを出さない形に変える。

### 0-3. `index` が無検査で通る

`AutoCollector/Automation/ShopExchangeCurrencyReader.cs:35`

```csharp
AtkValueType.UInt => new AtkValueProbe(index, true, typeName, value.UInt, true),
```

`Int` は負値を弾いている（:38-40）が、`UInt` は `0xFFFFFFFF` でも `Usable=true` で通り、`ShopService.cs:151` でそのまま `ShopEntry.Index` に入る。`(int)0xFFFFFFFF` は `-1` で、これは ICE がショップを閉じるコマンド値として使っている値（`fork-ICE/ICE/Scheduler/Tasks/Task_BuyCosmoItems.cs:120`）。

**修正:** §2 の事前条件（P-11〜P-13）で構造的に弾く。読み取り側は変更しない（読み取りは診断用途にも使うため、弾くのは発火側の責務にする）。

### 0-4. `ShopAddonLayout.Validate` が配列間隔を検査しない

`AutoCollector/Automation/ShopAddonLayout.cs:74-78` は `MaxEntries` を 1〜4096 で許すが、既定値では `EntryItemId`(1066) と `EntryIndex`(1310) の間隔は **244** しかない。245 件以上読むと ItemId 配列の読み取りが index 配列に食い込む。

**修正:** `Validate` に追加する。

```csharp

    reason = $"MaxEntries {this.MaxEntries} × EntryStride {this.EntryStride} が配列間隔 {minGap} を超えています。ItemId 配列の読み取りが別の配列に食い込みます";

```

### 0-5. 報酬の所持数が装備・アーマリーを数えない


### 0-6. 複数コスト／複数報酬エントリがモデル化されていない

`AutoCollector/Game/ExchangeResolver.cs:122-133` は報酬を最初の 1 件で `break` し、:140-169 のコストループは対象通貨に一致するものだけを `list.Add` して他の非ゼロコストを捨てている。トームストーン以外にアイテムも消費するエントリだと、「通貨が減った AND 報酬が増えた」が両方成立してしまい、モデル化していない消費を見逃す。

### 0-7. `CallbackRecorder.AddonFilter` が固定で、F-9 は「ダイアログが出なかった証拠」にならない

なお `CallbackRecorder.cs:127` は 1 レコードあたり先頭 32 値までしか記録しない。フィルタを外して計測するときは、32 値を超えるアドオンで欠落が起きうる点に留意する（今回の 4 値は影響しない）。

### 1-4. 使ってはならないもの

**`AddonMaster.ShopExchangeCurrency.ShopItemInfo.Select()` を交換の実行に使ってはならない。**

`_ac_refs/AutoRetainer/ECommons/ECommons/UIHelpers/AddonMasterImplementations/ShopExchangeCurrency.cs:41-50`

```csharp
public class ShopItemInfo(ShopExchangeCurrency master)
{
    public uint ItemId;
    public uint Index;      // ← uint
    public uint CostAmount;
    public void Select(int amount = 1)
    {
        Callback.Fire(master.Base, true, 0, Index, amount);   // ← 3 値
    }
}
```

`Index` が `uint` フィールドであるため `Callback.cs:86-89` により必ず `UInt` で送られ、**値の個数（3 対 4）と index の型（UInt 対 Int）の 2 点**で実測と食い違う。読み取りは `ShopExchangeCurrencyReader` を自前で持っているため、`Select()` を経由する理由がない。

**書いてはならない記法:**

- `0u` / `1u` — `u` を付けた瞬間 `case uint` に落ちて `UInt` になる
- `entry.Index` を素で渡す — `ShopService.cs:13` の `ShopEntry.Index` は `uint`
- `var` で受けた `uint` をそのまま渡す

`Callback.Fire` は `params object[]` なので、**型ミスをコンパイラが一切検出しない。** 必ず `int` 型の局所変数を経由させる。

## 2. 発火前の事前条件チェックリスト

### 2-1. 実行の構造（最重要）

**読み取り → 全検証 → 発火を、`Framework.Update` 内の 1 つの同期ブロックで完結させる。**

- UI のボタンは `pendingRequest` を立てるだけにする。ImGui の `Draw` から直接撃たない。
- ブロック内に `await` / `TickScheduler` / ImGui のフレーム境界を一切挟まない。
- アドオンポインタは `GenericHelpers.TryGetAddonByName` で **1 回だけ**取得し、その同一ポインタで読み取りと発火の両方を行う。

現行の `ShopService.TryReadEntries`（`ShopService.cs:77-170`）は内部でアドオンを自前解決するため、読み取りと発火で 2 回解決することになり、両者が同一インスタンスである保証がない。**次のリファクタを行う。**

```csharp
// 新規追加。addon を引数で受け取る本体。
public unsafe bool TryReadEntriesFrom(
    AtkUnitBase* addon, out IReadOnlyList<ShopEntry> entries,
    out ShopHeader header, out string failureReason);

// 既存の TryReadEntries は、アドオンを解決して上を呼ぶだけの薄いラッパにする。
```

ゲームロジックは単一スレッドなので、この 1 ブロック内では他プラグインのハンドラもタブ切替もサーバ応答も割り込めない。**これが index 陳腐化に対する唯一の完全な防御である。**

## 3. 発火後の状態遷移

### 3-1. 状態機械（S5 の範囲）

```
Idle
 └─(UI のボタン押下)──> Armed
Armed
 └─(次の Framework.Update で §2 のチェックを全通過)──> [発火] ──> WaitOutcome
 └─(1 つでも不成立)──────────────────────────────────> Error（撃っていない）

WaitOutcome
 ├─(通貨減 AND 報酬増)──────────────> Verified ──> Done
 ├─(ShopExchangeCurrencyDialog 出現)─> CancelDialog ──> Error
 ├─(SelectYesno 出現)───────────────> ConfirmDialog ──> WaitOutcome へ戻る
 └─(デッドライン到達)───────────────> Error（Unresolved）

任意の状態 ──(/ac stop / Dispose / Fail)──> [Cleanup] ──> Error
```

**`WaitOutcome` から `Armed` へ戻る辺を作らない。** これが二重支払いに対する構造的な防御である。`ConfirmDialog` から `WaitOutcome` へ戻る辺だけが唯一のループで、そこでは callback を撃たない（ボタンを押すだけ）。

### 3-2. `WaitOutcome` の毎フレーム処理

発火した次のフレームから、以下を順に評価する。**判定は 1 フレーム目には行わず、必ず次フレーム以降にポーリングする。**

```
1. ShopExchangeCurrencyDialog が IsAddonReady か
     → はい: CancelDialog へ（§3-5）
2. SelectYesno が出ているか
     → はい: ConfirmDialog へ（§3-3）
3. 所持数を再取得して判定（§3-4）
     → 成功: Verified
     → 変化なし: Continue（デッドラインまで待つ）
     → 想定外の差分: Error（ExchangeUnexpectedDelta）
4. デッドライン到達 → Error（ExchangeUnresolved）
```

### 3-3. `ConfirmDialog`: 確認ダイアログの扱い

**無条件に Yes を押してはならない。**

`GenericHelpers.TryGetAddonMaster<SelectYesno>` は `Svc.GameGui.GetAddonByName(Addon, 1)` を呼ぶだけで、**インデックス 1 のアドオンしか見ない**（`AddonHelpers.cs:139-152`）。他プラグインや別要因のダイアログが先に開いていると取り違える。

AutoRetainer と同じく、インデックスを走査して本文を照合する（`_ac_refs/AutoRetainer/AutoRetainer/Helpers/Utils.cs:1750-1770`）。

```csharp
// i = 1..N を走査し、テキストノード id 2 の本文に報酬アイテム名が含まれるものだけを掴む
for (var i = 1; i < 100; i++)
{
    var addon = (AtkUnitBase*)Svc.GameGui.GetAddonByName("SelectYesno", i).Address;
    if (addon == null) { break; }
    if (!GenericHelpers.IsAddonReady(addon)) { continue; }

    var textNode = addon->GetTextNodeById(2);
    if (textNode == null) { continue; }
    var text = GenericHelpers.ReadSeString(&textNode->NodeText).GetText();

    if (!text.Contains(rewardName, StringComparison.Ordinal)) { continue; }
    // ここで初めて対象と確定する
}
```

`rewardName` は `Svc.Data.GetExcelSheet<Item>()?.GetRowOrDefault(definition.RewardItemId)?.Name.ExtractText()`。空文字なら押さずに `Error`。

押す前に必ず本文を `AnomalyLog.Info("Shop", $"確認ダイアログ: {text}")` に残す。

**Addon シートの特定行との突き合わせは行わない。** AutoRetainer が使っている行 2436 / 11502（`GCContinuation.cs:104`）は交換確認ではなく「装備できない」系の確認であり、GC 交換確認は `AutoRetainer/Lang.cs:337` のコメントが示す行 **3290** である。`SpecialShop` 交換に対応する Addon 行は特定できていないため、報酬アイテム名の部分一致のみを条件にする。

押し方:

```csharp
var ym = new AddonMaster.SelectYesno((nint)addon) { RespectDisabledButtons = true };

// Yes() は YesButton の null チェックを行わない経路がある。
// SelectYesno.cs:41 の null チェックは「強制有効化」ブロックの内側だけで、
// :48 の ClickButtonIfEnabled(Addon->YesButton) は if の外にあり、
// !AddonMasterBase.cs:63 の button->IsEnabled で null を逆参照する。
// これは RespectDisabledButtons の値と無関係に起きるので、自分で確認する。
if (ym.Addon->YesButton == null
    || !ym.Addon->YesButton->IsEnabled
    || !ym.Addon->YesButton->AtkResNode->IsVisible())
{
    // ゲームが押させないと決めている。押さずに Error。
}
else
{
    ym.Yes();
}
```

**`RespectDisabledButtons = true` は必須。** 既定は `false`（`SelectYesno.cs:25`）で、その場合 `Yes()` は無効化された Yes ボタンの `NodeFlags` の bit5 を XOR で立ててから押す（`SelectYesno.cs:39-47`）。bit5 は `NodeFlags.Enabled(0x20)`（`_ac_refs/FFXIVClientStructs/FFXIVClientStructs/FFXIV/Component/GUI/AtkResNode.cs:392`）であり、`AtkComponentButton.IsEnabled` はまさにそのフラグを読む（`AtkComponentButton.cs:24`）。つまり既定のままだと**ゲームが押させないと決めたボタンを無理やり押す。**

押した後は `WaitOutcome` へ戻る。`Yes()` は `void` で押せたかを返さない（`SelectYesno.cs:37-49`、`!AddonMasterBase.cs:61-70`）ため、押下の成否は結果検証でしか分からない。

**`SelectYesno` が出なくても失敗にしない。** 出るかどうかはジルコンのショップでは未確認であり、出ないまま §3-4 の条件が満たされることもありうる設計にする。

### 3-4. `Verified`: 成功の判定条件

**権威データは `InventoryManager` 一本にする。** `AtkValues[86]`（画面上の通貨量）は画面の写しであり、更新タイミングを断定できるソースがない。撃つ前の整合チェック（P-14）にのみ使う。

```csharp
// 報酬は装備・アーマリーを含めて数える（§0-5）
CurrencyService.TryGetCount(definition.RewardItemId, out var rewardAfter,
                            includeEquipped: true, includeArmory: true);
CurrencyService.TryGetCount(definition.CurrencyItemId, out var currencyAfter);

var rewardOk   = rewardAfter   >= inFlight.RewardBefore   + (int)definition.RewardQuantity;
var currencyOk = currencyAfter <= inFlight.CurrencyBefore - (int)definition.CurrencyCost;
```

**等値ではなく方向と下限で判定する。** 検証ウィンドウ中に別要因（周回中の通貨入手、他プラグイン、パーティ配分）で所持数が動くと、等値判定では成功しても失敗と判定される。失敗判定はリトライを誘発しやすいため、偽陰性を減らす方向に倒す。ただし **どちらに転んでも再送はしない**（§4）。

判定を 3 分類し、扱いを分ける。単一の `ExchangeVerificationFailed` にまとめると「何も起きなかった」と「予想外のものが動いた」が区別できない。

| 分類 | 条件 | 状態 | コード |
|---|---|---|---|
| 成功 | `rewardOk && currencyOk` | `Verified` → `Done` | — |
| 未成立の疑い | 両方まったく動いていない（`rewardAfter == RewardBefore && currencyAfter == CurrencyBefore`） | `Error` | `ExchangeNotApplied` |
| 想定外 | 上記以外（片方だけ動いた、量が合わない） | `Error` | `ExchangeUnexpectedDelta` |

**`ExchangeNotApplied` でも `inFlight` は「未解決」として残し、自動で再送しない。** UI に赤字で「前回の交換の結果が未確認です」と出し、ユーザーがゲーム内で実際の所持数を確認してから手動でクリアする。

### 3-5. `CancelDialog`: 数量ダイアログが出た場合

MVP は数量指定に非対応のため、`ShopExchangeCurrencyDialog` が出たら**確実に閉じたうえで失敗**にする。

```csharp
var dlg = new AddonMaster.ShopExchangeCurrencyDialog((nint)dialogAddon);
dlg.Cancel();   // CancelButton は id 18（ShopExchangeCurrencyDialog.cs:15, :20）
```

`Cancel()` も `void` なので、押した後 `IsAddonReady` が false になるまでポーリングする。1 s throttle で最大 3 回。それでも閉じなければ `Callback.Fire(dialogAddon, true, -1)` へエスカレーションする（`GCContinuation.cs:555-562` の `CleanupUI` が同じ形）。

**数量が初期値のまま `Exchange()`（id 17）を押す事故だけは絶対に避ける。** `ExchangeButton` には一切触れない。

閉じたら `Error(ConfirmDialogUnexpected)`。ただしこの時点で交換が成立している可能性を否定できないため、§3-4 の所持数再取得だけは必ず行い、結果を `AnomalyLog` に残す。

### 3-6. タイムアウト表

| 状態 | 毎フレームの動作 | 成功条件 | タイムアウト | 失敗コード |
|---|---|---|---|---|
| `Armed` | §2 のチェックリストを評価 | 全条件成立 → 発火 → `WaitOutcome` | **1 フレームのみ**。次フレームまで持ち越さない（index の陳腐化を防ぐため、失敗したら `Error` に落としてユーザーに押し直させる） | §2 の各コード |
| `WaitOutcome` | §3-2 の順で評価 | §3-4 の成功条件 | **15 s** | `ExchangeUnresolved` |
| `ConfirmDialog` | 本文照合 → Yes | Yes を押した、または `SelectYesno` が消えた | **10 s**（`WaitOutcome` の 15 s とは別枠） | `ConfirmDialogTimeout` |
| `CancelDialog` | Cancel → Fire(-1) | `ShopExchangeCurrencyDialog` が非表示 | **10 s** | `ConfirmDialogUnexpected` |
| `Verified` | — | 即 `Done` | — | — |

**`WaitOutcome` のタイムアウトは「交換が成立していない」ことを意味しない。** サーバ応答が遅れただけの可能性があるため、必ず `Error` に落とし、`inFlight` を未解決として残す。**タイムアウトから `Armed` へ戻す遷移を作ってはならない。**

### 4-1. `EzThrottler` を二重発射の防止に使わない

### 4-2. 明示的なラッチ

```csharp
/// <summary>撃った 1 回分の記録。撃つ直前に立て、結果が確定するまでクリアしない。</summary>
public sealed record PurchaseAttempt(
```

**発火の直前に `inFlight` へ代入し、その後に `Callback.Fire` を呼ぶ。** 順序を逆にしない。

- `inFlight != null` の間は `Armed` の入口（P-2）で即座に拒否する。
- `Done` / `Error` のいずれに落ちても、`inFlight` は**自動ではクリアしない**。ユーザーが UI で明示的にクリアするまで残す。
- `inFlight` を `Config` に持たせ、代入直後に `EzConfig.Save()` を呼ぶ（`Plugin.cs:75` と同じ手段）。プラグインのリロードやクラッシュを跨いでも残るようにする。
- `Plugin.Load()`（`Plugin.cs:53`、`TickScheduler` 経由）で `inFlight` が残っていたら、自動実行を一切開始せず UI に赤字で「前回の交換の結果が未確認です」と表示する。

### 4-3. UI 側

- 交換ボタンは押下時に `pendingRequest` を立てるだけ。`Draw` から `Callback.Fire` を呼ばない。
- `pendingRequest != null` または `inFlight != null` の間は、ボタンを描画しないか無効化する。ImGui のボタンは押しっぱなしやウィンドウ再描画で複数フレーム true を返しうる。
- `pendingRequest` は `Framework.Update` の先頭で必ず消費し、成否にかかわらず null に戻す。

## 5. 中断・緊急停止時の後始末

現行の `Plugin.EmergencyStop`（`AutoCollector/Plugin.cs:149-155`）はログとチャット出力だけで、`:154` に「S8 以降でここに Cleanup を追加する」というコメントがある。S5 では**最低限、以下を実装する**（移動停止・外部抑制解除は S5 の範囲外なので、フックだけ用意して no-op にしておく）。

### 5-1. 構造

**`EmergencyStop` を「その場で全部やる同期関数」にしない。** 実際に閉じるには複数フレームかかる。

```csharp
internal void EmergencyStop(string reason)
{
    // 手順 0 だけを同期で行う
    this.aborted = true;
    this.pendingRequest = null;
    this.cleanupReason = reason;
    this.cleanupStep = CleanupStep.StopMovement;
    this.cleanupDeadline = DateTime.UtcNow.AddSeconds(30);

    this.AnomalyLog.Warn("Stop", $"緊急停止しました: {reason}");
    Svc.Chat.Print($"[Auto Collector] 停止しました: {reason}");
}
```

以降の手順は `OnFrameworkUpdate` から回す。各手順は**べき等**で、**失敗しても次の手順を止めない**。`try/finally` ではなく逐次のステップとして実装する。

### 5-2. 手順（順序厳守）

| # | 手順 | 内容 | 上限 |
|---|---|---|---|
| **0** | **停止ゲート（同期・最優先）** | `aborted = true`、`pendingRequest = null`。**Purchase 系 callback の送信経路を完全に封鎖する。** `inFlight` はクリアしない（未解決として残す） | 即時 |
| **1** | 移動停止 | S5 では no-op。S6 以降で `vnavmesh` の停止を入れる（自分が移動を開始していた場合のみ） | — |
| **2** | **エリア移動の判定** | `Svc.ClientState.TerritoryType` が交換開始時に記録した値と違う → 手順 3〜5 を**全部スキップ**して手順 6 へ。アドオンは既に破棄されているため触ってはならない | 即時 |
| **3** | **内側のダイアログを閉じる** | `SelectYesno` があれば `Callback.Fire(addon, true, -1)`。**絶対に `Yes()` を呼ばない。** `ShopExchangeCurrencyDialog` があれば `Cancel()`（id 18）→ 閉じなければ `Fire(addon, true, -1)`。いずれも 1 s throttle | 各 5 s |
| **4** | **ショップを閉じる** | `addon->Close(true)`（`_ac_refs/FFXIVClientStructs/FFXIVClientStructs/FFXIV/Component/GUI/AtkUnitBase.cs:287` の `[VirtualFunction(4)]`）を 1 s throttle で最大 3 回。消えなければ `Callback.Fire(addon, true, -1)` を最大 3 回。毎回 `TryGetAddonByName` で取り直し、`IsAddonReady` が false になったら成功 | 10 s。失敗しても `ShopCloseFailed` を記録して次へ進む |
| **5** | 会話メニューの残骸 | `SelectString` / `SelectIconString` / `Talk` が残っていたら `Callback.Fire(addon, true, -1)`。**自分が開いた記録があるものだけ**（§5-3） | 5 s |
| **6** | occupied の解除待ち | `GenericHelpers.IsOccupied()` が false になるまで待つ。抜けなくても次へ進む | 10 s |
| **7** | 外部抑制の解除 | S5 では no-op。S7 以降で `SetSuppressed(false)`（**自分が true にした場合のみ**） | — |
| **8** | ターゲット解除 | `Svc.Targets.Target = null` | 即時 |
| **9** | 記録 | `AnomalyLog` に理由と各手順の結果を残す。`inFlight` が残っている場合は「結果未確認」として赤字で UI に出す | 即時 |

**内側（ダイアログ）→ 外側（ショップ）→ 会話メニュー の順序を守る。** 逆順にするとダイアログだけが孤立して残り、その後の `-1` が意図しない対象へ飛ぶ。

**手順 4 で `Close(true)` を先に試す理由:** `Callback.Fire(addon, true, -1)` は購入コマンドと**同じ経路**を通る。`Close(true)` は別の仮想関数であり、値の取り違えが購入として解釈される余地がない。ICE は同一リポジトリ内で両方を使っており（`Task_BuyCosmoItems.cs:120` が `Fire(-1)`、`:153` が `Close(true)`）、使い分けの理由はコード上に記述がないため、**誤爆しにくい側**を第一手段にする。

### 5-3. 所有権の判定

`GenericHelpers.TryGetAddonByName` は名前で最初のインスタンスを返すだけで、誰が開いたかの情報を持たない（`AddonHelpers.cs:139-152`）。**名前で見つかったから閉じる、をやってはならない。** 他プラグインや手動操作で開いたショップを閉じると、そちらの自動化やユーザーの買い物を壊す。

`Svc.AddonLifecycle`（`_ac_refs/AutoRetainer/ECommons/ECommons/DalamudServices/Svc.cs:16` の `IAddonLifecycle`）で記録する。

```csharp
Svc.AddonLifecycle.RegisterListener(
    AddonEvent.PostSetup,
    new[] { "ShopExchangeCurrency", "ShopExchangeCurrencyDialog", "SelectYesno", "SelectString", "SelectIconString" },
    this.OnAddonSetup);
```

- 自分の状態機械が `Armed` 以降 `Done`/`Error` 以前にいる間に `PostSetup` が来たアドオンの `args.Addon.Address`（`nint`。`dalamud-patch/Dalamud/Dalamud/Game/NativeWrapper/AtkUnitBasePtr.cs:21`）だけを `OwnedAddons` に記録する。
- `AddonEvent.PreFinalize` で除去する。
- Cleanup では `OwnedAddons` に無いインスタンスには一切 callback を撃たない。

**注意:** `PreFinalize` はアドオンが非表示になっただけでは発火しない（`dalamud-patch/Dalamud/Dalamud/Game/Addon/Lifecycle/AddonEvent.cs` の remarks）。古い `nint` が残り、そのアドレスが後に別アドオンへ再利用されうる。したがって:

- 保存するのは `nint` の値だけにし、**それを逆参照しない**（取り直したポインタのアドレスと突き合わせるだけに使う）。
- 記録に時刻を持たせ、一定時間（60 s）で失効させる。
- 所有権判定は「`nint` が一致」かつ「いまその名前で取得したアドオンが `IsAddonReady`」の両方を満たすこと。

**S5 のデバッグ実行ではユーザーが手動でショップを開くため、`OwnedAddons` は空のままになる。** その場合 Cleanup はショップを閉じず、`AnomalyLog.Info("Shop", "自分が開いたショップではないため閉じません")` を残すだけにする。これは正しい挙動である。

### 5-4. `Dispose` での短縮版

`Dispose`（`Plugin.cs:157-188`）では手順 6 の「待ち」ができない。順序を次のようにする。

1. `Svc.Framework.Update -= this.OnFrameworkUpdate`（現行 `:161` のまま。最優先を維持）
2. `Svc.AddonLifecycle` のリスナ解除
3. 外部抑制の解除（S7 以降。同期）
4. `inFlight` が残っていれば `EzConfig.Save()` で確実に永続化する
5. ショップ／ダイアログの閉鎖を **1 回だけ**試行し、結果を待たない（所有権判定は通す）
6. `Svc.Targets.Target = null`
7. `this.CallbackRecorder?.Dispose()`（現行 `:165`）
8. `ECommonsMain.Dispose()`（現行 `:187`）

## 8. 未解決事項（S5 の実装では前提にしない）

以下は本仕様では「撃たない側に倒す」ことで回避しており、**実装の根拠として使っていない**。

1. **3 値（`Fire(0, index, amount)`）でも交換が成立するか。** ECommons の `Select()` は 3 値で、ICE がそれを宇宙探索のショップで使っているコードは存在するが、そのコードが実際に成功したという証拠はリポジトリ内にない。実測できている 4 値で撃つ以外に安全な選択肢はない。
2. **第 1 値 `0` の正確な意味。** ソースにも FFXIVClientStructs にも記述がない。ICE の実装から `4` = タブ切替（`Task_BuyCosmoItems.cs:364`）、`-1` = 閉じる（`:120`）であることは分かるが、`0` についての記述はどこにもない。「購入」と断定して他コマンドに流用してはならない。
3. **第 4 値が `Type=0` でなければならないのか、単にゲームが使っていない領域なのか。** `ZeroAtkValue` で `Type` レベルは一致するが、union のペイロード 8 バイトの一致は `CallbackRecorder` が記録していないため検証不能。
4. **ジルコンのショップで `SelectYesno` が出るか。** §7-A で確定する。ICE の実装は宇宙探索のショップで出ることを示唆するが、それは防御コードの存在からの推論であり証拠ではない。本仕様は**出ても出なくても壊れない**設計にしてある。
5. **`ShopExchangeCurrency` で `ShopExchangeCurrencyDialog` が開く条件。** `GrandCompanyExchange` には per-entry の `OpenCurrencyExchange` フラグ（`ReaderGrandCompanyExchange.cs:22`）があるが、それがダイアログ出現を決めている証拠はない（`GCContinuation.cs:443, :494` の分岐は `itemInfo.ItemID == VentureItem` というアイテム ID 比較）。`ShopExchangeCurrency` 側に相当するフラグがどこにあるかは未特定。
6. **個数を 2 以上にしたときの挙動。** 第 3 値を変えるだけで足りるのか、数量ダイアログ経由になるのかは未実測。MVP が 1 個固定である限り問題にならない。
7. **`AtkValues[1310+i]` の index が `SpecialShop` の何に対応するか。** §7-B で確定する。
8. **`AtkValues[86]` が交換直後に何フレームで更新されるか。** 断定できるソースがないため、成否判定には使わない。
9. **`AtkUnitBase.NumBlockingAddons`（`AtkUnitBase.cs:71`）でモーダルの被りを検出できるか。** 参照した全リポジトリに使用例が 0 件で、誰がこのカウンタを増やすかを示すコードもない。**P-5 の必須条件に入れない**（アドオン名の列挙で代替する）。§7-A の計測ついでに値を観察し、有用性が確認できたら追加を検討する。
10. **開いている `ShopExchangeCurrency` がどの `SpecialShop` 行かを、内容推定に頼らず直接読む方法。** `EventFramework.GetEventHandlerById`（`_ac_refs/FFXIVClientStructs/FFXIVClientStructs/FFXIV/Client/Game/Event/EventFramework.cs:75-76`）と `EventHandlerModule.EventHandlerMap`（`EventHandlerModule.cs:9`）は実在し、`SpecialShop` の ContentId は `0x1B`（`EventHandler.cs:447-448`）だが、「いま開いているショップの EventHandler をどう一意に選ぶか」は未検証。参照した全プラグインに使用例が無い。Phase 2 で調査する。
11. **`FireCallback` の第 3 引数の意味。** FFXIVClientStructs では `close`（既定 `false`）と命名されており（`AtkUnitBase.cs:218`）、ECommons が `updateState` と呼んでいるだけ。実測が `True` だったので `true` を再現するが、この引数が何を制御しているかは不明。
