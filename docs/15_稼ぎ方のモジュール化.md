# 稼ぎ方のモジュール化

対象: `AutoCollector`
ブランチ: `feature/earner-modules`

## なぜ分けるのか

**分けるのは「稼ぎ方」だけ。交換は 1 本のまま。**

```
稼ぎ方（戦闘 / クラフター / 将来のギャザラー）  ← 分ける
        ↓ 通貨が貯まる
交換（窓口・区分・歯止め・検証）                ← 分けない
```

交換の歯止め（`ExchangeLimits`）は 2026-09-17 に 1 本化した。
窓口ごとに分かれていたことが、所持の上限を無視して買い続ける重大な不具合の原因だった。
**ここを再び分ける案は採らない。**

一方、「いま誰が動いているか」「止める・戻す」「自力で通貨を増やせるか」は
稼ぎ方ごとに違う。ここが共通側に散っているため、次の種類の不具合が繰り返し出ている。

| # | 内容 |
|---|---|
| F-60 | 止めるとき立てた旗を、戻す側が全部下ろしていない |
| F-61 | 周回を止める側が「まだ渡せていない交換」を知らない |
| F-68 | 止めたあと、製作だけが動いて納品が弾かれる（旗が 2 本あって片方しか見ていなかった） |

**この 3 件はいずれも「複数の実行体が互いの状態を覗き合う」構造から出ている。**
分けると構造で潰せる。

**効かない種類もある。** F-67（交換画面の区分）や F-69（選択の確認）は
ゲーム画面の読み方の問題で、モジュール化では防げない。過大評価しないこと。

## 採った方針

**既存の型を 1 つも移さない。** `IEarner` という差し替え口と `EarnerRegistry` を新設し、
戦闘（`AutoDutyIpc` / `AutoDutyKeeper` / `AutoDutySetup`）とクラフター
（`GoalRunner` / `ArtisanIpc`）へ委譲するアダプタを挟む。

### 設定は作り直さない

`Config` の器を `Config.Combat` / `preset.Crafter` へ移す案もあったが**採らない**。

`EzConfig` は Newtonsoft を使うため、**プロパティ名を変えると旧キーが読まれず既定値に戻る。**
`KeepAutoDutyLooping=false` や `CraftKeepFreeSlots=115` を入れている利用者の値が黙って消える。
しかも移行が終わった時点では稼ぎ方はまだ 1 つも分かれておらず、払うリスクに対して得るものが無い。

代わりに**置き場所の規約だけを決める**。

| 置き場所 | 何を置くか |
|---|---|
| `Config` 直下 | 稼ぎ手そのものの動かし方（周回を維持するか、再開までの秒数、必要な版） |
| `preset` の中 | このプリセットで何をどう稼ぐか（作る収集品、ジョブ、残す空き枠） |

**現状の戦闘 5 項目もクラフター 5 項目も、この規約に照らすとすでに正しい場所にある。**
だから移行が要らない。

## 契約

```
IEarner
  DisplayName        画面に出す名前
  IsAvailable        連携先が導入されているか
  IsRunning          いま稼いでいるか
  SuppliesCurrency   自力で通貨を増やせるか（歯止めの「終わりを決めずに回す」もこれで判断）
  MarkInterrupting() これから交換で中断する合図
  IsAtSafeBreak()    いま中断してよい切れ目か
  Suspend()          中断させる
  Resume()           自分が止めたぶんを戻す
  StopForEmergency() / ResumeAfterStop()
```

### 守る約束

1. **自分が止めたときだけ戻す。** 利用者が自分で止めていたものは戻さない
2. **中断に成功した稼ぎ手だけが復帰を受ける。** 登録簿が「止めた相手」を持ち、
   そこに入った相手だけへ復帰を配る。条件を書かなくても、止めていない相手は動かない
3. **稼ぎ手は自分の設定を自分で読む。** 共通側は稼ぎ手の設定を 1 つも読まない
4. **中断・復帰・稼働判定は、導入されている稼ぎ手すべてに対して行う。**
   誰が稼いでいようと、交換の前には全員に手を離させる
5. **旗を 2 本に割らない。** `SuppliesCurrency` 1 つで両方の用途を賄う

### 触ってはいけない場所

ここに手が伸びたら設計が破れた合図。

`ExchangeExecutor` / `ExchangeLimits` / `MonitorService` の判定式 /
納品一式（`CollectableCycleRunner` / `CollectableDeliveryRunner` / `CollectablesShopService`）/
`RetainerRestockRunner` / `SafetyGuard` / `NavigationService` / `ExchangeResolver` /
`Plugin.cs` の Tick 列と `EmergencyStop` の**順序**

とくに `EmergencyStop` の順序は載荷条件。
取り出し側の後始末が AutoRetainer の抑制を返す前に `Abort` を通すと空振りする。
登録簿化で 1 行になっても、**その 1 行の位置は変えない。**

## ギャザラーを足すとき

### いまどこまで来ているか（段 0-5 時点で実測）

**分かれているもの。**ギャザラーを足すとき、ここは書くだけで乗る。

| できること | 置き場所 |
|---|---|
| 誰が動いているか | `IEarner.IsRunning` / `DescribeRunning` |
| 止める・戻す | `TickSuspend` / `TickResume` |
| 緊急停止と解除 | `StopForEmergency` / `ResumeAfterStop` |
| 自力で稼げるか | `SuppliesCurrencyFor(preset)` |
| 画面に製作の操作を出すか | `CanEarn(通貨)` |

**まだ分かれていないもの。**

| 残っている場所 | 段 |
|---|---|
| 稼ぎの手順（製作・取り出し・納品）は `GoalRunner` が直接呼ぶ | 6 |
| 周回の維持は `AutoDutyKeeper` | 7 |
| 画面は 1 枚 | 8 |

**つまり、骨は通っているが「採集して納品する段取りを回す場所」がまだ無い。**
ギャザラーを動かすには段 6 が要る。

### そのまま使える既存部品

**納品の報酬側は出どころを問わない。**
`CollectableRewardService` は `CollectablesShopItem` → `CollectablesShopRewardScrip` から
索引を作るので（`CollectableRewardService.cs:88-91`）、
**ギャザラー収集品も同じ索引に入る。**納品して何がいくつもらえるかは、そのまま引ける。

リテイナーからの取り出しは `RestockRequest` が ItemId と個数しか知らないため、
呼び出し側を差し替えるだけで使える。

### そのままでは使えないもの

**`CraftPlanService` はクラフター専用。**
`Build()` は `Recipe` シートを回している（`CraftPlanService.cs:243`）ので、
**レシピを持たないギャザラー収集品は 1 件も入らない。**

したがって `GathererEarner.CanEarn` に `ListCraftable` は使えない。
採集側の索引（`GatheringItem` 起点）を別に作ることになる。

**これは欠陥ではなく、むしろ都合がよい。**
`CrafterEarner.CanEarn` がクラフターだけを答えるので、
ギャザラースクリップのプリセットに製作の操作が出ない。

### 足すもの

```
Earning/Gatherer/GathererEarner.cs      1 本
Game/GatherPlanService.cs               1 本（CraftPlanService の採集版）
Earning/Gatherer/GathererEarnerUi.cs    1 本（段 8 のあと）

```

## プリセットを種別で分ける件

### 通貨が種別を決めている（設定は要らない）

`Data/special_currency_map.json` を確認すると、スクリップは**種別ごとに別アイテム**。

```
アラガントームストーン:哲学 / 詩学 / 数理 / 記憶 / 天道   → 戦闘
クラフタースクリップ:紫貨 / 橙貨                          → クラフター
ギャザラースクリップ:紫貨 / 橙貨                          → ギャザラー
```

**通貨を選んだ時点で稼ぎ方は一意に決まる。**
利用者に「これは戦闘用です」と申告させる必要は無い。

申告させる案を採らない理由はもう 1 つある。
**申告と通貨が食い違う状態を作れてしまう。**
「戦闘用」と宣言したプリセットでクラフタースクリップを選べたら、どちらを信じるのか。
通貨だけを持てば、その矛盾は存在しない。

`EzConfig` はプロパティ名を変えると旧キーが読まれず既定値に戻るため、
**器を増やすほど事故の面が広がる**という事情もある。

### ただし「作るときに迷う」のは本当

通貨の一覧は長く、どれを選べば何ができるのかが分からない。
そこは**絞り込みで解く。**

```
新しいプリセット
  何で稼ぎますか？   [戦闘] [クラフター] [ギャザラー] [交換だけ]
        ↓
  通貨の一覧が、その稼ぎ方のものだけになる
        ↓
  保存されるのは通貨だけ
```

**選んだ種別は保存しない。**通貨を選ぶための絞り込みにしか使わない。
設定が増えないので移行も要らず、食い違いも起きない。

振り分けは稼ぎ手に聞く（`CanEarn(通貨)`）。
ギャザラーを足したら、その通貨が自動で「ギャザラー」の側に並ぶ。
**振り分け表をコードへ持たない。**

### 一覧にも稼ぎ方を出す

プリセットの一覧に、通貨から導いた稼ぎ方のしるしを添える。
これも保存しない。導出するだけ。

## 挙動が変わる予定のもの

段 7 で、周回の維持の条件が「有効なプリセットがあるか」から
「戦闘のプリセットがあるか」に変わる。
**製作だけの利用者は周回が維持されなくなる。** 意図した改善だが変化なので、
リリース時に告知する。

## 実装して分かったこと（段 1〜4）

### 契約は `Suspend()` ではなく `TickSuspend()` にした

中断も復帰も**1 フレームでは終わらない。**
AutoDuty の停止は要求を送ってから実際に止まるまで間があり、
1 秒ごとに送り直しながら待つ。復帰は 2 秒ごと。
最初の設計案の `Suspend()` / `Resume()` では表せなかった。

### 「終わった」と「止めた」を別の値にした

もともと動いていなかった稼ぎ手も「中断は終わった」を返す。
だが**止めてはいない。**止めていない相手を復帰させると、
利用者が自分で止めていたものを勝手に動かすことになる。

`EarnerStepResult.Acted` で区別し、
登録簿はこの値を見て復帰を配る相手を決める。
F-60 / F-61 / F-68 はいずれもこの区別が無いことから出ていた。

### まとめて中断する口は、まだ交換から呼んでいない

**止める順序が載荷条件だった。**

```
Artisan を止める → AutoRetainer を抑制する → AutoDuty を止める
```

真ん中の AutoRetainer は稼ぎ手ではない（協調的な抑制の相手）。
`TickSuspendAll` でまとめて中断すると AutoDuty が先に止まり、
抑制が立つ前にリテイナー処理が始まる隙間ができる。

いまは交換の側が稼ぎ手を 1 つずつ呼び、この順序を保っている。
**段 7 でここを畳むときは、AutoRetainer の抑制をどこへ置くかを先に決めること。**

### 緊急停止では Artisan を止めない（従来どおり）

登録簿の約束 4 は「導入されている稼ぎ手すべてに行う」だが、
緊急停止で Artisan を止めると**戻す道筋が無い。**

緊急停止は `ExchangeExecutor.Abort` → `Cleanup` の順に走り、
`Cleanup` が解除を通る。そのあとに停止を掛けると、
製作が止まったまま戻らない（F-60 と同じ形）。

緊急停止は「こちらの自動処理をやめる」ためのもので、
利用者が自分で回している製作まで止める話ではない。
交換の間だけ止めるぶんは `TickSuspend` が行い、必ず解除される。

### 挙動が変わったところ（段 4）

**復帰の段で、抑制の解除とウィンドウを閉じるのが最大 2 秒早くなった。**

以前は再開の間引き（2 秒）を通ってから後始末をしていた。
いまは段に入って 1 回だけ後始末をしてから、稼ぎ手へ復帰を頼む。
解除が早まる向きなので安全側だが、変化ではある。

## 段 6 以降を、まだ入れていない理由

**段 4 が実機で通るのを見てから入れる。**

段 3〜5 は、止める・戻すという**最も壊れやすい経路**を書き換えた。
ここはゲーム内でしか確かめられない。

段 6 は `GoalRunner`（1133 行）の状態機械から
製作・取り出し・納品の段取りを `CrafterEarner` へ移す。
**これも実機でしか確かめられない経路で、しかも直前に実機で直したばかりの場所。**

2 つを重ねて入れると、何かが動かなくなったときに
「止める側が壊れたのか、作る側が壊れたのか」を切り分けられない。
段は単独で入れられるように切ってあるのだから、単独で確かめる。

### 段 6 に入る前に決めること

段 7 で `AutoDutyKeeper` を畳むとき、
**AutoRetainer の抑制をどこへ置くかを先に決める。**

止める順序が載荷条件になっている。

```
Artisan を止める → AutoRetainer を抑制する → AutoDuty を止める
```

真ん中は稼ぎ手ではない。稼ぎ手だけを束ねても、この順序は表せない。

## プリセットを稼ぎ方で分ける

### 出ていた不具合

戦闘用（アラガントームストーン:数理）のプリセットに、
**「作る収集品が選ばれていません。下の「製作するジョブ」から選んでください」**
と出ていた。製作と何の関係も無い設定に、製作の指示が出ていた。

原因は、**通貨が製作で稼げるかどうかを見ていなかった**こと。
「足りない → 作って補う」という筋書きを、通貨の種類に関わらず当てていた。

```
スクリップ        収集品を納品すると増える   → 製作で稼げる
トームストーン    周回で増える               → 製作では 1 つも増えない
```

### 種別の設定は足さない

利用者に「このプリセットは戦闘／クラフター／ギャザラー」と選ばせる案もあるが、
**通貨を選んだ時点で決まっている**ので聞かない。

判定は `CrafterEarner.CanEarn(currencyItemId)`。

```
その通貨を報酬にする収集品が 1 つでもあるか
  → CraftPlanService.ListCraftable(currencyItemId).Count > 0
```

**ゲームデータで決まる。**通貨の名前も種別もコードへ埋め込まない。
新しい通貨が来ても、収集品が紐づいていれば自動で「製作で稼げる」側に入る。

設定を足さないので、**移行も要らない。**
（`EzConfig` はプロパティ名を変えると旧キーが読まれず既定値に戻る。
　器を増やすほど、その事故の面が広がる）

### どこが変わったか

| 場所 | 以前 | いま |
|---|---|---|
| プリセットの画面 | 「製作するジョブ」を常に出す | 製作で稼げる通貨のときだけ出す |
| 目標の内訳 | 常に「作る収集品を選んでください」 | 稼げないなら「周回で貯まるのを待ちます」 |
| `GoalRunner.BeginCraft` | 収集品が未選択なら失敗 | 稼げない通貨なら、その旨で止まる |
| `SuppliesCurrencyFor` | `preset.CraftToEarn` | `preset.CraftToEarn && CanEarn(通貨)` |

最後の 1 行が要点。**設定に印が入っているだけでは足りない。**
トームストーンのプリセットで「製作で稼ぐ」に印を入れても、
交換の歯止めを緩める根拠にはならない。

### ギャザラーを足すときもここは変わらない

ギャザラーの収集品もスクリップを生むので、`ListCraftable` と同じ形で
「採集で稼げるか」を判定できる。`GathererEarner.CanEarn` を足すだけで、
画面の出し分けは同じ仕組みに乗る。
