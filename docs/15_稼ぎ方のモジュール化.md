# 稼ぎ方のモジュール化

対象: `AutoCollector`
ブランチ: `feature/earner-modules`

## なぜ分けるのか

**分けるのは「稼ぎ方」だけ。交換は 1 本のまま。**

```
稼ぎ方（戦闘 / クラフター / 将来のギャザラー）  ← 分ける
        ↓ 通貨が貯まる
交換（窓口・区分・歯止め・検証）                ← 分けない
```

交換の歯止め（`ExchangeLimits`）は 2026-09-17 に 1 本化した。
窓口ごとに分かれていたことが、所持の上限を無視して買い続ける重大な不具合の原因だった。
**ここを再び分ける案は採らない。**

一方、「いま誰が動いているか」「止める・戻す」「自力で通貨を増やせるか」は
稼ぎ方ごとに違う。ここが共通側に散っているため、次の種類の不具合が繰り返し出ている。

| # | 内容 |
|---|---|
| F-60 | 止めるとき立てた旗を、戻す側が全部下ろしていない |
| F-61 | 周回を止める側が「まだ渡せていない交換」を知らない |
| F-68 | 止めたあと、製作だけが動いて納品が弾かれる（旗が 2 本あって片方しか見ていなかった） |

**この 3 件はいずれも「複数の実行体が互いの状態を覗き合う」構造から出ている。**
分けると構造で潰せる。

**効かない種類もある。** F-67（交換画面の区分）や F-69（選択の確認）は
ゲーム画面の読み方の問題で、モジュール化では防げない。過大評価しないこと。

## 採った方針

**既存の型を 1 つも移さない。** `IEarner` という差し替え口と `EarnerRegistry` を新設し、
戦闘（`AutoDutyIpc` / `AutoDutyKeeper` / `AutoDutySetup`）とクラフター
（`GoalRunner` / `ArtisanIpc`）へ委譲するアダプタを挟む。

### 設定は作り直さない

`Config` の器を `Config.Combat` / `preset.Crafter` へ移す案もあったが**採らない**。

`EzConfig` は Newtonsoft を使うため、**プロパティ名を変えると旧キーが読まれず既定値に戻る。**
`KeepAutoDutyLooping=false` や `CraftKeepFreeSlots=115` を入れている利用者の値が黙って消える。
しかも移行が終わった時点では稼ぎ方はまだ 1 つも分かれておらず、払うリスクに対して得るものが無い。

代わりに**置き場所の規約だけを決める**。

| 置き場所 | 何を置くか |
|---|---|
| `Config` 直下 | 稼ぎ手そのものの動かし方（周回を維持するか、再開までの秒数、必要な版） |
| `preset` の中 | このプリセットで何をどう稼ぐか（作る収集品、ジョブ、残す空き枠） |

**現状の戦闘 5 項目もクラフター 5 項目も、この規約に照らすとすでに正しい場所にある。**
だから移行が要らない。

## 契約

```
IEarner
  DisplayName        画面に出す名前
  IsAvailable        連携先が導入されているか
  IsRunning          いま稼いでいるか
  SuppliesCurrency   自力で通貨を増やせるか（歯止めの「終わりを決めずに回す」もこれで判断）
  MarkInterrupting() これから交換で中断する合図
  IsAtSafeBreak()    いま中断してよい切れ目か
  Suspend()          中断させる
  Resume()           自分が止めたぶんを戻す
  StopForEmergency() / ResumeAfterStop()
```

### 守る約束

1. **自分が止めたときだけ戻す。** 利用者が自分で止めていたものは戻さない
2. **中断に成功した稼ぎ手だけが復帰を受ける。** 登録簿が「止めた相手」を持ち、
   そこに入った相手だけへ復帰を配る。条件を書かなくても、止めていない相手は動かない
3. **稼ぎ手は自分の設定を自分で読む。** 共通側は稼ぎ手の設定を 1 つも読まない
4. **中断・復帰・稼働判定は、導入されている稼ぎ手すべてに対して行う。**
   誰が稼いでいようと、交換の前には全員に手を離させる
5. **旗を 2 本に割らない。** `SuppliesCurrency` 1 つで両方の用途を賄う

### 触ってはいけない場所

ここに手が伸びたら設計が破れた合図。

`ExchangeExecutor` / `ExchangeLimits` / `MonitorService` の判定式 /
納品一式（`CollectableCycleRunner` / `CollectableDeliveryRunner` / `CollectablesShopService`）/
`RetainerRestockRunner` / `SafetyGuard` / `NavigationService` / `ExchangeResolver` /
`Plugin.cs` の Tick 列と `EmergencyStop` の**順序**

とくに `EmergencyStop` の順序は載荷条件。
取り出し側の後始末が AutoRetainer の抑制を返す前に `Abort` を通すと空振りする。
登録簿化で 1 行になっても、**その 1 行の位置は変えない。**

## ギャザラーを足すとき

```
Earning/Gatherer/GathererEarner.cs     1 本
Earning/Gatherer/GathererEarnerUi.cs   1 本
Plugin.cs に登録 1 行
設定の器（要るなら。規約に従って置く）
この文書に 1 節
```

**そのまま使える既存部品**

- 収集品の納品は出どころを問わない（`CollectableRewardService` は `Item.IsCollectable`
  だけで索引を作るので、ギャザラー収集品も同じ索引に入る）
- リテイナーからの取り出しは `RestockRequest` が ItemId と個数しか知らないため、
  呼び出し側を差し替えるだけで使える

## 挙動が変わる予定のもの

段 7 で、周回の維持の条件が「有効なプリセットがあるか」から
「戦闘のプリセットがあるか」に変わる。
**製作だけの利用者は周回が維持されなくなる。** 意図した改善だが変化なので、
リリース時に告知する。

## 実装して分かったこと（段 1〜4）

### 契約は `Suspend()` ではなく `TickSuspend()` にした

中断も復帰も**1 フレームでは終わらない。**
AutoDuty の停止は要求を送ってから実際に止まるまで間があり、
1 秒ごとに送り直しながら待つ。復帰は 2 秒ごと。
最初の設計案の `Suspend()` / `Resume()` では表せなかった。

### 「終わった」と「止めた」を別の値にした

もともと動いていなかった稼ぎ手も「中断は終わった」を返す。
だが**止めてはいない。**止めていない相手を復帰させると、
利用者が自分で止めていたものを勝手に動かすことになる。

`EarnerStepResult.Acted` で区別し、
登録簿はこの値を見て復帰を配る相手を決める。
F-60 / F-61 / F-68 はいずれもこの区別が無いことから出ていた。

### まとめて中断する口は、まだ交換から呼んでいない

**止める順序が載荷条件だった。**

```
Artisan を止める → AutoRetainer を抑制する → AutoDuty を止める
```

真ん中の AutoRetainer は稼ぎ手ではない（協調的な抑制の相手）。
`TickSuspendAll` でまとめて中断すると AutoDuty が先に止まり、
抑制が立つ前にリテイナー処理が始まる隙間ができる。

いまは交換の側が稼ぎ手を 1 つずつ呼び、この順序を保っている。
**段 7 でここを畳むときは、AutoRetainer の抑制をどこへ置くかを先に決めること。**

### 緊急停止では Artisan を止めない（従来どおり）

登録簿の約束 4 は「導入されている稼ぎ手すべてに行う」だが、
緊急停止で Artisan を止めると**戻す道筋が無い。**

緊急停止は `ExchangeExecutor.Abort` → `Cleanup` の順に走り、
`Cleanup` が解除を通る。そのあとに停止を掛けると、
製作が止まったまま戻らない（F-60 と同じ形）。

緊急停止は「こちらの自動処理をやめる」ためのもので、
利用者が自分で回している製作まで止める話ではない。
交換の間だけ止めるぶんは `TickSuspend` が行い、必ず解除される。

### 挙動が変わったところ（段 4）

**復帰の段で、抑制の解除とウィンドウを閉じるのが最大 2 秒早くなった。**

以前は再開の間引き（2 秒）を通ってから後始末をしていた。
いまは段に入って 1 回だけ後始末をしてから、稼ぎ手へ復帰を頼む。
解除が早まる向きなので安全側だが、変化ではある。
