## 1. スクリップ交換: 特殊通貨インデックスの解決

### 1-1. 方針

`SpecialShop.ItemCosts[].CostType == 3` の `ItemCost.RowId` は**特殊通貨バケットのインデックス**であり、対応表はゲームの Excel シートに存在しない。一方 **クライアントの実行時には存在する**（`CurrencyManager.SpecialItemBucket`）。したがって:

> **解決の一次情報源は実行時の `CurrencyManager` とする。JSON は情報源にしない。**

### 1-2. `SpecialCurrencyResolver`（新規、`Game/SpecialCurrencyResolver.cs`）

```
BuildFromRuntime():
  1. CurrencyManager.Instance() が null → 表を空のままにして失敗を返す。
  2. SpecialItemBucket を GetEnumerator() で走査する。
     ★ インデクサ this[key] は絶対に使わない（StdMap.cs:36 は未登録キーでノードを挿入する）。
     各 pair について itemId = pair.Item1、specialId = pair.Item2.SpecialId。
     specialId == 0 は捨てる（0 は ItemBucket 用の値）。
  3. Item シートに実在し Name が空でない ItemId だけを採用する。
  4. 同一 index に異なる ItemId が 2 件以上入ったら、その index は「解決不能」として表から除く。
  5. 結果を IReadOnlyDictionary<int, uint> として公開する。
```

**補完（任意・失敗を許容）**

```
  6. typeof(CurrencyManager).Addresses.GetItemIdBySpecialId.Value != 0 を確認したときだけ、
     i = 1..8 について GetItemIdBySpecialId((byte)i) を呼び、
     手順 2 で埋まらなかった index を補完する。
     Value == 0 のときは呼ばない（未解決シグネチャの呼び出しはクラッシュしうる）。
     戻り値 0 は「不明」。決して ItemId として採用しない。
     手順 2 の結果と食い違ったら、その index を「解決不能」にする（自動補正しない）。
```

すべて `try/catch` で包み、例外は `AnomalyLog.Error("Currency", ...)` に落として**表を空のまま返す**。

### 1-3. 解決できない場合の挙動（fail-closed）

| 状況 | 挙動 |
|---|---|
| 表が 1 件も作れなかった | `ExchangeResolver.TryResolveCostCurrency` の `SpecialShopCostType.SpecialCurrencyBucket` は **`false` を返す**（＝ CostType==3 のエントリを候補一覧から完全に除外する）。JSON へのフォールバックは**行わない**。 |
| 対象 index が表に無い | その index を使うエントリを候補から除外。 |
| 対象 index が「解決不能」に落ちた | 同上。 |
| 表はあるが、発火直前の照合（§1-6）が通らない | `CurrencyMismatch` で停止。**自動補正しない。** |

候補が 0 件になれば交換は起きない。これが唯一の安全な失敗形である。UI には「特殊通貨バケットを解決できないため、スクリップ交換は無効です」と明示し、原因（`CurrencyManager.Instance()` が null / シグネチャ未解決 / index 重複）を併記する。

**ログイン前・キャラ未選択の間はバケットが空でありうる。** 表の構築はキャラクターログイン後に行い、空だった場合は「未構築」であって「解決不能」ではないものとして再試行する。ただし再試行中は §1-3 の除外を維持する。

### 1-4. `special_currency_map.json` の降格

`Game/SpecialCurrencyMap.cs` の役割を「解決表」から「**前回起動時のスナップショットと差分検出**」へ変える。

- `SpecialCurrencyResolver` の実行時表を**常に採用**する。
- 起動時に JSON と実行時表を比較し、差があれば `AnomalyLog.Warn("Currency", ...)` に「index N: JSON=X / 実行時=Y」を出す。
- **JSON を自動更新しない。** 診断タブのボタンでユーザーが承認したときだけ書き込む。
- `ExchangeResolver` のコンストラクタ引数 `SpecialCurrencyMap` は `SpecialCurrencyResolver` に差し替える。`ExchangeResolver` の `TryResolveCostCurrency` は実行時表だけを見る。
- 現在の JSON に入っている `{ "index": 1, "itemId": 28, ... }`（`Data/special_currency_map.json:14`）は**訂正も削除もしない**。差分ログの初期値としてそのまま残し、実行時表と食い違ったら警告を出すだけにする。現行データで CostType==3 に index 1 は出現しないため、実行時表を採用する限り実害は生じない。

### 1-5. 通貨の所持数と上限

`CurrencyService` に以下を追加する（既存 `TryGetCount`（`CurrencyService.cs:24`）のシグネチャは**変更しない**）。

```csharp
// CurrencyManager 由来の値。取得できなければ false。
public bool TryGetCurrencyManagerCount(uint itemId, out uint count);
public bool TryGetCurrencyManagerMaxCount(uint itemId, out uint maxCount);
```

## 2. スクリップ交換: ショップへの到達経路

### 2-1. 現状

`ExchangeResolver.InspectHandler` は既に `EventHandlerType.InclusionShop`（`EventHandlerType.cs:18` = `0x003A`）を処理している（未コミットの作業ツリー変更）。経路は

```
ENpcBase.ENpcData[32]  ─┬─ 0x3A InclusionShop（直参照）
                        └─ 0x36 PreHandler → Target が 0x3A
                                 ↓
                        InclusionShop.Category[30] → InclusionShopCategory
                                 ↓ InclusionShopSeries（サブロウ）
                                 ↓ 各サブロウの SpecialShop
                        shopEntries に載っていれば RecordNpc
```

`PreHandler` の `case` は `Target` を `InspectHandler` に再帰させているので、直参照と PreHandler 経由の**両方**が拾えている。`ENpcData` は 32 要素すべてを走査し 0 で `break` していない（`ScanNpcs`）。**この部分は正しく、変更しない。**

### 2-2. 追加する内容

#### (1) `InclusionPath` の拡張

```csharp
public sealed record InclusionPath(
    uint InclusionShopId,
    string? ShopName,          // InclusionShop.ShopName。空文字がありうる
    uint CategoryId,           // InclusionShopCategory.RowId
    string CategoryName,
    uint SeriesId,             // ★追加: InclusionShopCategory.InclusionShopSeries.RowId
    ushort SeriesSubrowIndex); // ★追加: そのシリーズ内の位置（＝サブカテゴリの位置）
```

`SeriesId` が必要な理由: 実行時に `AgentInclusionShop.AgentData._categories[]` を線形走査して目的カテゴリを特定するとき、Agent が持っているのは `Category.InclusionShopSeriesId` であって `InclusionShopCategory.RowId` ではない。`InclusionShop.Category[]` の**並び順に依存してはならない**（ClassJobCategory 制限つきカテゴリがジョブによって消える可能性があり、表示インデックスがずれうる）。

#### (2) `inclusionPaths` のキー変更（S7-0-2）

`Dictionary<uint, InclusionPath>`（`ExchangeResolver.cs:48`）を `Dictionary<(uint ShopId, uint NpcId), InclusionPath>` に変える。同一 SpecialShop は最大 6 通りの (InclusionShop, Category) に属するため、ShopId 単独キーでは後勝ちで壊れる。カテゴリ名が偶然同じでログ上は正常に見えるまま別カテゴリを選ぶ事故になる。

#### (3) `RecordNpc` との同伴（S7-0-3）

`NpcHandlerRecord` に `InclusionPath?` を持たせ、経路の優先度比較で record を差し替えるときに `InclusionPath` も同時に差し替える／捨てる。

#### (4) 会話メニュー候補の並び

`ExchangeDefinition.MenuHint` に `CategoryName` を入れる現行の扱いをやめる。候補は**空文字を積まずに**次の順で構築する。

```
1. definition.Inclusion?.ShopName   （InclusionShop.ShopName。空のことがある）
2. definition.ShopName              （SpecialShop.Name）
3. definition.Inclusion?.CategoryName
4. definition.MenuHint              （TopicSelect.Name / CustomTalk.MainOption 由来）
```

**メニューに実際どの文字列が出るかは未実測である。** 実測（§8-C）で確定するまで、候補が 1 つも一致しなければ `MenuResolutionFailed` で停止し、部分一致で 2 件以上に当たったら `MenuAmbiguous` で停止する。`InteractionService.cs:229-236` の部分一致フォールバックは、スクリップ／納品の経路では**完全一致のみ**に狭める（別の納品面を開く事故を避けるため。§6-A）。

#### (5) 到達不能ショップの扱い

NPC が付かない SpecialShop は `HasLocation == false` になり `LiveResults` から落ちる。この既存挙動を維持する。UI の `Results` を直接使う画面では `HandlerPath.InclusionShop` と所属カテゴリ名を明示表示し、ユーザーが到達できない候補を選ばないようにする。

#### (6) 「アドオン名はシート経路から決めない」

`ExchangeDefinition.UsesInclusionShop`（`ExchangeDefinition.cs:90`）は**シート上の到達経路**を表すだけで、「開くアドオンが InclusionShop である」ことを意味しない。実行時のアドオン名は必ず名前で確認する。

```
到達後の判定:
  "InclusionShop" が Ready かつ ownership 所有 → InclusionShop リーダーを使う
  "ShopExchangeCurrency" が Ready かつ ownership 所有 → 既存リーダーを使う
  どちらでもない → ShopNotOpen で停止
  両方開いている → ForeignShopAddonPresent で停止（撃たない）
```

### 2-3. カテゴリ／サブカテゴリの選択

**第 1 段階では選択を行わない。** 目的の SpecialShop が「すでに画面に出ている」ときだけ交換を許可する（`ShopService.IdentifyShop` が `definition.ShopId` と一致したときのみ）。サブカテゴリを 1 つ間違えると別の SpecialShop の商品を買うことになり、取り返しがつかない。同じカテゴリ内の隣接サブカテゴリは「Lv90～向け【ILv570】」「【ILv590】」のように商品構成が似ており、事後の所持数検証でも気づけない。

第 2 段階で選択を実装するときの手順:

1. `AgentInclusionShop` を `AgentModule.Instance()->GetAgentByInternalId(AgentId.InclusionShop)` で取得。`Data` が null なら停止。
2. `Data->IsShopReady` が false なら待つ。
3. `Data->_categories[0..CategoryCount)` を走査し、`Category.InclusionShopSeriesId == definition.Inclusion.SeriesId` の位置を探す。**ちょうど 1 件でなければ停止。**
4. カテゴリ選択は `AgentInclusionShop.SelectCategory(byte)`（ネイティブ）より `AgentData.SelectSubCategory(byte)`（範囲チェック付きのマネージドヘルパ）を優先する。ただし `SelectCategory` の引数が生インデックスか `_categoryIndexMap` 経由の表示インデックスかは**未確定**。実測で確定するまでカテゴリ選択は実装しない。
5. `VisibleSubCategoryCount` は `includes the default "-- select a subcategory --"` と明記されている。**オフバイワンの確定を実測で取るまでサブカテゴリ選択を実装しない。**
6. 選択後は必ず画面を読み直し、`IdentifyShop` が `definition.ShopId` と一致するまで**撃たない**。選択が効いたかどうかを推測で進めない。

### 2-4. `atkvalue_layout.json` の拡張

`Data/atkvalue_layout.json` に `"InclusionShop"` セクションを追加する。既定値は `AddonInclusionShop.cs:18-38` 由来。

### 2-5. 発火 index

`ECommons` は `Select()` でループ位置 `i` を渡す（`InclusionShop.cs` の `Callback.Fire(master.Base, true, 14, index, amount)`）。一方 `AddonInclusionShop` は各エントリに `Index`（`+17`）という AtkValue を別に持つ。`ShopExchangeCurrency` では **AtkValue 由来の Index を渡すのが正解**だった実績がある（`ExchangeExecutor.cs:196` 付近の設計）。

## 3. 収集品納品: 納品可能な収集品の判定

### 3-1. 索引の型

```csharp
public sealed record TurnInEntry(
    uint ShopHandlerId,      // CollectablesShop の RowId（= EventHandler ID）
    int  SlotIndex,          // CollectablesShop.ShopItems[] の位置（0..10）
    uint ItemId,
    string ItemName,
    ushort LowCollectability,
    ushort MidCollectability,
    ushort HighCollectability,
    ushort LowReward,
    ushort MidReward,
    ushort HighReward,
    uint CurrencyBucketIndex,  // CollectablesShopRewardScrip.Currency の生値
    uint CurrencyItemId);      // §1 の実行時表で解決した値。0 なら未解決
```

### 3-2. 索引の構築（起動時 1 回、オフライン、ゲームを変更しない）

```
1. 到達可能な CollectablesShop の RowId を集める（★ Name では選別しない）
   a. ENpcBase.ENpcData[32] を全走査（0 でも break しない）し、
      EventHandlerType.Of(h) == 0x3B のものを直接収集
   b. PreHandler.Target が 0x3B のものを収集し、その PreHandler を持つ NPC を収集
   c. CustomTalk.SpecialLinks の上位 16bit が 0x3B のものを収集し、
      その CustomTalk を ENpcData に持つ NPC を収集
      ★ 現行 ExchangeResolver は SpecialLinks を CustomTalkNestHandlers としてのみ
        解釈している。0x3B 分岐を追加する。
   d. どの経路でも NPC が 1 体も付かない CollectablesShop 行は索引に入れない。

2. 収集した行のうち RewardType == 1 のものだけを残す（スクリップ報酬）。
   RewardType == 2（素材交換）は明示的に除外する。

3. shop.ShopItems[i]（i = 0..10）の RowId != 0 について、
   GetSubrowExcelSheet<CollectablesShopItem>() の全 subrow を走査。

4. 各 subrow について:
   - Item.RowId <= 1000 は捨てる
   - CollectablesShopRefine 行を引き、Low/Mid/HighCollectability を取る
   - CollectablesShopRewardScrip 行を引き、Currency と Low/Mid/HighReward を取る
     ★ RewardType == 1 の行に限っているので、この列は
       CollectablesShopRewardScrip の行番号として読んでよい。
       （RewardType == 2 では CollectablesShopRewardItem の行番号になる。
         この多義性が実装の取り違えを生むため、RewardType による分岐を必ず入れる。）
   - Currency を §1 の実行時表で ItemId に解決する

5. ItemId をキーに Dictionary に登録する。
```

### 3-3. 索引の自己検証（カナリア）

構築時に次のいずれかが 1 件でも出たら、**索引全体を無効化し「納品しない」側へ倒す**。`SelfCheck` / `AnomalyLog` に載せる。

| # | 検査 |
|---|---|
| C-1 | `CollectablesShopRefine.RowId == 0` または `LowCollectability == 0` |
| C-2 | `CollectablesShopRewardScrip.RowId == 0` または `Currency == 0` |
| C-3 | `Currency` が §1 の実行時表で解決できない |
| C-4 | 同一 ItemId が同一ショップ内で 2 回以上出る |
| C-5 | `Item.IsCollectable` が false |
| C-6 | `LevelMin > LevelMax` |

パッチでデータ構造が変わったことを検出する強いカナリアになる。

### 3-4. 納品可否の判定手順（1 スタックごと）

```
前提: ユーザーが明示した「納品してよい ItemId」の許可リストが空でないこと。
      空なら納品ループ自体を開始しない（AllowListEmpty）。

1. 所持収集品の列挙
   InventoryManager.Instance()->GetInventoryContainer(InventoryType.Inventory1..4)
   の Items[0..Size) を走査し、
   (a) IsEmpty はスキップ
   (b) item->GetFlags().HasFlag(ItemFlags.Collectable) が false ならスキップ
   (c) baseId = item->GetBaseItemId()    ★ 生の ItemId は +500000 されうるため
       （GetItemId() を使う場合は ItemUtil.GetBaseId で 500000 を引く）
   (d) collectability = item->GetCollectability()
   armory / equipped は収集品が入らないので対象外。

2. baseId が許可リストに無ければ対象外。
3. baseId が索引に無ければ対象外（この窓口では納品できない）。
4. 段の決定（そのスタックについて）
   collectability >= HighCollectability かつ High > 0  → High 段
   collectability >= MidCollectability  かつ Mid  > 0  → Mid 段
   collectability >= LowCollectability                → Low 段
   それ未満                                            → 「納品不可」
   ★ 閾値 0 の段は「存在しない段」として飛ばす。
     納品ショップ内には 0 は無いが、Refine シート全体には high=0 の行が実在するため
     防御的に扱う。
5. 同一 ItemId で複数の収集度が混在する場合
   ★ どのスタックが渡されるかを我々は決められない。
   → 全スタックのうち最低の collectability が Low 未満なら、その ItemId は納品しない。
   → 期待報酬は「全スタック中の最低段の報酬量」を使う（保守的）。
   この扱いは設定 StrictCollectabilityGate（既定 ON）で制御する。OFF にできるが
   OFF は「低い段で納品される可能性を受け入れる」ことの明示的な同意とする。
6. 期待報酬 expected = 段に対応する (Low|Mid|High)Reward
   currencyItemId = 索引の CurrencyItemId
   currencyItemId == 0 → 対象外（RewardUnknown）
7. スクリップ上限
   §1-5 の手順で cap と now を取り、now + expected > cap なら納品しない。
   ★ 「上限に達したら止める」ではなく「達する前に交換へ切り替える」条件として使う。
8. ここまで全部通ったものだけが「納品可能」。
```

### 3-5. `CollectablesShopRewardScrip.Currency` の同一空間仮説を前提にしない

`Currency` の値域 {0,2,4,6,7} が CostType==3 の {2,4,6,7} と一致するのは**状況証拠にすぎない**。実装では:

- 索引構築時に `Currency` を §1 の表で解決するが、それは**候補の表示と上限判定の見積り**にしか使わない。
- **最初の納品 1 回**（§7 の S7-7）で、納品前後に **すべての既知スクリップ ItemId（表に載っている全 ItemId）の所持数を記録**し、実際に増えた ItemId が索引の `CurrencyItemId` と一致するかを検証する。
- 一致しなければ**即座にループを停止**し、索引を無効化する。自動補正はしない。
- 一致が確認できるまで、納品ループの「上限に近づいたら交換へ」の判定は `expected` を最大値（そのショップで得られうる最大の報酬）で見積もる保守側に倒す。

## 5. 納品 → 交換 → 納品 ループ

### 5-1. 構造

既存の `ExchangeExecutor` を**拡張しない**。3 層に分ける。

```
TurnInLoopController   … 脚の管理・外部制御の保持・停止の起点
  ├─ TurnInExecutor    … 納品脚（新規）
  └─ ExchangeExecutor  … 交換脚（既存にそのまま委譲。ExternalSessionOwner=true）
```

**分離する理由**: `ExchangeExecutor` の二重支払い防止は「`WaitOutcome` から `Armed` へ戻る辺が存在しない」という構造そのものに依存している。唯一の再入は結果確定後の `EvaluateOutcome` 内にしかない。ここにループ状態を足すと `Armed` への候補辺が増え、この不変条件をレビューで維持できなくなる。また `travelTarget`（`ExchangeExecutor.cs:232`）が唯一の目的地であり、全移動 Tick が冒頭で `if (target is null) { Step = Idle; return; }` を行うため、2 目的地を扱えない。

`Plugin.OnFrameworkUpdate`（`Plugin.cs:183-196`）の呼び出し順を固定する:

```
NpcLocationService.TickBuild
→ ExchangeResolver.TickBuild
→ TurnInResolver.TickBuild        （新規）
→ ExchangeExecutor.Tick
→ TurnInExecutor.Tick             （新規）
→ TurnInLoopController.Tick       （新規）
→ MonitorService.Tick
```

### 5-2. 状態遷移

```

 └─(UI からの開始要求)──> Preflight

Preflight ──(P-A〜P-J のいずれか不成立)──> Error   ※1 歩も動かない
 └─(全通過)──> AcquireControl

AcquireControl（SafetyGuard 待ち → AutoRetainer 抑制 → AutoDuty 停止 → ownership.IsClaiming=true）

TravelToTurnIn（Teleport / AethernetHop / Navigate / Interact / SelectMenu）
 └─("CollectablesShop" が Ready かつ ownership 所有)──> TurnInOpen

 ├─(所持 −1 かつ 期待通貨 +expected 以上)──> TurnInVerified ──> TurnInDecide

 ├─(まだ納品できる)──> TurnInScan

任意の状態 ──(/ac stop / Dispose / いずれかの Fail)──> [Cleanup] ──> Error
```

### 5-3. 崩してはならない不変条件

1. `TurnInWait` / `TurnInConfirm` から `TurnInArmed` へ戻る辺を**作らない**。
2. `TurnInArmed` は 1 フレームで決着する。持ち越さない。アドオンポインタは `TurnInArmed` の中で 1 回だけ取得し、読み取りと発火で同じものを使う。
3. `TurnInDecide` は `TurnInVerified` からしか到達できない。
4. 1 つのラッチにつき発火は 1 回だけ（`latch.Fired` で封鎖）。
5. `ExchangeLeg` の間、外側はゲームを一切触らない。

### 5-7. ループの終了条件（`TurnInDecide`）

| 終了理由 | 判定 | 扱い |
|---|---|---|
| 収集品が尽きた | `TurnInScan` で一致行が 0 件 | 正常終了。**判定は一覧の読み取り結果だけを根拠にする**。インベントリ側の推定で「まだあるはず」と続けない |
| スクリップが上限に近い | `now + 次の expected > cap` | `TravelToExchange` へ（達してからではなく、達する前に） |
| いずれかの脚のエラー | どちらかの実行器が `Error` | **再試行しない。**ループ全体を止める |
| ユーザー停止 | `/ac stop` → `Abort()` | 即座に封鎖 → `Cleanup` → `Error(Aborted)` |
| 回数上限 | 納品 500 回／往復 10 回／総経過 60 分 | 打ち切り。理由をログに残す |
| 判断材料が欠けた | 期待値不明・所持数が読めない・選択照合失敗 | 「実行しない」側に倒して停止 |

### 5-8. `TurnInAttempt`（二重納品の防止）

`PurchaseAttempt` とは**別レコード・別スロット**にする。納品はアイテム消費・報酬可変で、購入（通貨消費・報酬固定）とは形が違う。型で取り違えを防ぐ。

```csharp
public sealed class TurnInAttempt
{
    public uint ShopHandlerId { get; set; }
    public uint NpcDataId { get; set; }
    public uint ItemId { get; set; }
    public string ItemName { get; set; } = "";
    public ushort Collectability { get; set; }   // 押す直前に読んだ最低値
    public short TierMinCollectability { get; set; }
    public int  SelectedIndex { get; set; }
    public uint ScripItemId { get; set; }
    public int  ExpectedReward { get; set; }
    public int  ItemBefore { get; set; }         // minCollectability 付きで数えた値
    public int  ScripBefore { get; set; }
    public Dictionary<uint,int> AllScripBefore { get; set; } = [];  // §3-5 の検証用
    public bool Fired { get; set; }              // ★1 ラッチ 1 発火の封鎖
    public DateTime FiredAtUtc { get; set; }
    public bool Resolved { get; set; }
    public string Outcome { get; set; } = "";
}
```

- `Config.InFlightTurnIn` として永続化。代入直後に `EzConfig.Save()`。
- **両方のラッチが相互に相手を止める。** `InFlightTurnIn != null` の間は交換も開始しない（インベントリ状態が不明なままの購入判定は信用できない）。
- `Done` / `Error` のどちらでも自動クリアしない。`Plugin.Load()` で残っていたら赤字表示し、自動実行を開始しない。
- 成否判定は方向と下限で見る（等値にしない）。

### 5-9. 緊急停止・後始末

- `Plugin.EmergencyStop`: 「ループ封鎖 → 納品封鎖 → 交換封鎖 → Cleanup」の順。
- `Cleanup` の閉じる順序は「内側 → 外側」: `SelectYesno`（`Fire(addon, true, -1)` = Yes を押さない） → `CollectablesShop`（`Close(true)`） → `SelectString` / `SelectIconString`。`ShopExchangeCurrency` / `InclusionShop` は各実行器に任せる。
- **`Cleanup` は納品・引き渡し系のボタンを絶対に押さない。** 「見つかった名前のボタンを押す」実装にしない。
- `ownership.IsClaiming` はループ制御役が**ループ全体を通して**保持し、`Clear()` はループ終了時にだけ呼ぶ。
- エリア変更判定は `ExpectedTerritoryId` を根拠にする（`travelTarget` に依存しない）。

### 5-10. 交換脚と納品脚の位置関係

`Preflight` で 3 通りに分類し、以後は分岐しない。

| 分類 | 判定 | 移動 |
|---|---|---|
| 同一 NPC | `turnIn.NpcDataId == exchange.NpcDataId` | 移動しない。画面を閉じて会話メニューから選び直す |
| 同一エリア | `TerritoryId` が一致 | 徒歩のみ。エーテライト短縮は距離が縮むときだけ |
| 別エリア | 不一致 | 往復ともテレポート。**両方のアクセス済みを P-G で確認** |

戻り先は「出発地点」ではなく「納品 NPC の座標」を目的地にする。出発地点の記憶は使わない。

## 6. 危険な経路と防御

### 6-1. 別の納品相手に収集品を渡す

| 経路 | 防御 |
|---|---|
| 会話メニューの部分一致が別の選択肢に当たり、クエストの引き渡し／GC 納品／カスタムデリバリー画面が開く | **一次防御（構造的）**: 我々は `"CollectablesShop"` という名前でしかアドオンを取得せず、かつ `AddonOwnershipTracker.TryGetOwned` が真のものしか触らない（T-4）。他の納品面はそもそも操作対象にならない。<br>**二次防御**: T-5 の名前リスト。既定は `[Request, GrandCompanySupplyList, GrandCompanySupplyReward, SatisfactionSupply, ShopExchangeCurrency, InclusionShop]`（`[Addon("...")]` 属性で実在を確認済みの名前のみ）。`Data/blocking_addons.json` に外出しし、未確認の名前は空のまま置く。**実在を確認していない名前を既定リストに入れない**（名前が違えばチェックが無言で通り、防御が消える）。<br>**三次防御**: T-7（NPC の BaseId 一致）と T-8（TerritoryType 一致）。<br>**四次防御**: スクリップ／納品経路では `MenuService` の**部分一致フォールバックを禁止**し、完全一致のみにする。候補が 0 件なら `MenuResolutionFailed`、2 件以上なら `MenuAmbiguous` で停止。 |

### 6-2. 納品したくないアイテムを納品する

- **許可リスト方式のみ。** 「一覧の先頭を納品」「全部納品」「収集品なら何でも」は実装しない。
- `TurnInScan` の一致が 2 件以上なら `ItemAmbiguous` で停止。**この停止条件を後から緩めない。**

### 6-3. 選択と実行の間に一覧が入れ替わる

- `TurnInArmed` を 1 フレームで完結させ、その中で選択行の表示名（T-9）と行数（T-18）を**再取得して照合**する。
- 読み取りと発火で同じアドオンポインタを使う。

### 6-4. ジョブタブが目的と違う

- `TurnInOpen` で「押す」と「確認する」をフレームで分ける。確認できるまで `TurnInScan` へ進まない。
- タブ順と `ShopItems[i]` の対応が実測で確定するまで、**タブ切替そのものを実装しない**。

### 6-5. 収集度が段の下限未満のものを納品する

- T-11。段の下限未満なら納品しない。`GetCollectability()` が読めなければ納品しない。
- 同一 ItemId で収集度が混在する場合は最低値で判断する（§3-4 手順 5）。
- 「あと何ポイントで次の段に届くか」を UI に表示し、**High 未満の収集品を自動納品しない**オプションを既定 ON にする。

### 6-6. スクリップ上限を超えて納品する

- T-13。上限到達時のゲーム側の挙動（ボタン無効化／エラー／切り捨て）は**未確認**なので、「余裕が無い時点で交換脚へ切り替える」で近づけない。
- 上限は `CurrencyManager.GetItemMaxCount` を第一根拠にする（§1-5）。

### 6-7. 二度押し

- ラッチの `Fired` フラグで封鎖。`TurnInWait` → `TurnInArmed` の辺を作らない。
- ボタンはサーバ応答前も `IsEnabled` のままでありうるので、`IsEnabled` を「押してよい」の根拠にしない。

### 6-8. 確認ダイアログの取り違え

- `TryGetAddonMaster<SelectYesno>` はインデックス 1 しか見ない。**インデックスを走査して全ての `SelectYesno` を候補にする。**
- **本文の照合条件は実測で決める。** 交換では「本文に報酬アイテム名が含まれる」を必須にして、実際には含まれず自分のダイアログを認識できなかった前例がある（docs/03 F-11）。納品でも本文の実物を採取するまで照合条件を確定させない。
- 照合できないダイアログは**押さない**。`ConfirmDialogNotConfirmable` で停止する（安全側）。
- `RespectDisabledButtons = true` を設定し、`YesButton` の null / `IsEnabled` / `IsVisible` を自分で確認する。

### 6-9. 誤った通貨で交換する

- §1-6 の P-S1〜P-S4。
- 表がずれていても、P-S2（InventoryManager と CurrencyManager の所持数一致）と P-S4（画面の値との照合）の両方を通らなければ撃たない。
- **ショップ名・カテゴリ名から通貨を推測しない。** 名前が「白貨の取引」なのに実コストが紫貨のショップが実在する。名前はメニュー照合にのみ使う。

### 6-10. 自分が開いていない画面を操作する

- `AddonOwnershipTracker.Tracked` に `CollectablesShop` / `InclusionShop` を追加（S7-0-4）。
- 60 秒失効を「`IsClaiming` の間は再スタンプ」に変える。1 か所で 60 秒以上納品を続けると所有権を失い、緊急停止時に自分の画面を閉じられなくなる。

### 6-11. 監視がループの途中で別の交換を開始する

- `MonitorService.Tick` の先頭に「ループ制御役が稼働中なら return」を追加（S7-0-6）。納品脚の間 `ExchangeExecutor` は `Idle` のままなので、現在のゲートを素通りする。

### 6-12. AutoDuty がループの途中で再開される

- `ExternalSessionOwner = true` の間、`ExchangeExecutor` は `ResumeAutoDuty` を実行しない（S7-0-5）。AutoDuty の停止／再開はループ制御役が**ループ全体で 1 回ずつ**だけ行う。

### 6-13. 他プラグインとの干渉

- ノード 51 が `IsVisible() == false` のときは押さず `TradeButtonHidden` で停止する。DailyRoutines の `AutoCollectableExchange` オーバーレイが表示中はノード 51 を毎フレーム非表示化するため、この状態は「他プラグインが同じ画面を操作している」ことのサインとして扱う。

## 8. 実機で確認すべきこと（ユーザーへの依頼手順）

> すべて S7-5 の段階で行う。**A〜F は 1 つも通貨・収集品を消費しない。**

### A. 特殊通貨バケットの実行時内容（S7-1 完了後・最優先）

1. スクリップを持っているキャラクターでログインする。
2. `/ac` → 診断タブ → 「実行時バケット表」を開く。
3. 次をそのまま貼り付けて報告してほしい。
   - 表に載っている index / ItemId / アイテム名 / MaxCount / Count の全行
   - JSON との差分警告があればその全文
   - `GetItemIdBySpecialId` のシグネチャが解決できたかどうか（表示欄あり）
4. **可能なら**、橙貨を 1 つも持っていないキャラクターと、白貨を持っていないキャラクターでも同じ表を取る。
   - 確認したいこと: **未所持の通貨がバケットに載るかどうか**。載らない場合、そのキャラでは index 6/7 が解決できず候補が空になる（安全側だが機能が使えない）。

### B. スクリップ交換所で開くアドオン名（S7-2 完了後）

   - 確認したいこと: スクリップ交換が `InclusionShop` と `ShopExchangeCurrency` の**両方**で開きうるという想定が正しいか。

### C. 会話メニューの選択肢文字列（S7-2 完了後）

2. 特に、スクリップ取引窓口で「スクリップの取引」という選択肢が出るか、それとも別の文言かを確認する。

### D. InclusionShop の実測（S7-4 完了後）

1. 診断タブ → 「callback 記録」→ **フィルタ欄を空にする**（`AddonFilter = ""`）→ 記録開始。
2. スクリップ取引窓口に話しかけ、**カテゴリとサブカテゴリを手で選び**、任意の 1 品を **1 個だけ手で交換する**。
3. 記録停止 → 記録された全 callback を（アドオン名・updateState・値の型と値をすべて）報告する。
4. 交換の直前に、診断タブの「InclusionShop レイアウト診断」のスクリーンショットを撮る。表示されるのは:
   - `AtkValues[296] / [297] / [298]`
   - 先頭 5 エントリの `ItemId` / `AmountOwned` / `GiveCount` / `_giveItemId[0..2]` / `_giveAmount[0..2]` / `MaxAmount` / `Flags` / `Index`
   - `AgentInclusionShop`: `InclusionShopId` / `CategoryCount` / `SelectedCategoryIndex` / `SelectedSubCategoryIndex` / `SelectedSubCategoryTab` / `VisibleSubCategoryCount` / `SelectedItemIndex` / `IsShopReady`
   - 各 `Category` の `InclusionShopSeriesId` と `Name`
5. 交換後に `SelectYesno` が出たかどうか、出たなら**本文をそのまま**書き写す。

**この 1 回で確定させたいこと**
- `_giveItemId[0]`（`AtkValues[299+18i+6]`）が **実 ItemId** か **バケット index** か（§1-6 の P-S4 の (a)/(b)）
- 交換 callback の第 1 引数（`14` か否か）、値の個数、`index` が**ループ位置**か `AtkValues[+17]` の `Index` 値か
- `AtkValues[297]`（ピン留め通貨）が対象スクリップの所持数と一致するか
- サブカテゴリの `tabIndex` がプレースホルダを含む番号か（`VisibleSubCategoryCount` と実カテゴリ数の差）
- 確認ダイアログの有無と本文の形式

### E. CollectablesShop の実測（S7-4 完了後）

1. 収集品を**最低 2 個**持った状態で「収集品納品窓口」に**手動で**話しかける。
2. 何も押さずに、診断タブの「CollectablesShop ダンプ」のスクリーンショットを撮る。表示されるのは:
   - `AtkValuesCount` と `AtkValues[0..64]` の型と値
   - `GetNodeById(28)` / `(31)` / `(51)` の有無・ノード型・`NodeFlags`・`IsVisible`
   - 28 / 31 を `AtkComponentList` / `AtkComponentTreeList` として読めたかと、`ListLength` / `SelectedItemIndex`
   - 各行のテキストノード（候補 4）から取れた文字列
3. **ジョブタブを 1 つ隣に切り替える。** 切替後に同じダンプをもう 1 枚撮る。
4. 一覧の**行を 1 つ選択する**（納品はしない）。選択後にもう 1 枚撮る。
5. **フィルタを空にした callback 記録を開始**し、手で 1 個だけ納品する。記録された全 callback を報告する。
6. 納品後に `SelectYesno` が出たかどうか、出たなら**本文をそのまま**書き写す。
7. 納品直後の `CollectablesShop` が開いたままか閉じたかを報告する。
8. 納品前後で、**どのスクリップが何ポイント増えたか**を報告する（通貨タブの数値）。

**この 1 回で確定させたいこと**
- U-1（一覧のノード ID とコンポーネント型）、U-2（AtkValue 配置と有効タイミング）、U-3（発火手段）、U-4（`12` の意味）、U-5（`SelectYesno` の有無と本文）、U-6（選択行の読み方）、U-7（タブ切替後の再構築）
- **`CollectablesShopRewardScrip.Currency` → ItemId の対応が正しいか**（§3-5 の裏取り）

### F. 事前条件が正しく撃たせないことの確認（S7-6 の直前・消費なし）

1. 許可リストを**空**にした状態でループを開始し、`AllowListEmpty` で 1 歩も動かないことを確認する。
2. スクリップが上限（4000）に近い状態を作り、`ScripCapWouldOverflow` で納品しないことを確認する。
3. 収集品を持たない状態で納品窓口に立ち、`ItemNotInList` で停止することを確認する。
4. 別の窓口（GC 納品や親方など）に立ってループを開始し、`WrongNpc` で停止することを確認する。
5. **一度も「取引」ボタンが押されていないこと**をログで確認する。

### G. 最初の 1 回（S7-6 / S7-7・消費する）

- **S7-6**: スクリップ交換を 1 個だけ。事前に対象スクリップの所持数と、買うアイテムの所持数をメモしておく。実行後に両方の増減が意図どおりかを確認する。
- **S7-7**: 収集品納品を 1 個だけ。事前に **全種類のスクリップ所持数**と対象収集品の個数・収集度をメモしておく。実行後に「対象収集品がちょうど 1 個減った」「意図した種類のスクリップだけが期待量増えた」を確認する。
- どちらも失敗した場合、**ラッチ（`InFlight` / `InFlightTurnIn`）をクリアする前に**、ゲーム内の実際の所持数を報告する。

### H. 異常系（G が完全に成功した後だけ）

1. 納品の途中で `/ac stop` を撃ち、ボタンが押されずに停止し、自分が開いた画面だけが閉じることを確認する。
2. 交換脚の途中でエリア移動し、ループが `Error` で止まりウィンドウに触らないことを確認する。
3. 手動で `CollectablesShop` を開いた状態で監視を有効にし、**自分が開いていない画面には一切触らない**ことを確認する。
