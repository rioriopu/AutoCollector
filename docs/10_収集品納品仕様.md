## 4. 判定式

### 4-1. 納品可否（1 ItemId ごと。ゲームを変更しない純関数として実装する）

```
入力: TurnInDefinition d, 許可リスト allow, 設定 StrictCollectabilityGate

1. d.ItemId ∈ allow でなければ 不可（ItemNotInAllowList）
2. 所持スタックの列挙（Inventory1..4 のみ。収集品は装備・アーマリーに入らない）
     container = InventoryManager.GetInventoryContainer(t)  (t = Inventory1..4)
     slot      = container->GetInventorySlot(i)
     採用条件: slot->ItemId != 0
             かつ (slot->Flags & ItemFlags.Collectable) != 0        ← 素のフィールド（0x1C）を一次情報にする
             かつ slot->GetBaseItemId() == d.ItemId
     collectability = slot->SpiritbondOrCollectability               ← 素のフィールド（0x18）
     ★ 併せて slot->IsCollectable() / GetCollectability() も呼び、食い違ったら
       その ItemId は納品対象から外す（CollectabilityUnknown）。仮想関数の解決失敗を検出するため。
3. 該当スタックが 0 件 → 不可（NoStack）
4. tier(c) = c >= High && High > 0 ? High段
           : c >= Mid  && Mid  > 0 ? Mid段
           : c >= Low  && Low  > 0 ? Low段
           : なし
   ★ 閾値 0 の段は「存在しない段」として飛ばす（Refine の 0 行目対策）
5. minC = min(全スタックの collectability), maxC = max(...)
   StrictCollectabilityGate（既定 ON）:
     tier(minC) が「なし」なら その ItemId は納品しない（CollectabilityBelowTier）
   OFF にできるが、OFF は「低い段で納品されうることへの明示的な同意」とする
6. tierMin      = tier(minC) の下限しきい値（Low/Mid/High のいずれか）
   rewardOfMin  = tier(minC) に対応する (Low|Mid|High)Reward
   rewardOfMax  = tier(maxC) に対応する (Low|Mid|High)Reward
   expectedMin  = min(rewardOfMin, rewardOfMax)      ← 単調性を仮定しない
   expectedMax  = max(rewardOfMin, rewardOfMax)
   expectedMin == 0 → 不可（RewardUnknown）
7. tierMin > short.MaxValue → 不可（TierOutOfRange。GetInventoryItemCount の引数は short）
8. d.CurrencyItemId == 0 → 不可（RewardUnknown）
9. 上限ゲート
     cap = CurrencyService.GetEffectiveCap(d.CurrencyItemId)   ← CurrencyManager 優先（CurrencyService.cs:73）
     cap が取れない → 不可（ScripCapUnknown）
     scripNow + expectedMax > cap → 不可（ScripCapWouldOverflow）※ 保守側に expectedMax を使う
10. ここまで通ったものだけが「納品可能」
```

### 4-3. 成功判定式

発火前に記録する値（`TurnInAttempt`）:

```
itemBeforeTotal = TryGetCollectableCount(itemId, minCollectability: 0)        // NQ+HQ, Inventory1..4 のみ
itemBeforeTier  = TryGetCollectableCount(itemId, minCollectability: tierMin)
scripBefore     = TryGetCount(scripItemId)                                    // == CurrencyManager 値（TI-13）
allScripBefore  = { id → TryGetCount(id) | id ∈ 既知スクリップ ItemId 全部 }
```

発火後、毎 Tick で:

```
itemTotalDelta = itemBeforeTotal - itemAfterTotal
itemTierDelta  = itemBeforeTier  - itemAfterTier
scripDelta     = scripAfter      - scripBefore
otherScripMoved = ∃ id ≠ scripItemId : allScripBefore[id] != TryGetCount(id)

成功 ⇔ itemTotalDelta == 1
     ∧ itemTierDelta  == 1
     ∧ expectedMin <= scripDelta <= expectedMax
     ∧ ¬otherScripMoved
```

既存の交換（`ExchangeExecutor.cs:2226-2227`）は「方向と下限」だけを見るが、納品は段によって報酬が変わるため**上限側も要る**。上限を外すと「Low 段で納品されたのに High 段のつもり」を検出できない。

判定の分岐:

| 観測 | 扱い | ラッチ |
|---|---|---|
| 全部 0（何も動いていない） | デッドライン（15 秒）まで待つ。時間切れで `TurnInNotApplied` | **未解決のまま残す**（実際に納品されたか不明） |
| `itemTotalDelta == 1` だが `scripDelta` がまだ 0 | 反映順序の差。デッドラインまで待つ | – |
| 成功条件が全部成立 | 成功。ラッチ解決 → `EzConfig.Save()` → 継続判定（§6-4） | 解決 |
| `itemTotalDelta >= 2` | **タイムアウトを待たず即停止**（`TurnInBatchHandover`）。反映順序では説明できず、複数納品の確定証拠 | 解決（何が起きたかは判明している）＋セッション停止＋許可リストを無効化して再開を要求 |
| `itemTotalDelta == 1` かつ `itemTierDelta == 0` | 段の勘定が誤り（`TurnInTierMismatch`）。即停止 | 解決＋停止 |
| `otherScripMoved` | `CurrencyIndex → ItemId` の索引が誤り（`ScripMappingWrong`）。即停止し、`TurnInResolver` の該当索引を無効化 | 解決＋停止。**自動補正しない** |
| デッドライン時点で `scripDelta > expectedMax` | 報酬表が誤り（`RewardAboveExpected`）。停止 | 解決＋停止 |
| デッドライン時点で `0 < scripDelta < expectedMin` | 上限で切られた可能性（`RewardBelowExpected`）。停止 | 解決＋停止 |
| その他の想定外 | `TurnInUnexpectedDelta` | **未解決** |

「ラッチを未解決で残すのは、実際に納品されたかどうかが不明なときだけ」を守る（既存の `Fail`（`:2609`）/ `FailUnresolved`（`:2623`）の使い分けと同じ）。

**通貨対応の検証**: 成功時、`scripItemId` の増加が観測できた時点で `Config.TurnIn.VerifiedCurrencyIndexToItemId[CurrencyIndex] = scripItemId` を書く。**一致したときだけ書く**（仮説の追認であり、上書き補正ではない）。不一致は上表のとおり停止。

# レビューで見つけた誤りと対処（2026-09-12）

実装後のレビューで 3 件の実害を確認し、いずれも修正した。

## 1. 発火に渡す番号の意味が確定していない（重大）

実測の並びには、番号だけがあって品目が空の位置がある。

```
[88]=5  [89]=544227   位置 5 / 番号 5
[99]=6  [100]=空      位置 6 / 番号 6・品目なし
[110]=6 [111]=536626  位置 7 / 番号 6
```

位置 7 で「並びの位置」と「書かれている番号」が初めて割れる。
実測できた発火は行 0 と行 1 の 2 件だけで、そこは両者が一致するため
**どちらを渡すべきかを区別する観測が存在しない。**

対処: 位置と番号が一致している範囲だけを発火可とし、割れた先は発火させない。
`CollectableOffer.Verified` で区別し、UI でもボタンを出さない。

確定させるには、割れた先にある品を手動で 1 個納品して記録すればよい。

## 2. 発火の型が実測と違う（重大）

実測は `Fire(12, 0u)`。`CallbackRecorder.Describe` は UInt にだけ `u` を付けるため、
**第 2 引数は UInt** で確定している。

一方コードは `int` を渡しており、ECommons の `Callback.Fire` は
`int` を `AtkValueType.Int` にする（`Callback.cs:90-93` で確認）。
実測と型が食い違っていた。

既存の交換側には「実測どおり…すべて Int」「uint のまま渡すと UInt 型になり
実測と食い違う」と自分で書いてあり、その規律が納品側だけ抜けていた。

対処: `(uint)current.RowIndex` を渡す。

## 3. 走査に実体の末尾がない（重大）

申告 33 件に対し倍の 66 位置まで走査するが、実体配列の末尾に対する上限が無い。
66 位置目は AtkValue の 748 番目で、総数 5146 の範囲内のため止まらない。

画面には `4150289` のような 500000 超の値が別の意味で入っており、
実体を越えた先でそれらを収集品として拾う余地があった。

対処: 読み終えたあと、番号が 0 から連番で並んでいることを確かめる。
崩れていれば読み取りごと失敗にする。

## 机上検証

実測の値を再現して修正後の読み取りを流した結果:

```
行  0  ItemId 44232  発火可=True
行  1  ItemId 44231  発火可=True
...
行  6  ItemId 36626  発火可=False   ← 割れた先。正しく発火不可になる
```

部分的なダンプでは 7 件しか読めず、申告 33 件と合わないため
読み取り全体が失敗する（＝撃たない）。安全側に倒れることを確認した。

全 33 件を読めるかは、より広い範囲のダンプが要る。

## 記録を読み直すと辻褄が合う

```
2 回目: 21:49:40 Fire(12, 1u)  →  21:49:43 Fire(15, 0u)   納品成立
3 回目: 23:51:55 Fire(12, 7u)  →  23:52:00 Fire(15, 0u)   納品成立
```

`Fire(12, N)` のあとに別の操作があり、そこで納品が成立していた。

ダンプの node 51（納品ボタン）も裏づけになっていた。

```
選択前のダンプ: node 51: Button visible=False
選択後のダンプ: node 51: Button visible=True
```

**選ぶまで納品ボタンは現れない。**

## 記録の取りこぼし

`CallbackRecorder` は `AtkUnitBase.FireCallback` だけをフックしていた。
ボタンの押下は `FireCallbackWithResult` を通ることがあり、そちらは記録されない。
「記録に出ないのに画面が動く」という取りこぼしになっていた。

両方をフックするようにした。戻り値つきの経路は名前の末尾に印を付けて区別する。

## 直した手順

```
1. Fire(12, (uint)行番号)         一覧から選ぶ
2. 納品ボタン（node 51）が押せるようになるまで待つ
3. ボタンを押す
4. 収集品が減った かつ スクリップが増えた で検証
```

待ち時間は固定にせず、ボタンが押せる状態になったことで判断する。
何回目の確認で押せたかをログへ残し、待ち方が足りているかを後から判断できるようにした。
