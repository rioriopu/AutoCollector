# 他プラグインの設定を変更する — AutoDuty 連携の仕組み

Auto Collector の画面にある「AutoDuty の設定を直す」ボタンが、どうやって他プラグインの
設定を書き換えているかをまとめる。**別プラグインの開発へ転用することを前提**に、
Auto Collector 固有の事情は最小限にして、仕組みと落とし穴を中心に書く。

---

## 0. 結論

**Auto Collector は特別なことをしていない。AutoDuty が自分で扉を開けている。**

AutoDuty は `AutoDuty/IPC/IPCProvider.cs` で、自分の設定の読み書きを意図的に公開している。

```csharp
[EzIPC] public string GetConfig(string config) => ConfigHelper.GetConfig(config);

[EzIPC]
public void SetConfig(string config, object setting)
{
    switch (setting)
    {
        case string s:    ConfigHelper.ModifyConfig(config, s); break;
        case JArray js:   ConfigHelper.ModifyConfig(config, js.ToObject<string[]>() ?? []); break;
        case string[] ss: ConfigHelper.ModifyConfig(config, ss); break;
        default:          Svc.Log.Warning("setting has to be string or string[]"); break;
    }
}
```

こちらはその窓口を叩いているだけ。**他プラグインの設定を勝手にこじ開ける汎用の方法は無い。**
相手が公開しているかどうかが最初の分かれ目になる。

```
Auto Collector                          AutoDuty
─────────────────────                   ─────────────────────
GetIpcSubscriber<string,string>   ───→  [EzIPC] GetConfig(string)
  ("AutoDuty.GetConfig")                    ↓
                                        ConfigHelper.FindConfig(名前)
                                          → Configuration の FieldInfo を
                                            リフレクションで探す
                                          → field.GetValue().ToString()
                                        （見つからなければ string.Empty）
```

## 1. 呼ぶ側の実装

実体は `AutoCollector/Ipc/AutoDutyIpc.cs` の 2 メソッドだけ。

```csharp
/// <summary>AutoDuty の設定値を読む。フィールド名をそのまま渡す。</summary>
public bool TryGetConfig(string key, out string value)
    => this.TryInvoke("GetConfig",
        () => this.Func<string, string>("AutoDuty.GetConfig").InvokeFunc(key), out value);

/// <summary>設定を書き換える。AutoDuty 側は型変換と保存まで行う。</summary>
public bool TrySetConfig(string key, string value)
    => this.TryAction("SetConfig",
        () => this.Func<string, object, object>("AutoDuty.SetConfig").InvokeAction(key, value));
```

`Func<...>` は `AutoCollector/Ipc/IpcGate.cs` の薄いラッパーで、中身は素の Dalamud API。

```csharp
protected ICallGateSubscriber<T1, TRet> Func<T1, TRet>(string name)
    => Svc.PluginInterface.GetIpcSubscriber<T1, TRet>(name);
```

### ECommons の EzIPC を購読側では使わない

呼ぶだけなら素の `GetIpcSubscriber` で足りる。
そのうえ例外の種類を自分で捌けるので、**相手の仕様変更に気づける**。

| 例外 | 意味 |
|---|---|
| `IpcNotReadyError` | まだ登録されていない（相手の起動順が後） |
| `IpcTypeMismatchError` | 型が変わった |
| `IpcLengthMismatchError` | 引数の数が変わった |
| `IpcValueNullError` | null が返った |

`IpcGate.cs` の `TryInvoke` はこれらを個別に捕まえ、**それぞれ違う文言でログに残す**。
まとめて `catch (Exception)` にすると、相手がバージョンアップで壊れたのか
こちらの呼び方が悪いのかが分からなくなる。

## 2. 受ける側で起きていること

`AutoDuty/Helpers/ConfigHelper.cs`。

```csharp
private const BindingFlags All =
    BindingFlags.Public | BindingFlags.NonPublic | BindingFlags.Instance | BindingFlags.Static;

internal static FieldInfo? FindConfig(string configName)
{
    var i = Assembly.GetExecutingAssembly()
        .GetType("AutoDuty.Windows.Configuration")?.GetFields(All);

    foreach (var field in i!)
    {
        if (field.Name.Replace(">k__BackingField", "").Replace("<", "")
            .Equals(configName, StringComparison.InvariantCultureIgnoreCase))
            return field;
    }
    return null;
}
```

書き込み側は型に合わせて変換してから代入し、**最後に保存まで行う**。

```csharp
object? newValue = ModifyConfig(configType, configValues[0], out string failReason);
if (newValue != null) field.SetValue(Plugin.Configuration, newValue);
else PrintError(failReason);

Plugin.Configuration.Save();   // ← ユーザーの設定ファイルが即座に書き換わる
```

変換は `string` → そのまま / `enum` → `Enum.TryParse` / `Nullable<>` → 中身へ再帰 /
`IConvertible` → `Convert.ChangeType(..., CultureInfo.InvariantCulture)` の順。
**文字列を渡せば相手が型に合わせてくれる**ので、こちらは常に文字列で渡してよい。

## 3. 落とし穴

### ① void メソッドは型引数の末尾に `object` を足す

`SetConfig` は `void` を返すのに、購読側は `Func<string, object, object>` と **3 つ**宣言する。
これは ECommons の仕様。

```csharp
// ECommons/EzIpcManager/EzIPC.cs
var isAction = method.ReturnType == typeof(void);
var genericArray = (Type[])[
    .. method.GetParameters().Select(x => x.ParameterType),
    isAction ? attr.ActionLastGenericType : method.ReturnType];
```

`ActionLastGenericType` の既定は `typeof(object)`（`EzIPCAttribute.cs`）。

> **EzIPC で公開された void メソッドは `<引数..., object>` で購読し、`InvokeAction` で呼ぶ。**

ここを `Func<string, object>` にすると `IpcLengthMismatchError` で落ちる。
相手が EzIPC を使っているかどうかで購読の形が変わるため、**必ず相手のソースを見る**。

### ② IPC 名の前置詞は相手の InternalName

```csharp
// EzIPC.Init(this) を引数なしで呼んだ場合
prefix ??= Svc.PluginInterface.InternalName;
var name = attr.ApplyPrefix ? $"{prefix}.{ipcName}" : ipcName;
```

AutoDuty の `IPCProvider` は `EzIPC.Init(this)` を引数なしで呼んでいるので、
前置詞は `AutoDuty`、後半はメソッド名そのまま。よって `AutoDuty.GetConfig`。

### ③ 失敗しても例外が飛ばない

`GetConfig` は見つからないと **`string.Empty` を返して終わり**
（エラーは AutoDuty 自身のログに出るだけ）。
`ModifyConfig` に至っては成功しても `return false` という書き方で、
しかも IPC 側が `void` なので呼び出し元には何も返らない。

> **書いたら読み直して確かめるしかない。**

Auto Collector は `AutoDutySetup.Apply` で書き込み後に `Invalidate()` を呼んでキャッシュを捨て、
2 秒以内に読み直した値で画面の「直っているか」を判定している。

```csharp
if (!this.autoDuty.TrySetConfig(item.Key, item.ApplyValue))
{
    this.anomalyLog.Warn("Setup", $"{item.Title}: AutoDuty へ設定を渡せませんでした");
    return;
}

this.anomalyLog.Info("Setup", $"AutoDuty の設定を変更しました: {item.Key} = {item.ApplyValue}");
this.Invalidate();   // 次の読み取りで実際の値を確かめる
```

`TrySetConfig` が `true` を返すのは「IPC 呼び出しが例外を投げなかった」ことだけを意味し、
**設定が変わったことは意味しない。**

### ④ キー名は Configuration の「フィールド名」

UI のラベルではない。大文字小文字は無視される。
一覧は `/ad cfg list` で Dalamud のログに吐かせるのが確実
（`AutoDuty.cs` のコマンド登録 → `ConfigHelper.ListConfig()`）。

Auto Collector が使っているキーは `AutoCollector/Automation/AutoDutySetup.cs` にまとめてある。

| キー | 期待値 | 用途 |
|---|---|---|
| `LoopTimes` | `1` | 1 周ごとに交換の機会を作る |
| `EnableBetweenLoopActions` | `true` | ループ間処理の枠そのもの |
| `ExecuteBetweenLoopActionLastLoop` | `true` | **要**。最終周のあとも実行する |
| `EnableAutoRetainer` | `true` | ダンジョン後のリテイナー |
| `AutoRetainer_RemainingTime` | `300` | 0 だとリテイナーへ行かない |
| `AutoGCTurnin` | `true` | 軍票交換と希少品納品 |
| `AutoExitDuty` | `true` | 無効だとダンジョン内で止まる |
| `TerminationMethodEnum` | `Do_Nothing` | **書き換えない**（後述） |

### ⑤ リスト型は先頭に動詞が要る

`List<T>` のフィールドは値を渡すだけでは動かない。
`set` / `add` / `del` / `delEntry` / `insert` を先頭要素にした `string[]` を渡す。

```
SetConfig("CustomCommandsTermination", new[] { "add", "/test" })
SetConfig("SelectedTrustMembers",      new[] { "set", "Yshtola", "Graha", "Thancred" })
```

`string[]` は IPC を跨ぐと `JArray` になることがあるため、AutoDuty 側は両方を受ける。

### ⑥ 保存まで相手がやる＝ユーザーの設定を壊しうる

`Plugin.Configuration.Save()` が呼ばれるので、**ユーザーの設定ファイルが即座に書き換わる。**

Auto Collector が自動では絶対に呼ばず、**画面のボタンを押されたときだけ**実行しているのは
このため。`AutoDutyIpc.TrySetConfig` にその方針をコメントで残してある。

同じ理由で `TerminationMethodEnum`（終了時の動作）は `CanApply: false` にして、
**注意喚起だけして書き換えない**。ログアウトやクライアント終了を設定している人の
意図を壊してしまうため。

```csharp
Add("TerminationMethodEnum", "終了時の動作を確認する",
    "AutoDuty の設定「Termination Actions」",
    "1 周ごとに終了処理を通ります。ログアウトやクライアント終了を設定していると毎周回それが走ります。",
    "Do_Nothing", string.Empty,
    v => string.Equals(v, "Do_Nothing", StringComparison.OrdinalIgnoreCase),
    canApply: false);   // ← 直さない
```

### ⑦ 引数の既定値に頼らない

AutoDuty の `Run` は `loops` に 0 以外を渡すと **設定 `LoopTimes` が恒久的に書き換わる**。
「実行するだけ」のつもりの呼び出しが、ユーザーの設定を残して帰ることがある。

```csharp
/// loops には必ず 0 を渡す。0 以外を渡すと LoopTimes が恒久的に書き換わり、設定を壊す。
public bool TryRun(uint territoryType)
    => this.TryAction("Run",
        () => this.Func<uint, int, bool, object>("AutoDuty.Run").InvokeAction(territoryType, 0, false));
```

**実行系の IPC でも、引数が設定へ書き戻されていないかを相手のソースで確かめる。**

## 4. IPC が無い場合の逃げ道（3 段階）

相手が公開していない情報・操作は、この順に落としていく。

| 段 | 手段 | 相手への影響 | Auto Collector での例 |
|---|---|---|---|
| 1 | IPC | 相手が想定済み | `AutoDuty.GetConfig` / `SetConfig` |
| 2 | コマンド | 相手が想定済み | `/ad pause` `/ad resume` |
| 3 | リフレクション | **想定外** | 一時停止中かの判定 |

### 2 段目：コマンド

`Svc.Commands.ProcessCommand` を先に試し、未登録なら `Chat.ExecuteCommand` へ落とす。
両方用意しているのは、環境によって片方しか届かないことがあったため。

```csharp
private bool TryProcessCommand(string command)
{
    if (!this.IsLoaded) return false;

    try
    {
        if (Svc.Commands.ProcessCommand(command)) return true;
        this.AnomalyLog.Warn("Ipc", $"[AutoDuty] コマンド {command} が登録されていません。チャット経由で送ります");
    }
    catch (Exception ex) { /* ログ */ }

    try { Chat.ExecuteCommand(command); return true; }
    catch (Exception ex) { /* ログ */ return false; }
}
```

**IPC にあるものをコマンドで送らない。** 逆に、IPC に無い操作はコマンドを探す。
AutoDuty の一時停止は IPC に無いのでコマンドを使っている
（`Stop` は `TaskManager.Abort` を呼ぶため、ダンジョン後に積まれた予約ごと消えてしまう）。

### 3 段目：リフレクション

ECommons の `DalamudReflector.TryGetDalamudPlugin` で相手のインスタンスを取り、`GetField` で読む。

```csharp
if (!DalamudReflector.TryGetDalamudPlugin(this.InternalName, out var instance, suppressErrors: true))
    return false;

var field = instance.GetType().GetField("States",
    BindingFlags.Instance | BindingFlags.NonPublic | BindingFlags.Public);

if (field?.GetValue(instance) is not { } value) return false;

paused = (Convert.ToInt32(value) & 4) != 0;   // PluginState.Paused = 4
```

守ること:

- **読み取り専用にする。** 相手の内部状態を書き換えると、相手が想定していない遷移を起こす
- **値ではなく「読めたか」を返す。** 読めなければ `false` を返し、呼び出し側は
  「確認できなかった」として安全側に倒す
- **キャッシュする。** UI から毎フレーム呼ばれるとリフレクションのコストが効いてくる（500ms 保持）
- **ログを間引く。** 読めない状態が続くとログが埋まる（`IpcGate.cs` で 10 秒に 1 回）
- **ビット値をハードコードしたら根拠をコメントに残す。**
  `PluginState.Paused = 4` は相手の enum に依存する。パッチで変わりうる

## 5. 状態の問い合わせは fail-closed に倒す

設定変更そのものとは別だが、他プラグイン連携で一番痛い目を見る箇所なので残す。

```csharp
public bool IsRunningFailClosed()
{
    if (!this.IsLoaded) return false;

    if (!this.TryIsStopped(out var stopped))
    {
        this.AnomalyLog.Warn("Ipc", "[AutoDuty] 状態を取得できないため、動作中とみなします");
        return true;   // 取れなかったら「動作中」
    }

    return !stopped;
}
```

**ECommons の `SafeWrapper` は使わない。** 例外を握り潰して `default(T)` を返すため、
`IsBusy` が例外の代わりに `false` を返すと「相手は暇」と誤判定して割り込むことになる。

> 取得に失敗したら「進めてよい」ではなく「進めない」側へ倒す。

`IpcGate.cs` の冒頭にこの方針を書き残してある。

## 6. 導入済み判定はキャッシュする

`IsLoaded` は IPC 呼び出しのたびに走る。導入済みプラグイン一覧の走査は毎回やるには重い。

```csharp
this.loadedCache = Svc.PluginInterface.InstalledPlugins
    .Any(x => x.InternalName == this.InternalName && x.IsLoaded);
this.loadedCacheExpiry = now.AddSeconds(5);
```

導入状態が数秒遅れて反映されても実害は無い。
`IsLoaded` を見ずに IPC を呼ぶと、未導入の環境で毎フレーム `IpcNotReadyError` が飛ぶ。

## 7. 設計としての作法

Auto Collector が `AutoDutySetup` で採った形。他プラグインでも同じ形が使える。

1. **点検項目を宣言的に並べる**（キー・期待値・直す値・なぜ必要か・どこにあるか）
2. **読むのは自動、書くのは手動**。ボタンを押されたときだけ相手の設定を触る
3. **直せないものは直せないと明示する**（`CanApply: false`）。
   相手の意図を壊す設定は、指摘だけして触らない
4. **読めなかった項目は「違反」ではなく「不明」として扱う**（`Readable`）。
   相手が未導入・旧版のときに「設定が間違っています」と出さない
5. **変更は必ずログとチャットに残す。** 他人の設定を書き換えた事実を、
   後から追えるようにする

```csharp
public sealed record SetupItem(
    string Key,           // 相手のフィールド名
    string Title,         // 画面に出す名前
    string Where,         // 相手のどの画面にあるか
    string Why,           // なぜこの値が必要か
    string ExpectedLabel, // 期待値の説明
    string ApplyValue,    // ボタンで入れる値
    string Current,       // いまの値
    bool Ok,              // 期待どおりか
    bool Readable,        // 読めたか
    bool CanApply);       // 自動で直してよいか
```
