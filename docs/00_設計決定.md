# Auto Collector — 設計決定記録

決定日: 2026-08-25
決定者: プロジェクトオーナー（「推奨で」により推奨案をすべて採用）

引き継ぎ済みの 2 つの仕様書は一部が正反対の内容を述べているため、本書で**どちらを採用したかを確定**させる。
以降の実装は本書を最上位の基準とし、元仕様書と矛盾する場合は本書を優先する。

- 元仕様書 A: `FFXIV トークン自動交換・周回連携プラグイン 開発仕様書.md`
- 元仕様書 B: `Token Exchange Automation Plugin.md`

## D-1. AutoRetainer の扱い — 自前実装 ＋ 競合回避のみ

**採用**: 文書 B の「軍票交換は自前実装・AutoRetainer 非依存」を基本とし、文書 A の「AutoRetainer を妨害しない」という安全要件だけを取り込む。

### 決定内容

- 軍票交換は **Auto Collector が自前で実装する**。AutoRetainer に交換を依頼しない。
- AutoRetainer が未インストールでも、軍票を含む全通貨の交換機能が動作する。
- ただし AutoRetainer が存在する場合は、交換処理の前後で以下を行う:

```
交換開始前:
  AutoRetainer.PluginState.IsBusy() == true  → 待機（強制中断しない）
  IsBusy() == false → AutoRetainer.SetSuppressed(true) を立ててから交換開始

交換終了後（成功・失敗・緊急停止いずれも）:
  AutoRetainer.SetSuppressed(false) で必ず解除
```

### 根拠

`AutoRetainer/Modules/IPC.cs` および参照箇所を実ソースで確認した結果、`SetSuppressed(true)` は次の効果を持つ:

| 影響先 | 実装箇所 | 効果 |
|---|---|---|
| MultiMode | `Modules/Multi/MultiMode.cs:28` `Active => Enabled && !IPC.Suppressed` | 新規開始を停止 |
| スケジューラ | `Scheduler/SchedulerMain.cs:21` `PluginEnabledInternal && !IPC.Suppressed` | 新規開始を停止 |
| MiniTA | `Modules/MiniTA.cs:15` | 停止 |
| リテイナーセンス | `AutoRetainer.cs:656` | 停止 |

**実行中のタスクは中断しない**。つまり文書 A §39「外部プラグインそのものを強制停止しないこと」を守ったまま、交換中の割り込みだけを防げる。
AutoRetainer 側 UI にも抑制状態が表示される（`UI/MainWindow/AutoRetainerWindow.cs:189`）ため、ユーザーから見て不可解な停止にならない。

また `IsBusy` の実体は `Helpers/Utils.cs:1275`:

```csharp
internal static bool IsBusy => P.TaskManager.IsBusy || AutoGCHandin.Operation || Lifestream.IsBusy();
```

タスク実行中・GC 納品中・Lifestream 移動中を一括で拾えるため、競合判定として十分。

### 破棄した案

- 文書 A 準拠（軍票交換を AutoRetainer に委譲）: AutoRetainer が必須依存になり、文書 B §49「AutoRetainer 未導入でも全機能が動作すること」と両立しないため不採用。
- 文書 B 厳密準拠（AutoRetainer を一切参照しない）: 同時利用時に NPC 操作が衝突するため不採用。`SetSuppressed` という協調的な手段が実在する以上、使わない理由がない。

### 注意点

`IsBusy() == false` を確認した直後に AutoRetainer が処理を開始する可能性は残る。
そのため **`SetSuppressed(true)` を先に立ててから、もう一度 `IsBusy()` を確認する**二段構えとする。

## D-2. 交換データの Source of Truth — Lumina 実行時解決

**採用**: ゲームデータ（Excel シート）を Lumina 経由で実行時に解決する。外部の解析データファイルは持たない。

### 決定内容

文書 B が要求する「引き継ぎ済み解析データ」は本プロジェクトに存在しなかった。代替として、**ゲームクライアント自身が持つシートを Source of Truth とする**。

| 用途 | シート |
|---|---|
| 交換定義 | `SpecialShop` / `GCScripShopItem` / `GCScripShopCategory` / `InclusionShop` |
| トームストーン解決 | `Tomestones` / `TomestonesItem` |
| NPC 解決 | `ENpcBase` / `ENpcResident` / `PreHandler` / `TopicSelect` / `CustomTalk` |
| 座標 | `Level` / `TerritoryType` |
| アイテム属性 | `Item`（StackSize / IsUnique / ItemUICategory） |
| 軍票上限 | `GrandCompanyRank.MaxSeals` |
| 収集品納品 | `CollectablesShopItem` / `CollectablesShopRefine` / `CollectablesShopRewardScrip` |

これにより文書 B §50「新パッチで交換品が追加されても本体ロジック修正なしに Resolver が扱える」を**構造的に**満たす。ゲーム更新でシートが更新されるため、プラグイン側の更新が不要になる。

### 唯一の例外: スクリップの特殊通貨インデックス

`SpecialShop.UseCurrencyType == 16` のショップでは、コストが ItemId ではなくクライアント内部のインデックスで記録されており、**対応表がシート内に存在しない**（詳細は `docs/01_交換対応範囲.md` §4）。

この部分のみ `Data/special_currency_map.json` に外出しし、以下の三段構えで運用する:

1. JSON に定義（コード修正なしで更新可能）
2. ショップを開いた際に実際のコスト通貨を読み戻して照合し、不一致なら**安全停止して通知する**
3. デバッグ UI で解決結果を可視化（文書 B §45）

#### 改訂 2026-08-25: 「自動補正」を取りやめた

当初は 2 で「警告＋自動補正」としていたが、**自動補正は取りやめる**。

理由: 表がずれている状態で自動補正すると、**意図しない別の通貨で交換してしまう**。通貨の消費は不可逆であり、
ユーザーが気付いたときには手遅れになる。「サイレントに誤動作するくらいなら安全に停止する」という本プロジェクトの
基本方針とも矛盾する。

改訂後の挙動: **検出 → 停止 → 通知 → UI でユーザーが承認したときのみ補正を適用**する。

## D-3. 命名

| 項目 | 値 |

| InternalName | `AutoCollector` |

| 日本語表示名 | オートコレクター |
| メインコマンド | `/autocollector` |

元仕様書の `TokenExchangeLoop` / `TokenExchangeAutomation` / `/tex` はすべて破棄する。

`/ac` は他プラグインと衝突する可能性があるため、起動時に登録失敗を検出したら `/autocollector` のみで動作を継続し、その旨をログに出す。

## D-4. 移動手段

| 役割 | 使用するもの |
|---|---|
| エーテライト間テレポート | **Lifestream** `Teleport(uint aetheryteId, byte subAetheryteId)` |
| 都市内エーテライト（アクセス） | **Lifestream** `AethernetTeleport(string)` |
| エリア内の徒歩移動 | **vnavmesh** `SimpleMove.PathfindAndMoveCloseTo(Vector3, bool fly, float range)` |
| フォールバック | TeleporterPlugin `Teleport(uint aetheryteId, byte subAetheryteId)` |

### 決定内容

- Lifestream が利用可能ならテレポートは Lifestream に一本化する。都市内サブエーテライトまで面倒を見るため、交換 NPC への到達率が最も高い。
- Lifestream が未インストールの場合は TeleporterPlugin にフォールバックする。両方無い場合は「テレポート不可」として**同一エリア内の交換のみ**に機能縮退し、エラーで無理に進めない。
- 独自のナビメッシュ・経路探索は実装しない（文書 B §9）。

## D-5. 収集品納品（Phase 4）の実行主体

**採用**: Auto Collector が `CollectablesShop` を直接操作する。

外部の納品自動化プラグインに依存すると、対応範囲・停止タイミング・エラー処理をこちらで制御できず、
文書 A §15 の「納品 → 交換 → 納品」ループの安全な一時停止・再開が保証できないため。

Phase 4 の着手時点で、`CollectablesShopItem` / `CollectablesShopRefine` から納品可能な収集品を解決し、
本プラグインの State Machine 内の一状態として実装する。

## 共通の実装原則（両仕様書で一致しているため確定）

1. **ID 優先** — `ItemId` / `TerritoryId` / `ShopId` / `NpcDataId` / `CurrencyItemId` で管理する。表示文字列に依存しない。
2. **固定時間待機の禁止** — 「ショップが開いた」「通貨が減った」「アイテムが増えた」等、実際の状態変化を確認して遷移する。各状態にはタイムアウトを設けるが、タイムアウトは失敗であって「次へ進む合図」ではない。
3. **交換結果の検証** — UI 操作の実行をもって成功としない。`通貨が減った AND アイテムが増えた` を確認する。期待値との一致も検証する。
4. **UI 位置への直接依存を避ける** — ID からエントリ index を逆引きし、**その index の実際の内容を読み戻して照合してから**操作する。
5. **同期的な無限ループの禁止** — State Machine + フレーム駆動で実装する。
6. **緊急停止** — 本プラグインのタスク・移動・NPC 操作・Queue のみを停止する。外部プラグインを無差別に停止しない。`SetSuppressed` は必ず解除する。
7. **安全条件** — 戦闘中・死亡中・カットシーン・ロード中・Duty 中・操作不能中は交換を開始しない。条件成立時は要求を Queue に保存するだけにとどめる。
