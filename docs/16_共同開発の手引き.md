# Auto Collector — 共同開発の手引き

**最終更新: 2026-09-22 / 対象: `main` = 0.1.2.8 相当（リリース済みは 0.1.2.6）**

このリポジトリへ参加していただくにあたっての取り決めです。
**「絶対に守ること」と「ブランチ運用」の 2 つは例外なく守ってください。**
それ以外は相談のうえ変えて構いません。

---

## 1. これは何か

FFXIV / Dalamud 向けプラグインです。

> 通貨が閾値へ到達したら、実行中の自動処理を**安全に停止**し、交換所へ移動して交換し、**元の処理へ復帰する**。

扱う稼ぎ方は 2 つあり、将来ギャザラーを足す予定です。

| 稼ぎ方 | 流れ |
|---|---|
| 戦闘 | AutoDuty の周回に相乗り → トームストーンが貯まる → 交換所へ → 交換 → 周回へ戻す |
| クラフター | リテイナーから素材を取り出す → 収集品を製作 → 納品してスクリップを得る → 交換 |

**他プラグインと協調して動くことが設計の中心**です。AutoDuty / AutoRetainer / Artisan /
vnavmesh / Lifestream と同時に動くため、相手の処理を壊さないことが最優先になります。

| 用途 | 場所 |
|---|---|
| ソース | `https://github.com/rioriopu/AutoCollector` |
| 配布（repo.json とリリース） | `https://github.com/rioriopu/PrivateReleaseRepo` |

## 2. 絶対に守ること

**この 6 つは相談なしに破らないでください。**すべて、実際に起きた不具合から来ています。

### 2-1. 実在を確認していない名前を創作しない

API 名・IPC 名・メソッド名・シート名・ノード ID・コールバックの値。
**必ず実ソースかゲームデータで確認してから使ってください。**

- 他プラグインの IPC → 相手のソースを読む（後述の参照リポジトリが手元にあります）
- ゲームのシート → Lumina で実際に引いて確かめる
- アドオンの操作 → **実機で記録を取る**（診断タブの callback 記録）

「たぶんこうだろう」で書いた値は、ゲームのアイテムを失わせます。

### 2-2. 交換情報をハードコードしない

アイテム ID・NPC ID・ショップ ID・値段・座標・会話の選択肢。
**すべて Lumina のシートから実行時に解決します。**

パッチで変わるうえ、埋め込むと「なぜこの値なのか」が追えなくなります。
区分の名前すら `SpecialShopItemCategory` から引いています。

### 2-3. 固定時間待機で次へ進まない

```csharp
// だめ
await Task.Delay(2000);
FireExchange();

// よい
if (ShopIsOpen() && ItemIsVisible()) { FireExchange(); }
```

**実際の状態変化を確認してから進みます。**「ショップが開いた」「通貨が減った」
「アイテムが増えた」「一覧が入れ替わった」など。

時間はあくまで**諦めるまでの上限**にだけ使ってください。
「N 秒待ったから次へ」は禁止です。回線やサーバの状態で簡単に崩れます。

### 2-4. 成功は「減った AND 増えた」で検証する

**UI 操作を実行したことをもって成功としない。**

| 動作 | 成功の判定 |
|---|---|
| 交換 | 通貨が減った **かつ** アイテムが増えた |
| 納品 | 収集品が減った **かつ** スクリップが増えた |

撃ったのに反映されていない場合があります。撃つ前の値を控え、撃ったあとに
実際の所持数を見て判断してください。**狙っていない物が減っていないかも見ます。**

### 2-5. 外部プラグインを強制停止しない

AutoRetainer は `SetSuppressed` による**協調的な抑制のみ**。実行中の処理は中断しません。
**緊急停止のときも必ず抑制を解除してください。**解除漏れは相手を永久に止めます。

AutoDuty を止めてよいのは「周回の切れ目」だけです。コンテンツの途中では止めません。

### 2-6. 日本語で書く

README・ドキュメント・**コードコメント**・UI の文言、すべて日本語です。
識別子（クラス名・メソッド名）は英語のままで構いません。

## 3. ブランチ運用

**`main` には実機で確認が取れたものだけを置きます。**

```
feature/<名前>  ← ここで開発。C:\DevPlugins へのデプロイもここから
      ↓ 実機で確認が取れてから
    main        ← 確認済みのものだけ。ここでタグとリリースを打つ
      ↓
  repo.json を更新 → 利用者へ配布
```

### 守ること

1. **`main` へ直接コミットしない。**小さな修正でもブランチを切る
2. ブランチ名は `feature/<英数字の短い名前>` または `fix/<英数字の短い名前>`
3. **マージは実機で確認してから。**確認前のものを `main` へ入れない
4. タグ（`v<版>`）と GitHub リリースは、**`main` へマージしたあと `main` で**打つ
5. 配布リポジトリの `repo.json` を書き換えるのも `main` へ入れたあと
6. 差し戻しになったら作業ブランチで直して押し直す。**`main` は動かさない**

デプロイ（`C:\DevPlugins\AutoCollector`）は**作業ブランチからで構いません。**
実機で見てもらうための配置であって、配布ではないからです。

### 手順

```bash
# 1. 最新の main から切る
git switch main
git pull
git switch -c feature/やること

# 2. 開発する。Debug ビルドすると DevPlugins へ出る
dotnet build AutoCollector/AutoCollector.csproj -c Debug

# 3. 実機で確認する

# 4. コミットして押す
git add -A
git commit
git push -u origin feature/やること

# 5. PR を立てる（または直接マージ）
```

### いま動いているブランチ

| ブランチ | 内容 | 状態 |
|---|---|---|
| `main` | 0.1.2.8 相当 | 納品の修正 2 件をマージ済み。**未リリース** |
| `feature/earner-modules` | 稼ぎ方のモジュール化 | 段 0 まで完了。`docs/15` に全 8 段 |
| `feature/multi-cost-exchange` | 対価が 2 つある交換（武器など） | 未着手 |
| `fix/stop-blocks-delivery` | 納品の修正 2 件 | main へマージ済み。削除可 |

## 4. コミットとリリースの帰属

### 4-1. AI の痕跡を残さない

**コミット・PR・issue・リリースノートに、AI 生成を示す記述を一切含めません。**

- `Co-Authored-By: Claude ...` を**付けない**
- `Generated with ...` のような署名を**付けない**
- セッション URL の行も**付けない**

author / committer は常に `rioriopu <rioriopuu@gmail.com>` です。
環境の git config が別人になっている場合は明示してください。

```bash
git -c user.name=rioriopu -c user.email=rioriopuu@gmail.com commit
```

**確認方法**

```bash
git log --format='%an|%ae|%cn|%ce' -100 | grep -i claude    # 0 件であること
git log --format='%b' -100 | grep -i "co-authored-by:.*claude"   # 0 件であること
```

### 4-2. コミットメッセージの書き方

**「何をしたか」ではなく「なぜそうしたか」を書きます。**日本語です。

```
選択の確認を、実際に変わる値で行う

納品窓口は開くのに納品されず、窓を開いては閉じるのを繰り返す。
収集用のタコスだけは納品できていた。

選択は効いていた。確認の仕方が間違っていた。
品を選ぶと右の一覧が 0 行から手持ちの数だけ埋まる。一方、左の一覧の
SelectedItemIndex は動かない。この動かない値を使っていたため誤判定していた。

確認を右の一覧の行数で行うようにした。
```

1 行目は要約、空行、そのあとに**症状 → 原因 → 対処**。
「タコスだけ通っていた理由」のような**決め手になった観察は必ず残してください。**

## 5. リリース手順

**指示があったときだけ**行います。自分の判断でリリースしないでください。

```bash
# 1. main へマージ済みであること、実機確認が済んでいることを確認

# 2. 版を上げる（AutoCollector.csproj の <Version>）
#    版を上げずにアセットだけ差し替えない。Dalamud は版で更新を判断するため、
#    導入済みの環境に届かない

# 3. Release ビルド
dotnet build AutoCollector/AutoCollector.csproj -c Release
#    → AutoCollector/bin/Release/AutoCollector/latest.zip

# 4. タグを打つ
git tag -a v0.1.2.9 -m "0.1.2.9"
git push origin v0.1.2.9

# 5. latest.zip を AutoCollector.zip に改名してリリース
gh release create "AutoCollector-0.1.2.9" AutoCollector.zip \
  --repo rioriopu/PrivateReleaseRepo \
  --title "Auto Collector 0.1.2.9" \
  --notes-file notes.md \
  --prerelease=false --latest
```

### repo.json の書き換え

`rioriopu/PrivateReleaseRepo` の `repo.json` で、**AutoCollector の項だけ**を書き換えます。
**他 14 プラグインの項には絶対に触れないでください。**

| 言われ方 | 書き換える場所 |
|---|---|
| 「ベータ版」「テスト版」 | `TestingAssemblyVersion` と `DownloadLinkTesting` **だけ**。`AssemblyVersion` 系は据え置き |
| 「正式リリース」 | 上記に加えて `AssemblyVersion` / `DownloadLinkInstall` / `DownloadLinkUpdate` も同じ版へ |

`Changelog` の先頭にも 1 項追加します（利用者向けの言葉で、内部用語を避けて）。

書き換えたあとは**必ず差分を確認**してください。

```bash
git diff repo.json   # AutoCollector の 6 行だけが変わっていること
```

## 7. ドキュメントの読む順番

**`docs/` が最上位の基準です。**元仕様書 2 つ（リポジトリ直下の .md）は参考であり、
AutoRetainer の扱いなどで**正反対の内容**を含みます。矛盾したら `docs/` を優先してください。

| # | 文書 | 内容 |
|---|---|---|
| 00 | 設計決定 | **最初に読む。**元仕様書の矛盾に対する裁定 |
| 01 | 交換対応範囲 | どの交換にどこまで対応するか（実データ実測値つき） |
| 15 | 稼ぎ方のモジュール化 | いま進めている構造変更。全 8 段と「触ってはいけない場所」 |
| 03 | 調査結果 | **F-01 〜 F-69 の不具合記録。**同じ罠を踏まないために読む価値が高い |
| 03 | 実装中の発見 | 実機実測の記録。callback の値やノード ID はここに根拠がある |
| 10 | 収集品納品仕様 | 納品画面の配置と発火の実測 |
| 13 | 他プラグインの設定を変更する | AD の設定を外から書き換える仕組み |
| 14 | 呼び鈴へ自動で移動して話しかける | 呼び鈴の探索と移動 |

**`docs/03_調査結果.md` を先に眺めてください。**「なぜこんな作りになっているのか」の
答えがほぼここにあります。過去に直した不具合を、知らずに元へ戻してしまうのが一番多い事故です。

### 記録を残す義務

**不具合を直したら `docs/03_調査結果.md` に F-番号で追記してください。**

- 症状（実機のログや画面をそのまま）
- 原因（`file:line` つき）
- 対処
- **決め手になった観察**

この記録があったおかげで、2 週間前の記述から今回の原因が特定できた例が複数あります。
逆に、誤った訂正を書いたせいで 2 週間見逃した不具合もあります（F-67）。

## 8. 落とし穴（実際に踏んだもの）

新しく入る方が同じところを踏みやすい順に並べます。

### 8-1. 交換画面は区分ごとにしか品を出さない

「ILv750ファイター装備」は全 37 件ありますが、開いた直後は防具の 25 件しか見えません。
アクセサリは窓の中のタブを切り替えないと出てきません。

```
Fire(4, -1, 1, 区分)   ← 前 3 つが Int、第 4 引数だけ UInt
```

**品目のある交換ショップ 1218 件のうち 668 件が区分混在です。**

### 8-2. 納品画面の `SelectedItemIndex` は動かない

`Fire(12, 行番号)` で品を選んでも、左の一覧の `SelectedItemIndex` は変わりません。
選択が効いたかどうかは**右の一覧（node 31）が手持ちの数だけ埋まったか**で判断します。

納品ボタン（node 51）も現れません。`Fire(15, 0u)` を直接撃ちます。

### 8-3. 型を取り違えると効かない

記録の表示規則は「`Int` なら数字のみ、`UInt` なら `u` を付ける」です。

```
Fire(0, index, 個数, 空)     交換     … すべて Int
Fire(12, 行番号)              納品の選択 … 第 2 引数は UInt
Fire(15, 0u)                  納品の実行 … 第 2 引数は UInt
Fire(4, -1, 1, 区分)          区分の切替 … 第 4 引数だけ UInt
```

### 8-4. 止める旗が複数ある

`ExchangeExecutor.IsAborted` と `AutoDutyKeeper.Suspended` は別の旗です。
**片方だけ見ると、製作だけ動いて納品が弾かれる**状態になります（F-68）。

止める・戻すを触るときは、**両方を必ず対で扱ってください。**

### 8-5. `EmergencyStop` の順序は載荷条件

```
GoalRunner.Stop
  → RetainerRestock / CraftRunner / CollectableCycle / CollectableDelivery
    → ExchangeExecutor.Abort
      → AutoDutyKeeper.Suspend
        → 走っている周回の停止
```

取り出し側の後始末が AutoRetainer の抑制を返す**前に** `Abort` を通すと空振りします。
**順序を入れ替えないでください。**

### 8-6. 設定のプロパティ名を変えると利用者の値が消える

`EzConfig` は Newtonsoft を使っています。プロパティ名を変えると旧キーが読まれず、
**既定値に戻ります。**名前を変える必要があるときは、旧フィールドを残して
`ConfigVersion` を上げ、`MigrateConfig` で写してください。

## 9. 実機確認のお願い

このプラグインは**机上のレビューでは壊れ方が分かりません。**
ゲームの画面・他プラグイン・回線が絡むためです。

マージ前に、最低限この 3 つを実機で確認してください。

1. **触った機能が動くこと**
2. **「すべて止める」で止まり、「再開する」で戻ること**
3. **交換・納品の結果が実際の所持数と合っていること**

診断タブに次の道具があります。積極的に使ってください。

| 道具 | 用途 |
|---|---|
| callback の記録 | アドオンへ何が渡っているかを記録。**発火の値はすべてこれで確定させています** |
| 収集品納品画面のダンプ | ノード・AtkValues・手持ちを一括で書き出す |
| 詳細ログ | 状態遷移を時刻つきでファイルへ |

**記録が 1 行も出ないことも結論です。**（別経路を通っている証拠になります）

## 10. 困ったときの調べ方

実際にこの手順で原因を特定しています。

1. **症状を時刻つきで記録する**（詳細ログ＋ callback 記録）
2. **状態遷移の時間差を測る**
   例: 窓を開いてから閉じるまで 2.146 秒 → 諦めるまでの上限 2 秒と一致 → タイムアウト経路だと確定
3. **ゲームデータを直接引く**
   Lumina を参照するコンソールアプリを作って、シートの実値を確かめる
4. **`docs/03_調査結果.md` を検索する**
   同じ症状が過去にあることが多いです
5. **他プラグインの実装を読む**
   例: 交換画面の区分タブの構造は ItemVendorLocation の実装から確定させました

**推測で直さないでください。**根拠のない修正は、別の場所を壊したうえで
「直した」という記録だけを残します。
