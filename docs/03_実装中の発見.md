## F-1. トームストーンのスロット番号は「過去のショップ」まで巻き込む

### 何が起きるか

`SpecialShop` のコストは `CostType == 2` のとき `Tomestones` シートの**行番号**を指す。
そして `Tomestones` の行番号は固定で、中身がパッチごとに入れ替わる。

このため、**過去パッチのショップが「現在のトームストーンを要求している」ように見える**。

数理（`Tomestones` 行 2）で実測した結果:

| ShopId | PatchNumber | NPC 参照 | ショップ名 |
|---|---|---|---|
| 1770434 | 600 | **なし** | アラガントームストーン:経典の取引（ファイター） |
| 1770437 | 600 | **なし** | アラガントームストーン:天文の取引（ファイター） |
| 1770764 | 700 | **なし** | アラガントームストーン:美学の取引（ILv700ファイター装備） |
| 1770767 | 700 | **なし** | アラガントームストーン:天道の取引（ILv720ファイター装備） |
| **1770911** | **720** | **あり** | アラガントームストーン:数理の取引（ILv750ファイター装備） |
| **1770912** | **720** | **あり** | アラガントームストーン:数理の取引（ILv750ソーサラー装備） |
| **1770913** | **720** | **あり** | アラガントームストーン:数理の取引（ILv750武器） |
| **1770925** | **720** | **あり** | ファントムウェポン素材の取引 |
| **1770994** | — | **あり** | アラガントームストーン:数理の取引（その他） |
| **1770900** | 710 | **あり** | 強霊薬の取引 |

数理をコストとするショップは 18 件見つかるが、**現行で到達できるのは 6 件だけ**。
残り 12 件は 6.x / 7.0 当時に「行 2 のトームストーン」を要求していたショップで、いまは NPC から到達できない。

### 検証方法

対象 12 ショップの ID を、サブロウ以外の全シートの uint32 / int32 カラムに対して逆引きしたところ、
**参照が 1 件も見つからなかった**（`ENpcBase.ENpcData` / `FateShop` / `InclusionShop` を含む）。
ゲーム内から到達する手段が存在しない、いわゆる死んだ行である。

### 対応

**「NPC から到達できるショップだけを採用する」という現在の実装がそのまま正しい判定になる。**
死んだショップは NPC が付かないため、自然に除外される。特別なフィルタは不要。

ただし UI 上では「NPC 未解決」として件数を見せる。もし将来ここに現行ショップが紛れ込んだら、
それは解決経路の実装漏れを意味するサインになるため、黙って捨てずに表示する。

補助的な判定材料として `SpecialShop.Item[].PatchNumber` も使える（実測で死んだショップは 600 / 700、
現行は 710 / 720）。ただしパッチ番号が 0 の行も存在するため、単独の判定条件にはしない。

## F-2. NPC の座標は Level シートだけでは足りない

### 実測

| 取得元 | ユニーク NPC 数 |
|---|---|
| `Level`（`Type == 8`） | 24,210 |
| マップ配置ファイル `planevent.lgb` | 39,540 |
| **LGB にしか存在しない** | **16,441** |

MVP で必要な NPC の実例:

| NPC | ItemId | `Level` | LGB |
|---|---|---|---|
| ジルコン（数理装備） | 1049079 | ○ Solution Nine (-187.7, 0.7, -30.9) | ○ 同一座標 |
| エイレーネー（強霊薬） | 1049083 | **×** | ○ Solution Nine (-210.2, 0.9, -8.3) |
| **アーミナ（ファントムウェポン素材）** | 1053904 | **×** | ○ **Phantom Village (40.8, 0.0, 20.9)** |

**仕様書が主要ユースケースとして名指ししていた「ファントムウェポン関連の石」の交換 NPC は、`Level` シートからは座標を取得できない。** LGB を読まないと MVP の目的が達成できない。

`Level` と LGB の両方に存在するジルコンでは座標が完全に一致したため、LGB 側の値は信頼できる。

### コスト実測

計画（§6-Q6）では LGB 解析を「初期化コストが大きい」として Phase 2 送りにしていたが、これは誤りだった。

```
TerritoryType 1,290 件 → ユニーク Bg 589 件（Bg が同じエリアは配置ファイルを共有する）
589 個の planevent.lgb をすべて解析: 113 ms / 失敗 0 件
```

**113 ms で全エリアを解析できる。** 1 フレームで実行すると体感できるカクつきになるため、
フレームあたり 60 件ずつに分けて処理する（約 10 フレーム = 0.2 秒未満）。

### 対応

`NpcLocationService` を `Level` + LGB の統合索引に変更した。
`Level` を先に読み、LGB で不足を補う。同一エリア・同一座標（1 単位未満の差）の重複は排除する。

Lumina の API:

```csharp
Svc.Data.GetFile<LgbFile>($"bg/{bg[..bg.LastIndexOf('/')]}/planevent.lgb")
// layer.InstanceObjects → AssetType == LayerEntryType.EventNPC
// obj.Object as LayerCommon.ENPCInstanceObject → npc.ParentData.ParentData.BaseId
// obj.Transform.Translation
```

`ENPCInstanceObject` の `BaseId` は `ParentData.ParentData.BaseId` と 2 段ネストしている点に注意。

## F-3. ENpcBase の RowId は連番ではない（実装バグとして混入していた）

`ENpcBase` は 59,851 行だが、**RowId は 1000000 から始まる**。

```
Count       = 59851
先頭 RowId  = 1000000, 1000001, ...
TryGetRow(0)       → false
TryGetRow(1049079) → true
```

フレーム分割走査でカーソルを `0 .. Count` と回し、`TryGetRow(cursor)` で取得する実装を書いていたが、
これでは **1 件も取得できない**。しかも例外は出ず「交換候補 0 件」という静かな誤動作になる。

位置指定でのアクセスには `ExcelSheet<T>.GetRowAt(int rowIndex)` を使う。修正済み。

> 同種の間違いは他シートでも起こりうる。**フレーム分割走査を書くときは必ず `GetRowAt` を使う**こと。

## F-4. Lumina の構造体は既定値のプロパティに触ると例外になる

```csharp
// これは NullReferenceException を投げる
var reward = entry.ReceiveItems.FirstOrDefault(r => r.Item.RowId != 0);
if (reward.Item.RowId == 0) { ... }   // ← ここで落ちる
```

`FirstOrDefault` が返す `default(ReceiveItemsStruct)` は `ExcelPage` が null のため、
プロパティアクセスの時点で落ちる。**LINQ の `FirstOrDefault` + プロパティ参照を書かない。**
必ず `foreach` で取り出し、見つからなかった場合は ID を 0 のままにして判定する。

## F-5. CostType の意味（実データで確定）

`SpecialShop.UseCurrencyType` ではなく、エントリ単位の `ItemCosts[].CostType` で分岐する。

| CostType | `ItemCost.RowId` の意味 | 実データの件数 | 出現する RowId |
|---|---|---|---|
| 0 | 実 ItemId | 19,257 | すべて 8 以上 |
| 1 | 実 ItemId | 88 | すべて 8 以上 |
| **2** | **`Tomestones` シートの行番号** | 3,471 | 1 / 2 / 3 のみ |
| **3** | **特殊通貨バケット（スクリップ類）** | 2,422 | 2 / 4 / 6 / 7 のみ |

`UseCurrencyType` で分岐してはならない理由: `UseCurrencyType == 2` のショップが 463 件あり、
そこに詩学コストのエントリが含まれる。`UseCurrencyType` だけで判定するとギルやシャードへ誤解決する。

なお `CostType == 3` に出現するインデックスは 2 / 4 / 6 / 7 であり、**1 は出現しない**。
`special_currency_map.json` の index 1（詩学）はこの経路では使われていない。Phase 4 で再確認する。

## F-6. AtkValue の型は UInt に統一されていない（S4 実機）

`ShopExchangeCurrency` の実測値:

| 項目 | 位置 | 型 | 値 |
|---|---|---|---|
| AtkValues の総数 | — | — | 3,325 |
| NumEntries | 4 | UInt | 18 |
| CurrencyAmount | 86 | UInt | 594 |
| **CurrencyIcon** | 87 | **Int** | 65,122 |
| 1 件目 Cost | 456 | UInt | 20 |
| 1 件目 ItemId | 1066 | UInt | 49,226 |
| 1 件目 Index | 1310 | UInt | 0 |

**位置はすべて正しく、87 番だけが `Int` だった。**

ECommons の `AddonMaster` は `Addon->AtkValues[n].UInt` と型を確認せずに読む。`AtkValue` は共用体なので
`Int` の値でも同じ 4 バイトを `UInt` として読めてしまい、結果的に動作している。
一方 ECommons の `AtkReader` は型が `UInt` でなければ `InvalidCastException` を投げるため、こちらで止まった。

### 対応

`Int` と `UInt` の両方を整数として受け付ける。型を無視するのではなく、**受け付ける型を列挙し、
それ以外（文字列など）は従来どおり失敗として検出する**。`Int` が負値の場合も ID・個数としては使えないため弾く。

失敗時の扱いを重要度で分けた:

- `NumEntries` / `CurrencyAmount` が読めない → **中止**（交換前後の検証ができないため）
- `CurrencyIcon` が読めない → 続行（補助情報のため）
- 個別エントリの値が揃わない → そのエントリだけ除外し、件数を警告表示

## F-7. 同じアイテムが複数のショップに別の値段で載っている（S4 実機）

数理の「その他」交換で、画面のコストとゲームデータのコストが 12 件も食い違った。
原因は**私の照合ロジックのバグ**で、読み取り側は正しかった。

| アイテム | Shop 1770766（死） | Shop 1770770（死） | **Shop 1770994（現行）** | 画面 |
|---|---|---|---|---|
| マストドンの粗皮 | — | — | **20** | 20 |
| 新王国の研磨剤 | — | 20 | **10** | 10 |
| シュバラールのワニス | 20 | 10 | **10** | 10 |

照合用の辞書を `Results` 全体から `TryAdd` で組んでいたため、**先に見つかった死んだショップの定義が残り**、
現行ショップの値段と比較されて不一致になっていた。

### これが示す本質的な問題

**`ItemId` だけでは交換定義を一意に決められない。** 同じアイテムが複数のショップに、
別の値段で載っている。したがって「どのショップが開いているか」を確定させないと、
正しい値段と比較できない。

### 対応

1. `ExchangeResolver.LiveResults` を追加した。`Results` には原因調査用に死んだショップの定義も
   含まれるため、**値段の比較と交換の実行には必ず `LiveResults` を使う**。
2. `ShopService.IdentifyShop()` を追加した。読み取った **(ItemId, コスト) の組**が
   すべて含まれるショップを探して、開いているショップを特定する。
   完全一致が 1 件でなければ「特定できず」として交換しない。

`ShopMatchKind.CostMismatch` による安全停止は正しく機能していた。
実際、この食い違いは交換を撃つ前に検出され、赤字で「この状態では交換を実行してはいけません」と表示された。
**読み戻して照合する設計が意図どおり働いた事例。**

## F-8. ショップのタブは別々の SpecialShop 行（S4 実機）

ジルコンのショップには「武器 / 防具 / アクセサリ / その他」の 4 タブがあり、
`NumEntries` は**現在開いているタブの件数だけ**を返した（その他タブ = 18 件）。

数理の現行ショップ 4 件（1770911 ファイター / 1770912 ソーサラー / 1770913 武器 / 1770994 その他）が
そのままタブに対応していると見られる。

MVP はタブ切り替えを行わない方針のため、**目的アイテムが現在のタブに無ければ
`ExchangeItemNotFound` で安全停止する**。ファントムウェポン素材（アーミナ）は
ショップの登録が 4 件のみでタブ構成ではないため、MVP の主要ユースケースには影響しない。

### 未解決

Shop 1770994 のゲームデータ上のエントリは 29 件だが、画面には 18 件しか出ていない。
差の 11 件は開放条件などで非表示になっている可能性がある。
交換対象が非表示だった場合は `ItemNotFound` で安全に止まるため MVP では問題にならないが、
Phase 2 で原因を確認する。

## F-9. 交換 callback の実測値（S5 実装前）

ユーザーがジルコンのショップで手動で 1 個交換したときの `FireCallback` を記録した結果:

```
updateState=True   Fire(0, 5, 1, (なし))
```

- **値は 4 つ**。3 つではない。
- 記録側の表示規則は「`Int` 型なら数字のみ、`UInt` 型なら数字に `u` を付ける」実装なので、
  **`0` / `5` / `1` はすべて `AtkValueType.Int`**。`UInt` ではない。
- 4 つ目は `Type == 0` の空 `AtkValue`。
- `5` は画面から読み取った index（`AtkValues[1310 + i]`）と一致。`1` は個数。

### 参照実装との差分

ECommons の `AddonMaster.ShopExchangeCurrency.ShopItemInfo.Select` は次のように送っている:

```csharp
Callback.Fire(master.Base, true, 0, Index, amount);   // 3 値
```

`Index` は `uint` フィールドなので、`Callback.Fire` の変換規則（`case uint` → `AtkValueType.UInt`）により
**`UInt` 型で送られる**。実測した `Int` とは型が異なり、値の個数も 3 と 4 で違う。

### 対応方針

実測どおりに再現する。`Callback.Fire` は `case AtkValue rawValue` を持つため、
`Callback.ZeroAtkValue`（`Type = 0`）を 4 つ目として直接渡せる。

**`index` は必ず `int` にキャストする。`uint` のまま渡すと `UInt` 型になり、
ゲームが送っている `Int` と食い違う。**

3 値でも動作するかどうかはソースから判断できないため、確認できている 4 値の形で撃つ。

## F-10. 交換には確認ダイアログが必ず挟まる（S5 実装前・実測）

`CallbackRecorder` の `AddonFilter` を空にして全アドオンを記録し、手動で 1 個交換した結果（時系列順）:

| 時刻 | アドオン | callback | 意味 |
|---|---|---|---|
| 19:51:19 | **ShopExchangeCurrency** | `Fire(0, 5, 1, (なし))` | 交換コマンド |
| 19:51:19 | ItemDetail | `Fire(-1)` | ツールチップ。マウス移動に伴う付随的なもので交換とは無関係 |
| 19:51:20 | **SelectYesno** | **`Fire(0)`** | **確認ダイアログの Yes** |
| 19:51:21 | ItemDetail | `Fire(-1)` | 同上 |
| 19:53:08 | ScreenLog | `Fire(0, 0u)` | 約 2 分後。無関係 |

### 確定したこと

1. **確認ダイアログ（`SelectYesno`）は必ず出る。** 出ない前提の実装は成立しない。
   計画（`docs/02` §6-Q4）では「出るかどうか未確認」としていたが、出ることが確定した。
2. **`ShopExchangeCurrencyDialog`（数量入力）は出ない。** 1 個交換では登場しない。
3. **`SelectString` / `Talk` は交換の流れに絡まない。** 交換後もショップは開いたまま。
4. 交換コマンドから確認ダイアログまで **約 1 秒**かかる。同フレームで判定してはいけない。
5. `SelectYesno` の Yes は `Fire(0)`（1 値・Int）。

### 実装での扱い

ボタンをクリックする経路（`AddonMaster.SelectYesno.Yes()`）を使う。実測した `Fire(0)` は
ユーザーがボタンを押した結果として発生したものであり、ボタン経由なら同じ callback に行き着く。
callback を直接撃つとボタンの有効・無効状態を完全に無視することになるため採用しない。

ただし ECommons の `Yes()` には 2 つの落とし穴があるため、そのまま呼ばない。

```csharp
// SelectYesno.cs:37-49
public void Yes()
{
    if (!RespectDisabledButtons)          // ← 既定は false
    {
        if (Addon->YesButton != null && !Addon->YesButton->IsEnabled)
        {
            var flagsPtr = (ushort*)&Addon->YesButton->...NodeFlags;
            *flagsPtr ^= 1 << 5;          // ← 無効化された Yes を強制的に有効化する
        }
    }
    ClickButtonIfEnabled(Addon->YesButton);
}
```

- `RespectDisabledButtons` の既定 `false` は、**ゲームが押させないと決めたボタンを強制的に押す**。
  必ず `true` を設定する。
- `ClickButtonIfEnabled`（`!AddonMasterBase.cs:61-70`）は `button->IsEnabled` を
  **null チェックなしで**参照する。`YesButton` が null なら逆参照で落ちる。
  `RespectDisabledButtons` の値と無関係に起きるため、呼び出す前に自分で null / IsEnabled / IsVisible を確認する。

さらに、`GenericHelpers.TryGetAddonMaster<SelectYesno>` は**インデックス 1 のアドオンしか見ない**
（`AddonHelpers.cs:139-152`）。他プラグインや別要因のダイアログを取り違えるため、
インデックスを走査し、**本文に報酬アイテム名が含まれるもの**だけを対象にする。

## F-11. 確認ダイアログの本文に報酬アイテム名は含まれない（S5 実機）

最初の実装は「本文に報酬アイテム名が含まれること」を確認ダイアログの照合条件にしていたが、
実際の本文は次のとおりで、**報酬名を含まない**。

```
以下のアイテムを
アラガントームストーン:数理×20と交換します。
```

本文にあるのは**通貨名とコスト**だけで、報酬アイテム名（イヨラエキス）はアイコン横の別ノードにある。
このため自分が出したダイアログを認識できず、押さずに `ExchangeUnresolved` でタイムアウトした。

**これは安全側に倒れた失敗である。** 押せなかったときに再送する作りだったら、この時点で二重に購入していた。
`inFlight` ラッチと「`WaitOutcome` から `Armed` へ戻る辺を作らない」設計が意図どおり機能した。

### 対応

照合条件を次のように変更した。

- **必須**: 本文に**通貨名**と**コストの数値**の両方が含まれること
- **追加の裏付け**: アドオン内の全テキストから報酬名を探し、見つかれば確認済みとする。
  見つからない場合は、実際に表示されていた文字列を `AnomalyLog` に記録する

テキストの収集はノード ID を決め打ちせず、`AtkValue` の文字列と `UldManager.NodeList` の

配置ファイル由来の NPC 座標に床スナップ（最大 10 のずれを許容）が乗るため、

対応:
1. 移動中に NPC が視界に入ったら、**実際のオブジェクト位置を目的地に切り替える**
2. 対話前に距離を確認し、遠ければ NPC の実位置へ近づき直す（最大 3 回）

閉じる処理が緊急停止時にしか入っていなかった。開けっ放しだと、
次の交換の事前条件（ブロックするアドオンが無いこと）にも引っかかる。

### 失敗時に AutoRetainer の抑制を解除していなかった（重大）

`Fail()` / `FailUnresolved()` が抑制を解除していなかったため、
**エラーで停止したあとも AutoRetainer を止めたまま放置していた。**

設計決定 D-1 で「成功・失敗・緊急停止のいずれでも必ず解除する」と定めていた不変条件が、
実装で守られていなかった。失敗経路でも移動停止と抑制解除を必ず通すようにした。

### 同一内容のショップが複数あると特定できず停止していた

同じ品揃え・同じ値段のショップが複数存在する（ロウェナ商会の商人が 4 都市にいて、
それぞれ別の `InclusionShop` を持ちながら中身は同一）。
`IdentifyShop` は完全一致がちょうど 1 件であることを要求していたため停止していた。

**候補がすべて同じ品揃え・同じ値段である以上、どれであっても照合結果は変わらない。**
ショップ特定の目的は「別のショップの値段と比較する事故」を防ぐことなので、
候補全部が値段で一致しているなら危険はない。

そこで「自分が向かったショップが候補に含まれているか」を最後の手がかりにした。
含まれていなければ従来どおり停止する。

## F-16: `PluginState.Navigating` はコンテンツに入ったあとにしか立たない

「AutoDuty のループ間処理（リテイナー・GC 納品）が終わった合図」として
`AutoDuty.IsNavigating()` を使っていたが、これは成立しない。

`AutoDuty.cs` の周回タスク列は次の順で積まれる。

```
Run-WaitDutyStarted     : Svc.DutyState.IsDutyStarted を待つ
Run-WaitNavIsReady      : vnavmesh の準備を待つ
Run-StartNavigation     : StartNavigation() → States |= PluginState.Navigating
```

つまり `Navigating` が立つのは **コンテンツに入って開始したあと**。
これを待つと必ずコンテンツ内になり、`SafetyGuard` に弾かれて交換の機会が来ない。
実機では「ループ間処理が終わるのを待っています」から永久に進まなくなった。

IPC で読める状態は `IsStopped` / `IsLooping` / `IsNavigating` の 3 つだけで、
ループ間処理の進行度を表すものは無い。`Stage` は公開されていない。

さらに、ループ間処理の終了からコンテンツ突入までの間隔は
コンテンツサポート等では実質ゼロに近く、そもそも狙える窓ではなかった。

### 対策: 停止ではなく一時停止で割り込む

`AutoDuty.cs` の `Stage` セッタ:

```csharp
case Stage.Stopped:
    StopAndResetALL();      // TaskManager.Abort() を含む → 予約が消える
    break;
case Stage.Paused:
    PreviousStage = Stage;
    if (VNavmesh_IPCSubscriber.Path_NumWaypoints() > 0)
        VNavmesh_IPCSubscriber.Path_Stop();
    FollowHelper.SetFollow(null);
    TaskManager.SetStepMode(true);   // 実行を止めるだけ。キューは保持される
    States |= PluginState.Paused;
    break;
```

一時停止ならループ間処理の予約が残る。したがって

- 割り込む時刻を選ぶ必要がない（ダンジョンを出た直後でよい）
- リテイナー処理・GC 納品は交換のあと続きから実行される
- 周回カウンタが 0 に戻らない（`Run` による再開の副作用が無い）
- AutoDuty 側の「宿屋へ戻る」等のループ間設定も失われない

一時停止・再開は IPC に無いため、`Svc.Commands.ProcessCommand("/ad pause")` /
`("/ad resume")` で送る。`ProcessCommand` の戻り値でコマンドの有無を判定でき、
未対応版なら従来の `Stop` 方式へ自動的に落とす。

ダンジョン退出時のタスク列で `Stage = Stage.Looping` が設定されるため、
一時停止中の `PreviousStage` は `Looping` になる。`Looping` は `Stage` セッタに
case が無く副作用が無いので、解除時にそのまま戻して問題ない。

### 一時停止を放置しない

一時停止は AutoDuty から見るとユーザーが止めたのと区別がつかない。
こちらの都合で止めたものは、成功・失敗・中断のいずれでも必ず解除する。
`ResumeAutoDutyOnFailure` が false でも解除する（止めたままは「元に戻す」ではない）。

## F-17: 自動交換は外部の自動化が動いているときだけにする

プリセットを有効にしただけで交換が始まると、手動で遊んでいる最中に
勝手にテレポートして交換を始めてしまう。

`RequireExternalAutomationRunning`（既定 true）を追加し、
AutoDuty か Artisan が動作しているときだけ監視から交換を開始する。
手動の「行って交換」はこの設定に関わらず実行できる。

判定は fail-closed。状態を取得できない場合は「動いていない」として扱い、
自動交換を始めない側へ倒す。

## F-18: 一時停止は「外部プラグインの調整」より先に行う

一時停止方式にしただけでは足りなかった。手順が

```
安全待機 → AutoRetainer の抑制（処理中なら待つ） → AutoDuty を一時停止 → 移動
```

の順だったため、AutoRetainer の処理待ちをしている間に AutoDuty が
ループ間処理を終えて次のコンテンツへ入ってしまい、安全待機へ戻された。
これを周回のたびに繰り返すので、**全周回が終わるまで交換にたどり着かない**。

一時停止はタスク列を保持するので、安全な瞬間が来たら真っ先に止めてよい。
順序を

```
安全待機 → AutoDuty を一時停止 → AutoRetainer の抑制 → 移動
```

に変更した。止めてしまえば以降は急ぐ必要がなく、
ベンチャー完了待ちなどでいくら待っても周回を取り逃がさない。

なお `SafetyGuard.IsSafeToStart` は `IsOccupied()` を見るため、
リテイナー画面や納品画面が開いている間は安全と判定されない。
結果として、ダンジョン退出直後の静かな時点で一時停止することになる。

## F-19: 一時停止方式は成立しない。周回の途中には割り込めない

F-16 で採った一時停止方式は、前提そのものが誤りだった。

「一時停止なら AutoDuty のタスク列が保持されるので、ループ間処理は失われない」
としていたが、**こちらが交換のためにエリアを移動した時点で崩れる**。

```csharp
// AutoDuty.cs ClientState_TerritoryChanged
767: if (this.Stage == Stage.Stopped) return;   // ← Paused は通過する
780: if (!States.HasFlag(PluginState.Looping) || ...Helper.State == Running...) return;
794: if (t != CurrentTerritoryContent.TerritoryType)
798:     TaskManager.Abort();                    // ← 保持していたはずの予約が全消去
799-822: ループ間処理を先頭から積み直す
```

ループ間処理の最中は `States` に `Looping` が立っており、静かな瞬間に一時停止した場合は
どのヘルパーも実行中ではないため 780 の早期 return も通過する。
その結果、街へテレポートした瞬間に `TaskManager.Abort()` が走る。

一時停止が Stop より優れているとした唯一の根拠が、実際の使い方では成立しない。

さらに、`/ad pause` は「停止」ではない。`Stage.Paused` が行うのは
`PreviousStage` の保存・vnav パス停止・Follow 解除・`SetStepMode(true)`・
`States |= Paused` の 5 つだけで、次のものは動き続ける。

- `Framework_Update` と `SchedulerHelper.ScheduleInvoker`（AutoDuty.cs:456-457）
- 全 ActiveHelper（`ActiveHelperBase.cs:112-113` が自前で `Framework.Update` を購読）。
  中断条件は Navigating / InDungeon / GotoHelper 実行中だけで、Paused を見ていない
- 特に QueueHelper は一時停止中でも DutyPop を承諾して次の周回に入場する

## F-20: 合流点は `Stage.Stopped` にする

`Stage.Stopped` は AutoDuty が唯一「完全に静止した」と保証する状態である。

```csharp
// StopAndResetALL (AutoDuty.cs:1919-)
States = PluginState.None;
TaskManager?.SetStepMode(false);
TaskManager?.Abort();
```

以後 `TerritoryChanged` は 767 で抜けるため、こちらが何をしても反応しない。

そして最終周のあと `LoopsCompleteActions()` の末尾で

```csharp
1252: States      &= ~PluginState.Looping;
1253: CurrentLoop =  0;
1254: TaskManager.Enqueue(() => SchedulerHelper.ScheduleAction("SetStageStopped", () => Stage = Stage.Stopped, 1));
```

となるので、**`IsStopped() == true` は「ループ間処理も終了処理も全部終わった」を意味する**。
時間ベースの当て推量（`AutoDutySettleWaitSeconds` 等）は全廃できる。

交換の頻度は AutoDuty 側の周回数で決まる。こまめに交換したい場合は
AutoDuty の周回数を小さく設定する。

`AutoDuty.Run(territory, loops, ...)` は `loops > 0` のときだけ
`Configuration.LoopTimes` を書き換えるため、再開時は必ず 0 を渡す（既存の実装どおり）。

## F-21: 抑制中に AutoDuty の AutoRetainerHelper が起動すると 10 分固まる

- `AutoRetainer.IsBusy` は抑制中は常に false（AutoRetainer `Helpers/Utils.cs`）
- `RetainersAvailable()` は OfflineData を見るだけなので抑制中も true のまま
- そのため AutoDuty は「Retainers available, restarting」分岐で起動試行を繰り返す
- 解除されるのはヘルパーのタイムアウトのみ（`600_000 + AutoRetainer_RemainingTime*60` ms）

したがって **AutoRetainer の抑制と AutoDuty の稼働を絶対に重ねない**。
`Stage.Stopped` を合流点にする方式では、抑制をかけるのは AutoDuty の停止後だけになるため
この条件は構造的に満たされる。

## F-22: AutoDuty の GC 納品は外部から呼べない

AutoDuty のコマンドは 12 個（config/cfg, start, stop, pause, resume, dataid,
queue, overlay, skipstep, movetoflag, ttfull, run）で、ヘルパーを直接呼ぶものは無い。
`ActiveHelper.Commands` はどのヘルパーも定義しておらず、IPC にも無い。

つまり `GCTurninHelper` は AutoDuty 自身のループ間キューからしか実行できない。

## F-23: 理想の流れは AutoDuty の設定 2 つで成立する

「ID クリア → リテイナー → GC 納品 → 交換 → 次の ID」を実現する方法。

`LoopTasks` の末尾は次のようになっている。

```csharp
// AutoDuty.cs LoopTasks 末尾
if (!queue)
{
    LoopsCompleteActions();
    return;
}
```

そして最終周の分岐（AutoDuty.cs:831-837）:

```csharp
if (this.Configuration.ExecuteBetweenLoopActionLastLoop)
    this.LoopTasks(false);          // ← ループ間処理を全部やってから LoopsCompleteActions
else
    this.LoopsCompleteActions();
```

つまり `ExecuteBetweenLoopActionLastLoop = true` にすると、最終周のあとに

```
ループ間処理（リテイナー・GC 納品・修理・精製・分解）
  → LoopsCompleteActions()
  → Stage.Stopped
```

の順で実行される。`LoopTimes = 1` にすれば毎周回がこれになる。

Auto Collector は `IsStopped` を合流点にしているので（F-20）、
そのまま「ループ間処理が全部終わったあと」に交換が始まる。**コード変更は不要。**

### 必要な AutoDuty 設定と既定値

| 設定 | 既定 | 必要 |
|---|---|---|
| `LoopTimes` | 1 | 1 |
| `ExecuteBetweenLoopActionLastLoop` | **false** | **true** |
| `EnableBetweenLoopActions` | true | true |
| `EnableAutoRetainer` | **false** | **true** |
| `AutoRetainer_RemainingTime` | **0** | **0 より大きい値** |
| `AutoGCTurnin` | false | true |
| `AutoExitDuty` | true | true |
| `TerminationMethodEnum` | Do_Nothing | Do_Nothing |

`RetainersAvailable()` は
`EnableAutoRetainer && 最短ベンチャー残り秒 < AutoRetainer_RemainingTime`
なので、`AutoRetainer_RemainingTime` が 0 のままだとリテイナーへ行かない。

`TerminationMethodEnum` は毎周回 `LoopsCompleteActions` を通るため要注意。
ログアウトやクライアント終了を設定していると、1 周ごとにそれが走る。

これらを状況タブの「AutoDuty の設定点検」で表示する。書き換えはしない。

## F-24: AutoDuty の GC 納品は AutoRetainer を呼んでいる

```csharp
// Helpers/GCTurninHelper.cs:151
AutoRetainer_IPCSubscriber.EnqueueGCInitiation();   // AutoRetainer.GC.EnqueueInitiation
```

したがって **AutoRetainer を抑制すると GC 納品も動かない**。
抑制は AutoDuty の停止後にしかかけない（F-20 の方式）ので、この構成では衝突しない。

## F-26: 周回数 1 の構成では、交換が起きない周回で AutoDuty が止まる

F-23 の構成（周回数 1 + Run on last Loop）では、交換のあとの再開処理が
AutoDuty を動かし直す。しかし閾値に達していない周回では交換が起きないため、
誰も再開させず 1 周で止まったままになる。

`AutoDutyKeeper` を追加し、AutoDuty が停止したら再開させる。
交換後の再開と同じ `Run(エリア, 0)` を使うので、周回数の設定は書き換えない。

### 再開先のエリア

停止したあとは現在地が街になっており、そこからは分からない。
周回中（`Player.IsInDuty` かつ AutoDuty 稼働中）に記録しておき、
設定へ保存してプラグインの再読み込みを跨いでも残す。
`ContentHasPath` が真のエリアだけを記録する。

### 手動停止との区別

ユーザーが AutoDuty を手で止めた場合も「停止」として観測されるため、
そのまま再開させると止めたいのに止まらない状態になる。

再開させたあとコンテンツへ入らないまま 20 秒以内に再び停止したら
「押し返された」と数え、2 回続いたら維持をやめてチャットで知らせる。
状況タブから維持を再開できる。

### 再開しない条件

- 交換の処理中（交換後の再開はそちらが行う）
- 結果が未確認の交換が残っている
- コンテンツ中・画面の読み込み中
- 停止から待ち時間（既定 5 秒）が経っていない — 終了処理の残りを踏まないため
- AutoRetainer が処理中 — 途中で AutoDuty を動かすと取り合いになる
- 一度も AutoDuty が動いているのを観測していない — 起動直後に勝手に周回を始めないため

## F-27: 自動停止と手動停止は、状態の変わり方で区別できる

`AutoDutyKeeper` が手動停止も「周回完了」と誤認して再開させていた。
AutoDuty の 2 つの停止経路には、外から観測できる確実な差がある。

### 周回完了（`LoopsCompleteActions`）

```csharp
// AutoDuty.cs:1252-1254
States      &= ~PluginState.Looping;                            // 即座
CurrentLoop =  0;
TaskManager.Enqueue(() => SchedulerHelper.ScheduleAction("SetStageStopped", () => Stage = Stage.Stopped, 1));
```

`Stage = Stopped` は **ループ間処理を積んだキューの最後**に予約される。
そのため `周回=false かつ 停止=false` の期間が必ず存在する。
実測では 19〜25 秒あった（ループ間処理の実行時間そのもの）。

```
10:42:43  AD(停止=False 周回=False)  ← ここから
10:43:40  AD(停止=True  周回=False)  ← ここまで 57 秒
```

さらに、この経路へ来るのは `TerritoryChanged` 経由なので必ずコンテンツの外。

### 手動停止（`/ad stop`・停止ボタン）

```csharp
(["stop"], "stops everything", _ => Plugin.Stage = Stage.Stopped),
```

`Stage` の setter が同期的に `StopAndResetALL()` を呼び、
`States = PluginState.None` と `Stage` が**同一フレームで**変わる。
中間状態は存在しない。コンテンツ中でも止められる。

### 判定

観測した停止が次のいずれかに当てはまれば手動と判断し、再開させない。

1. 停止した時点でコンテンツ中だった
   （`AutoExitDuty` が有効な場合のみ。無効だと最終周がコンテンツ内で停止するため）
2. 停止する前に `周回=false かつ 停止=false` を観測していない

手動と判断したら、次にユーザーが AutoDuty を動かすまで維持を止める。
ユーザーが再開させれば、そこからまた維持を始める。

残る曖昧なケースは「ループ間処理の最中に街で手動停止した場合」で、
このときは 1 の条件も 2 の条件も満たさない。
再開させたあとコンテンツへ入らないまま再び停止したら諦める従来の判定で拾う。

### ログ

停止の前後を後から追えるよう、AutoDuty の状態が変わったときに記録するようにした。
以前は交換の処理中しか状態を残しておらず、手動停止の瞬間がログに無かった。
