## F-1. トームストーンのスロット番号は「過去のショップ」まで巻き込む

### 何が起きるか

`SpecialShop` のコストは `CostType == 2` のとき `Tomestones` シートの**行番号**を指す。
そして `Tomestones` の行番号は固定で、中身がパッチごとに入れ替わる。

このため、**過去パッチのショップが「現在のトームストーンを要求している」ように見える**。

数理（`Tomestones` 行 2）で実測した結果:

| ShopId | PatchNumber | NPC 参照 | ショップ名 |
|---|---|---|---|
| 1770434 | 600 | **なし** | アラガントームストーン:経典の取引（ファイター） |
| 1770437 | 600 | **なし** | アラガントームストーン:天文の取引（ファイター） |
| 1770764 | 700 | **なし** | アラガントームストーン:美学の取引（ILv700ファイター装備） |
| 1770767 | 700 | **なし** | アラガントームストーン:天道の取引（ILv720ファイター装備） |
| **1770911** | **720** | **あり** | アラガントームストーン:数理の取引（ILv750ファイター装備） |
| **1770912** | **720** | **あり** | アラガントームストーン:数理の取引（ILv750ソーサラー装備） |
| **1770913** | **720** | **あり** | アラガントームストーン:数理の取引（ILv750武器） |
| **1770925** | **720** | **あり** | ファントムウェポン素材の取引 |
| **1770994** | — | **あり** | アラガントームストーン:数理の取引（その他） |
| **1770900** | 710 | **あり** | 強霊薬の取引 |

数理をコストとするショップは 18 件見つかるが、**現行で到達できるのは 6 件だけ**。
残り 12 件は 6.x / 7.0 当時に「行 2 のトームストーン」を要求していたショップで、いまは NPC から到達できない。

### 検証方法

対象 12 ショップの ID を、サブロウ以外の全シートの uint32 / int32 カラムに対して逆引きしたところ、
**参照が 1 件も見つからなかった**（`ENpcBase.ENpcData` / `FateShop` / `InclusionShop` を含む）。
ゲーム内から到達する手段が存在しない、いわゆる死んだ行である。

### 対応

**「NPC から到達できるショップだけを採用する」という現在の実装がそのまま正しい判定になる。**
死んだショップは NPC が付かないため、自然に除外される。特別なフィルタは不要。

ただし UI 上では「NPC 未解決」として件数を見せる。もし将来ここに現行ショップが紛れ込んだら、
それは解決経路の実装漏れを意味するサインになるため、黙って捨てずに表示する。

補助的な判定材料として `SpecialShop.Item[].PatchNumber` も使える（実測で死んだショップは 600 / 700、
現行は 710 / 720）。ただしパッチ番号が 0 の行も存在するため、単独の判定条件にはしない。

## F-2. NPC の座標は Level シートだけでは足りない

### 実測

| 取得元 | ユニーク NPC 数 |
|---|---|
| `Level`（`Type == 8`） | 24,210 |
| マップ配置ファイル `planevent.lgb` | 39,540 |
| **LGB にしか存在しない** | **16,441** |

MVP で必要な NPC の実例:

| NPC | ItemId | `Level` | LGB |
|---|---|---|---|
| ジルコン（数理装備） | 1049079 | ○ Solution Nine (-187.7, 0.7, -30.9) | ○ 同一座標 |
| エイレーネー（強霊薬） | 1049083 | **×** | ○ Solution Nine (-210.2, 0.9, -8.3) |
| **アーミナ（ファントムウェポン素材）** | 1053904 | **×** | ○ **Phantom Village (40.8, 0.0, 20.9)** |

**仕様書が主要ユースケースとして名指ししていた「ファントムウェポン関連の石」の交換 NPC は、`Level` シートからは座標を取得できない。** LGB を読まないと MVP の目的が達成できない。

`Level` と LGB の両方に存在するジルコンでは座標が完全に一致したため、LGB 側の値は信頼できる。

### コスト実測

計画（§6-Q6）では LGB 解析を「初期化コストが大きい」として Phase 2 送りにしていたが、これは誤りだった。

```
TerritoryType 1,290 件 → ユニーク Bg 589 件（Bg が同じエリアは配置ファイルを共有する）
589 個の planevent.lgb をすべて解析: 113 ms / 失敗 0 件
```

**113 ms で全エリアを解析できる。** 1 フレームで実行すると体感できるカクつきになるため、
フレームあたり 60 件ずつに分けて処理する（約 10 フレーム = 0.2 秒未満）。

### 対応

`NpcLocationService` を `Level` + LGB の統合索引に変更した。
`Level` を先に読み、LGB で不足を補う。同一エリア・同一座標（1 単位未満の差）の重複は排除する。

Lumina の API:

```csharp
Svc.Data.GetFile<LgbFile>($"bg/{bg[..bg.LastIndexOf('/')]}/planevent.lgb")
// layer.InstanceObjects → AssetType == LayerEntryType.EventNPC
// obj.Object as LayerCommon.ENPCInstanceObject → npc.ParentData.ParentData.BaseId
// obj.Transform.Translation
```

`ENPCInstanceObject` の `BaseId` は `ParentData.ParentData.BaseId` と 2 段ネストしている点に注意。

## F-3. ENpcBase の RowId は連番ではない（実装バグとして混入していた）

`ENpcBase` は 59,851 行だが、**RowId は 1000000 から始まる**。

```
Count       = 59851
先頭 RowId  = 1000000, 1000001, ...
TryGetRow(0)       → false
TryGetRow(1049079) → true
```

フレーム分割走査でカーソルを `0 .. Count` と回し、`TryGetRow(cursor)` で取得する実装を書いていたが、
これでは **1 件も取得できない**。しかも例外は出ず「交換候補 0 件」という静かな誤動作になる。

位置指定でのアクセスには `ExcelSheet<T>.GetRowAt(int rowIndex)` を使う。修正済み。

> 同種の間違いは他シートでも起こりうる。**フレーム分割走査を書くときは必ず `GetRowAt` を使う**こと。

## F-4. Lumina の構造体は既定値のプロパティに触ると例外になる

```csharp
// これは NullReferenceException を投げる
var reward = entry.ReceiveItems.FirstOrDefault(r => r.Item.RowId != 0);
if (reward.Item.RowId == 0) { ... }   // ← ここで落ちる
```

`FirstOrDefault` が返す `default(ReceiveItemsStruct)` は `ExcelPage` が null のため、
プロパティアクセスの時点で落ちる。**LINQ の `FirstOrDefault` + プロパティ参照を書かない。**
必ず `foreach` で取り出し、見つからなかった場合は ID を 0 のままにして判定する。

## F-5. CostType の意味（実データで確定）

`SpecialShop.UseCurrencyType` ではなく、エントリ単位の `ItemCosts[].CostType` で分岐する。

| CostType | `ItemCost.RowId` の意味 | 実データの件数 | 出現する RowId |
|---|---|---|---|
| 0 | 実 ItemId | 19,257 | すべて 8 以上 |
| 1 | 実 ItemId | 88 | すべて 8 以上 |
| **2** | **`Tomestones` シートの行番号** | 3,471 | 1 / 2 / 3 のみ |
| **3** | **特殊通貨バケット（スクリップ類）** | 2,422 | 2 / 4 / 6 / 7 のみ |

`UseCurrencyType` で分岐してはならない理由: `UseCurrencyType == 2` のショップが 463 件あり、
そこに詩学コストのエントリが含まれる。`UseCurrencyType` だけで判定するとギルやシャードへ誤解決する。

なお `CostType == 3` に出現するインデックスは 2 / 4 / 6 / 7 であり、**1 は出現しない**。
`special_currency_map.json` の index 1（詩学）はこの経路では使われていない。Phase 4 で再確認する。

## F-6. AtkValue の型は UInt に統一されていない（S4 実機）

`ShopExchangeCurrency` の実測値:

| 項目 | 位置 | 型 | 値 |
|---|---|---|---|
| AtkValues の総数 | — | — | 3,325 |
| NumEntries | 4 | UInt | 18 |
| CurrencyAmount | 86 | UInt | 594 |
| **CurrencyIcon** | 87 | **Int** | 65,122 |
| 1 件目 Cost | 456 | UInt | 20 |
| 1 件目 ItemId | 1066 | UInt | 49,226 |
| 1 件目 Index | 1310 | UInt | 0 |

**位置はすべて正しく、87 番だけが `Int` だった。**

ECommons の `AddonMaster` は `Addon->AtkValues[n].UInt` と型を確認せずに読む。`AtkValue` は共用体なので
`Int` の値でも同じ 4 バイトを `UInt` として読めてしまい、結果的に動作している。
一方 ECommons の `AtkReader` は型が `UInt` でなければ `InvalidCastException` を投げるため、こちらで止まった。

### 対応

`Int` と `UInt` の両方を整数として受け付ける。型を無視するのではなく、**受け付ける型を列挙し、
それ以外（文字列など）は従来どおり失敗として検出する**。`Int` が負値の場合も ID・個数としては使えないため弾く。

失敗時の扱いを重要度で分けた:

- `NumEntries` / `CurrencyAmount` が読めない → **中止**（交換前後の検証ができないため）
- `CurrencyIcon` が読めない → 続行（補助情報のため）
- 個別エントリの値が揃わない → そのエントリだけ除外し、件数を警告表示

## F-7. 同じアイテムが複数のショップに別の値段で載っている（S4 実機）

数理の「その他」交換で、画面のコストとゲームデータのコストが 12 件も食い違った。
原因は**私の照合ロジックのバグ**で、読み取り側は正しかった。

| アイテム | Shop 1770766（死） | Shop 1770770（死） | **Shop 1770994（現行）** | 画面 |
|---|---|---|---|---|
| マストドンの粗皮 | — | — | **20** | 20 |
| 新王国の研磨剤 | — | 20 | **10** | 10 |
| シュバラールのワニス | 20 | 10 | **10** | 10 |

照合用の辞書を `Results` 全体から `TryAdd` で組んでいたため、**先に見つかった死んだショップの定義が残り**、
現行ショップの値段と比較されて不一致になっていた。

### これが示す本質的な問題

**`ItemId` だけでは交換定義を一意に決められない。** 同じアイテムが複数のショップに、
別の値段で載っている。したがって「どのショップが開いているか」を確定させないと、
正しい値段と比較できない。

### 対応

1. `ExchangeResolver.LiveResults` を追加した。`Results` には原因調査用に死んだショップの定義も
   含まれるため、**値段の比較と交換の実行には必ず `LiveResults` を使う**。
2. `ShopService.IdentifyShop()` を追加した。読み取った **(ItemId, コスト) の組**が
   すべて含まれるショップを探して、開いているショップを特定する。
   完全一致が 1 件でなければ「特定できず」として交換しない。

`ShopMatchKind.CostMismatch` による安全停止は正しく機能していた。
実際、この食い違いは交換を撃つ前に検出され、赤字で「この状態では交換を実行してはいけません」と表示された。
**読み戻して照合する設計が意図どおり働いた事例。**

## F-8. ショップのタブは別々の SpecialShop 行（S4 実機）

ジルコンのショップには「武器 / 防具 / アクセサリ / その他」の 4 タブがあり、
`NumEntries` は**現在開いているタブの件数だけ**を返した（その他タブ = 18 件）。

数理の現行ショップ 4 件（1770911 ファイター / 1770912 ソーサラー / 1770913 武器 / 1770994 その他）が
そのままタブに対応していると見られる。

MVP はタブ切り替えを行わない方針のため、**目的アイテムが現在のタブに無ければ
`ExchangeItemNotFound` で安全停止する**。ファントムウェポン素材（アーミナ）は
ショップの登録が 4 件のみでタブ構成ではないため、MVP の主要ユースケースには影響しない。

### 未解決

Shop 1770994 のゲームデータ上のエントリは 29 件だが、画面には 18 件しか出ていない。
差の 11 件は開放条件などで非表示になっている可能性がある。
交換対象が非表示だった場合は `ItemNotFound` で安全に止まるため MVP では問題にならないが、
Phase 2 で原因を確認する。

## F-9. 交換 callback の実測値（S5 実装前）

ユーザーがジルコンのショップで手動で 1 個交換したときの `FireCallback` を記録した結果:

```
updateState=True   Fire(0, 5, 1, (なし))
```

- **値は 4 つ**。3 つではない。
- 記録側の表示規則は「`Int` 型なら数字のみ、`UInt` 型なら数字に `u` を付ける」実装なので、
  **`0` / `5` / `1` はすべて `AtkValueType.Int`**。`UInt` ではない。
- 4 つ目は `Type == 0` の空 `AtkValue`。
- `5` は画面から読み取った index（`AtkValues[1310 + i]`）と一致。`1` は個数。

### 参照実装との差分

ECommons の `AddonMaster.ShopExchangeCurrency.ShopItemInfo.Select` は次のように送っている:

```csharp
Callback.Fire(master.Base, true, 0, Index, amount);   // 3 値
```

`Index` は `uint` フィールドなので、`Callback.Fire` の変換規則（`case uint` → `AtkValueType.UInt`）により
**`UInt` 型で送られる**。実測した `Int` とは型が異なり、値の個数も 3 と 4 で違う。

### 対応方針

実測どおりに再現する。`Callback.Fire` は `case AtkValue rawValue` を持つため、
`Callback.ZeroAtkValue`（`Type = 0`）を 4 つ目として直接渡せる。

**`index` は必ず `int` にキャストする。`uint` のまま渡すと `UInt` 型になり、
ゲームが送っている `Int` と食い違う。**

3 値でも動作するかどうかはソースから判断できないため、確認できている 4 値の形で撃つ。

## F-10. 交換には確認ダイアログが必ず挟まる（S5 実装前・実測）

`CallbackRecorder` の `AddonFilter` を空にして全アドオンを記録し、手動で 1 個交換した結果（時系列順）:

| 時刻 | アドオン | callback | 意味 |
|---|---|---|---|
| 19:51:19 | **ShopExchangeCurrency** | `Fire(0, 5, 1, (なし))` | 交換コマンド |
| 19:51:19 | ItemDetail | `Fire(-1)` | ツールチップ。マウス移動に伴う付随的なもので交換とは無関係 |
| 19:51:20 | **SelectYesno** | **`Fire(0)`** | **確認ダイアログの Yes** |
| 19:51:21 | ItemDetail | `Fire(-1)` | 同上 |
| 19:53:08 | ScreenLog | `Fire(0, 0u)` | 約 2 分後。無関係 |

### 確定したこと

1. **確認ダイアログ（`SelectYesno`）は必ず出る。** 出ない前提の実装は成立しない。
   計画（`docs/02` §6-Q4）では「出るかどうか未確認」としていたが、出ることが確定した。
2. **`ShopExchangeCurrencyDialog`（数量入力）は出ない。** 1 個交換では登場しない。
3. **`SelectString` / `Talk` は交換の流れに絡まない。** 交換後もショップは開いたまま。
4. 交換コマンドから確認ダイアログまで **約 1 秒**かかる。同フレームで判定してはいけない。
5. `SelectYesno` の Yes は `Fire(0)`（1 値・Int）。

### 実装での扱い

ボタンをクリックする経路（`AddonMaster.SelectYesno.Yes()`）を使う。実測した `Fire(0)` は
ユーザーがボタンを押した結果として発生したものであり、ボタン経由なら同じ callback に行き着く。
callback を直接撃つとボタンの有効・無効状態を完全に無視することになるため採用しない。

ただし ECommons の `Yes()` には 2 つの落とし穴があるため、そのまま呼ばない。

```csharp
// SelectYesno.cs:37-49
public void Yes()
{
    if (!RespectDisabledButtons)          // ← 既定は false
    {
        if (Addon->YesButton != null && !Addon->YesButton->IsEnabled)
        {
            var flagsPtr = (ushort*)&Addon->YesButton->...NodeFlags;
            *flagsPtr ^= 1 << 5;          // ← 無効化された Yes を強制的に有効化する
        }
    }
    ClickButtonIfEnabled(Addon->YesButton);
}
```

- `RespectDisabledButtons` の既定 `false` は、**ゲームが押させないと決めたボタンを強制的に押す**。
  必ず `true` を設定する。
- `ClickButtonIfEnabled`（`!AddonMasterBase.cs:61-70`）は `button->IsEnabled` を
  **null チェックなしで**参照する。`YesButton` が null なら逆参照で落ちる。
  `RespectDisabledButtons` の値と無関係に起きるため、呼び出す前に自分で null / IsEnabled / IsVisible を確認する。

さらに、`GenericHelpers.TryGetAddonMaster<SelectYesno>` は**インデックス 1 のアドオンしか見ない**
（`AddonHelpers.cs:139-152`）。他プラグインや別要因のダイアログを取り違えるため、
インデックスを走査し、**本文に報酬アイテム名が含まれるもの**だけを対象にする。

## F-11. 確認ダイアログの本文に報酬アイテム名は含まれない（S5 実機）

最初の実装は「本文に報酬アイテム名が含まれること」を確認ダイアログの照合条件にしていたが、
実際の本文は次のとおりで、**報酬名を含まない**。

```
以下のアイテムを
アラガントームストーン:数理×20と交換します。
```

本文にあるのは**通貨名とコスト**だけで、報酬アイテム名（イヨラエキス）はアイコン横の別ノードにある。
このため自分が出したダイアログを認識できず、押さずに `ExchangeUnresolved` でタイムアウトした。

**これは安全側に倒れた失敗である。** 押せなかったときに再送する作りだったら、この時点で二重に購入していた。
`inFlight` ラッチと「`WaitOutcome` から `Armed` へ戻る辺を作らない」設計が意図どおり機能した。

### 対応

照合条件を次のように変更した。

- **必須**: 本文に**通貨名**と**コストの数値**の両方が含まれること
- **追加の裏付け**: アドオン内の全テキストから報酬名を探し、見つかれば確認済みとする。
  見つからない場合は、実際に表示されていた文字列を `AnomalyLog` に記録する

テキストの収集はノード ID を決め打ちせず、`AtkValue` の文字列と `UldManager.NodeList` の

## F-13. 会話メニューの選択肢は SpecialShop.Name そのもの（S6 実機）

ジルコンに話しかけると、次の選択肢が出た。

```
アラガントームストーン:数理の取引（ILv750武器）          ← Shop 1770913
アラガントームストーン:数理の取引（ILv750ファイター装備）  ← Shop 1770911
アラガントームストーン:数理の取引（ILv750ソーサラー装備）  ← Shop 1770912
アラガントームストーン:数理の取引（その他）              ← Shop 1770994
アラガントームストーン:記憶の取引（ILv780武器）
アラガントームストーン:記憶の取引（ILv780ファイター装備）
アラガントームストーン:記憶の取引（ILv780ソーサラー装備）
キャンセル
```

**選択肢の文字列は `SpecialShop.Name` と完全に一致する。** NPC が `ENpcData` に複数のショップを
直接持っている場合、ゲームがショップ名で選択肢を組み立てている。

### F-8 の訂正

F-8 では「ショップのタブは別々の SpecialShop 行」と記録したが、より正確には
**この選択肢がショップを切り替えている**。ショップ画面上部のタブに見えていたものは、
実際には選択したショップに応じた別の画面である。

そのため「目的のアイテムが別タブにあると届かない」という懸念は解消される。
**ショップ名で正しいショップを選べば、目的のエントリが含まれる画面が開く。**

### 対応

`ExchangeDefinition` に `ShopName`（`SpecialShop.Name`）を追加し、
会話メニュー通過時のヒント候補を **ShopName → MenuHint** の順で試すようにした。

メニューが開いている限り毎フレーム処理へ入るため、候補を順に試すだけで
多段メニュー（話題を選んでからショップ名の一覧が出る形）も通過できる。

当初の実装は `TopicSelect` / `CustomTalk` 由来のヒントしか持たせておらず、
`Direct` 経路ではヒントが空だったため「どれを選ぶべきか分かりません」で停止していた。
