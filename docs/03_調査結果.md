
## F-30 リムサとグリダニアの交換窓口が候補に出ない

### 症状

ロネークの乳（ItemId 49231・橙貨 15）の交換窓口一覧に、リムサ・ロミンサが出ない。

### 調べ方

Dalamud 同梱の Lumina でゲームデータを直接読み、
この品を出す SpecialShop に到達できる NPC を全て洗い出した。

```
出している SpecialShop: 1770783（1 件のみ）
到達できる InclusionShop: 3801094 / 3801096 / 3801097 / 3801099 / 3801101 / 3801103
この品を扱う NPC: 18 体
```

18 体のうち 6 体が Level シートに座標を持っていなかった。
その 6 体を配置ファイルから探した結果:

| ENpc | 場所 | 配置ファイル |
|---|---|---|
| 1003077 | グリダニア：旧市街 | **planner.lgb** |
| 1003633 | リムサ・ロミンサ：下甲板層 | **planner.lgb** |
| 1019458 | ラールガーズリーチ | planevent.lgb |
| 1027541 | ユールモア | planevent.lgb |
| 1037307 | ラザハン | planevent.lgb |
| 1049085 | ソリューション・ナイン | planevent.lgb |

### 原因

`NpcLocationService.LayerFileNames` が `planevent.lgb` だけだった。
リムサとグリダニアの窓口は `planner.lgb` にしか置かれていないため座標が取れない。

座標の無い NPC は移動先を決められないので、
`ExchangeResolver.Resolve` と候補一覧の両方が `HasLocation` で弾いていた。
弾いた旨はどこにも出ないため、**無言で消えていた**。

コメントには「planevent に無い NPC が planner にいることがある。
片方しか読まないと、その NPC が無言で候補から落ちる」と既に書かれていたが、
配列が 1 つのままだった。

### 対処

`LayerFileNames` に `planner.lgb` を足した。

### 教訓

**候補から外すときは、外した理由が見える形にすべき。**
今回は「出ない」以外の手がかりが無く、ゲームデータを直接読むまで原因が分からなかった。

## F-31 NPC の手前で 5 秒ほど棒立ちになる

### 症状

スクリップ取引窓口の少し手前で停止し、5 秒ほど何もせず立ち尽くす。
放置すると再び動き出して NPC へ近寄り、交換を完了する。

### 原因

`NavigationService.Reissue` が `vnavmesh.TryStop()` を呼んでから
経路を出し直していた。

NPC が視界に入ると、配置ファイル由来の座標と実際の位置が 3 ヤルム以上
ずれている場合に経路を引き直す作りになっている。その引き直しで止めていた。

vnavmesh の実装（`AsyncMoveRequest.cs`）を読むと、止める必要はない。

```csharp
public bool MoveTo(Vector3 dest, bool fly, float range = 0)
{
    if (_pendingTask != null) { ... return false; }
    _pendingTask = _manager.QueryPath(...);   // 探索を積むだけ
    return true;
}

public void Update()
{
    if (_pendingTask != null && _pendingTask.IsCompleted)
        _follow.Move(_pendingTask.Result, ...);   // 完了時に初めて差し替え
}
```

`MoveTo` は経路探索を積むだけで、`_follow` の経路には触らない。
差し替わるのは探索が終わってから。**探索中も元の経路を歩き続ける。**

こちらで止めていたため、探索が終わるまでの数秒が棒立ちになっていた。

### 対処

`Reissue` から `TryStop()` を外した。
元の目的地へ歩きながら、探索が終わった時点で新しい経路へ移る。

あわせて、引き直しに失敗したときに移動が失敗扱いになる穴を塞いだ。
`BeginMove` は入口で `moveIssued` を倒すため、`MoveTo` が false を返すと
移動していない状態になり、`Tick` が `Failed` を返して交換ごと中止になっていた。
実際には元の経路を歩いているので、失敗時は元の状態へ戻す。

### 教訓

**外部プラグインの非同期 API は、止めてから出し直す必要があるとは限らない。**
実装を読めば、止めない方が滑らかに繋がる作りになっていた。

## 未対応 有効化の直後に 7 秒ほど固まる

### 症状

プラグインを無効化 → 設定を保存 → 有効化 すると、
FF14 が 7 秒ほど固まってから動き出す。

優先度は低いため後回し。ここに残しておく。

### 心当たり

有効化の直後に NPC 配置の索引を作っている。

```csharp
public bool TickBuild(int lgbBudgetPerFrame = 60)
```

1 フレームあたり 60 エリア分の配置ファイルを読む。
**F-30 で `planner.lgb` を足したため、1 フレームで読む数が倍になった。**
リムサとグリダニアの窓口を出すために必要な変更だが、
その負荷がこの固まる時間に乗っている可能性が高い。

`ScanLevelSheet` と `PrepareBgList` を 1 フレームで済ませている点も見る価値がある。

### 対応案

| 案 | 内容 |
|---|---|
| 予算を下げる | 60 → 20 程度。完成は遅くなるが固まらない |
| **索引を保存する** | 初回だけ作り、次回からファイルから読む |
| 遅らせる | 必要になるまで作らない |

索引の保存が本命。ゲームが更新されるまで中身は変わらない。
