
## F-30 リムサとグリダニアの交換窓口が候補に出ない

### 症状

ロネークの乳（ItemId 49231・橙貨 15）の交換窓口一覧に、リムサ・ロミンサが出ない。

### 調べ方

Dalamud 同梱の Lumina でゲームデータを直接読み、
この品を出す SpecialShop に到達できる NPC を全て洗い出した。

```
出している SpecialShop: 1770783（1 件のみ）
到達できる InclusionShop: 3801094 / 3801096 / 3801097 / 3801099 / 3801101 / 3801103
この品を扱う NPC: 18 体
```

18 体のうち 6 体が Level シートに座標を持っていなかった。
その 6 体を配置ファイルから探した結果:

| ENpc | 場所 | 配置ファイル |
|---|---|---|
| 1003077 | グリダニア：旧市街 | **planner.lgb** |
| 1003633 | リムサ・ロミンサ：下甲板層 | **planner.lgb** |
| 1019458 | ラールガーズリーチ | planevent.lgb |
| 1027541 | ユールモア | planevent.lgb |
| 1037307 | ラザハン | planevent.lgb |
| 1049085 | ソリューション・ナイン | planevent.lgb |

### 原因

`NpcLocationService.LayerFileNames` が `planevent.lgb` だけだった。
リムサとグリダニアの窓口は `planner.lgb` にしか置かれていないため座標が取れない。

`ExchangeResolver.Resolve` と候補一覧の両方が `HasLocation` で弾いていた。
弾いた旨はどこにも出ないため、**無言で消えていた**。

コメントには「planevent に無い NPC が planner にいることがある。
片方しか読まないと、その NPC が無言で候補から落ちる」と既に書かれていたが、
配列が 1 つのままだった。

### 対処

`LayerFileNames` に `planner.lgb` を足した。

### 教訓

**候補から外すときは、外した理由が見える形にすべき。**
今回は「出ない」以外の手がかりが無く、ゲームデータを直接読むまで原因が分からなかった。

## F-31 NPC の手前で 5 秒ほど棒立ちになる

### 症状

スクリップ取引窓口の少し手前で停止し、5 秒ほど何もせず立ち尽くす。
放置すると再び動き出して NPC へ近寄り、交換を完了する。

### 原因

`NavigationService.Reissue` が `vnavmesh.TryStop()` を呼んでから
経路を出し直していた。

NPC が視界に入ると、配置ファイル由来の座標と実際の位置が 3 ヤルム以上
ずれている場合に経路を引き直す作りになっている。その引き直しで止めていた。

vnavmesh の実装（`AsyncMoveRequest.cs`）を読むと、止める必要はない。

```csharp
public bool MoveTo(Vector3 dest, bool fly, float range = 0)
{
    if (_pendingTask != null) { ... return false; }
    _pendingTask = _manager.QueryPath(...);   // 探索を積むだけ
    return true;
}

public void Update()
{
    if (_pendingTask != null && _pendingTask.IsCompleted)
        _follow.Move(_pendingTask.Result, ...);   // 完了時に初めて差し替え
}
```

`MoveTo` は経路探索を積むだけで、`_follow` の経路には触らない。
差し替わるのは探索が終わってから。**探索中も元の経路を歩き続ける。**

こちらで止めていたため、探索が終わるまでの数秒が棒立ちになっていた。

### 対処

`Reissue` から `TryStop()` を外した。
元の目的地へ歩きながら、探索が終わった時点で新しい経路へ移る。

あわせて、引き直しに失敗したときに移動が失敗扱いになる穴を塞いだ。
`BeginMove` は入口で `moveIssued` を倒すため、`MoveTo` が false を返すと
移動していない状態になり、`Tick` が `Failed` を返して交換ごと中止になっていた。
実際には元の経路を歩いているので、失敗時は元の状態へ戻す。

### 教訓

**外部プラグインの非同期 API は、止めてから出し直す必要があるとは限らない。**
実装を読めば、止めない方が滑らかに繋がる作りになっていた。

### 症状

## F-32 NPC の手前で 15 秒ちょうど棒立ちになる

### 症状

納品窓口の少し手前で 15 秒ほど停止。放置すると動き出し、
NPC へ最接近して即座に納品を始める。

### 原因

`NavigationService` のスタック判定。

```csharp
private static readonly TimeSpan StuckWindow = TimeSpan.FromSeconds(15);
```

到着判定は `idle && distance <= range + 2f`。
vnavmesh が走り終わっても、目的地まで 5 ヤルムを超えて残っていると到着にならない。

**この状態から放置しても vnavmesh は二度と動かない。**
経路は完了しており、次の指示を待っているだけ。
15 秒後にスタック判定が経路を引き直して、ようやく動き出していた。

報告された 15 秒は `StuckWindow` の値そのもの。

### なぜ届かないのか

納品窓口はカウンターの内側に立っている。
その座標はナビメッシュの外にあるため、vnavmesh は近づけるところまで行って終わる。
**目的地に届かないこと自体は異常ではない。**

### 対処

`MoveStatus.ShortOfTarget` を足した。
走り終わったのに届いていない状態はその場で分かるので、15 秒待たない。

届かなくても話しかけられる距離には入っていることが多い。
そこで失敗にはせず、話しかける段階へ進める。
話しかけられなければ、そちらが近づき直しを試み、それでも駄目なら失敗する。

**距離ではなく「話しかけられるか」で判断する。**

## F-34 エーテライトの無いエリアへ行けない（ウルダハ）

### 症状

ウルダハの納品窓口へ「窓口へ移動してまとめて納品する」を押しても無反応。

手動でウルダハへ飛んでもナル回廊なので、判定は同じ。

**さらに、失敗がログにしか出ないため無反応に見えた。**

```
group 2 の親 = Aetheryte 2（グリダニア：新市街）
  └ Aetheryte 26〜30（グリダニア：旧市街）
```

親へテレポートしてから `Lifestream.AethernetTeleportById` で網を使う。
`AethernetTransfer` 段階を足した。


`TickSelectMenu` は選択に成功すると即 return する。
選んでも画面が進まない場合、次のフレームでも同じ選択肢が一致するため、
同じものを延々と選び直す。メニューは開いたままなので
「閉じたらやり直す」側の上限には掛からない。

道具強化の窓口のように、選択肢の先がさらに会話メニューだったり、
条件を満たしておらず元の一覧へ戻される場合にこうなる。

### 対処（続き）

選択そのものに上限を設けた。

- 同じ選択肢を続けて 3 回選んだら中止
- 1 回の移動で合計 8 回選んだら中止（多段のメニューがあるため 1 回では足りない）

中止時に**実際の選択肢を並べて出す**。
何を選ぶべきだったのかが分かるようにする。

### F-35 続き 2 — 抜けられなかった本当の理由

利用者に画面写真を撮っていただき、デニスの会話メニューが判明した。

```

スカイスチールツール第3段階への改良   → アイテム交換
スカイスチールツールの購入            → ショップ（ギル 80,000）
アイテムの購入                        → ショップ（ダークマター等）
話す
キャンセル
```

**探していた「改良用部材の交換：クラフター」がどこにもない。**
CollectablesShop 3866625 は、この会話メニューからは辿り着けない。

そして記録の `Fire(5)` は**利用者が押したキャンセル**だった（2 秒間隔＝手動操作）。
プラグインが撃っていたのではない。

流れはこうなっていた。

```
話しかける → メニューが出る → 候補が一致しない
  → 30 秒の締切まで待ち続ける
    → 人がキャンセルを押す → メニューが閉じる
      → 話しかけ直す → 最初へ戻る
```

**一致しないと分かった時点で止めるべきだった。**
選択肢が変わらないなら、待っても一致しない。

### 対処（続き 2）

- 選択肢の並びが 2 秒変わらないまま一致しなければ、その場で失敗させる
- 人がメニューを閉じたら 1 度だけやり直し、それでも駄目なら諦める

一覧には残すが、辿り着けない場合は数秒で理由を出して止まる。

1 件で数秒かかることがあるため、時間で区切っても 1 フレームを止めてしまう。

**索引そのものは Framework スレッドからしか触らない。**

保存の形式版を 2 に上げた。1 で作られたものは planevent しか
入っていないため作り直す。

2 回目以降の起動は保存済みを読むだけなので、背景走査も起きない。

### F-30 再対応の失敗 — 背景スレッドでも駄目だった

背景スレッドで planner.lgb を読む案を実装したところ、

まだ位置を知らない NPC があれば記録する。

## F-36 「いま 1 回だけ交換する」が 1 回目の押下で動かない

### 症状

状況タブの「いま 1 回だけ交換する」を 1 回押しても無反応。

## F-37 作り終えた収集品が 0 個と数えられ、「素材が足りない」と誤って止まる

### 症状

2026-09-13、`docs/11_製作計画.md` の手順で収集用のタコス・カルネ・アサーダを 12 個作らせた。

```

19:00:32  収集用のタコス・カルネ・アサーダ の製作が始まりました
```

```csharp
var hq = manager->GetInventoryItemCount(itemId, true, includeEquipped, includeArmory);
```

**収集品はこの方法では数えられない。** 作り終えた時点でも 0 が返る。

`CurrencyService.TryGetBagCount` を足し、鞄の枠（`Inventory1..4`）を直接見て数える。
`GetBaseItemId()` で照合するため、HQ も収集品も同じ品として合算される。

```
所持数の数え方が食い違います（枠を数えて 12 個 / 従来の方法で 0 個）
```

通貨は収集品ではなく、装備やアーマリーも見る必要があるため。

作る物の目標数が `plan.Crafts` そのままだった。
**すでに持っているぶんが乗っていない。** 中間素材の側は
`Held + 回数 × 1 回あたりの数` で正しく求めていたのに、作る物だけ抜けていた。

### 症状

```csharp
// 話しかけられる距離はものによって違う。
// 広めに取り、実際に届くかはゲームの応答で判断する。
if (Vector3.Distance(obj.Position, Player.Position) <= 10f)
```

- 話しかける前に距離を確かめる。3.5 より遠ければ歩き直す

- 終わるときは自分が始めた移動だけを止める
- **やり直す見込みがあるうちはスクリップを使わない。**

## F-39 「未設定」のはずのジョブが「木工」と表示される

### 症状

```csharp
var current = jobs.FirstOrDefault(x => x.CraftType == preset.CraftJob);  // 0 → 木工
```

`int` にして **負を未設定**とする。0 は木工として正しく扱う。

## F-40 素材がそろっているのに「足りません」で止まる（中間素材）

### 症状

2026-09-14。収集用のタコス・カルネ・アサーダを 67 個作る計画で、
リテイナーから次を取り出し終えていた。

```
ロネークの肩肉 134 / 黒麦粉 1 / 黒麦 270 / ホワイトペッパー 67 / ヤースラニガーリック 134
```

黒麦 270 個は黒麦粉 135 個ぶん（1 回 6 個使って 3 個できる × 45 回）。
黒麦粉さえ作れば 67 個作れる状態だったが、画面には次が出て止まった。

```
止まっています: リテイナーから取り出しても足りませんでした（黒麦粉 があと 133）
（いま持っている素材では 1 個も作れません）
```

### 原因

**「足りない」と「作れない」を同じものとして扱っていた。**

```csharp
var shortfalls = plan.Materials.Where(x => x.Shortfall > 0).ToList();
```

黒麦粉は `IsIntermediate = true` で、その素材（黒麦）は足りている。
`CraftRunner.BuildSteps` は**中間素材から先に作る**ようにできているため、
そのまま渡せば黒麦粉 45 回 → タコス 67 回と進めたはずだった。

さらに `BuildPlan(requireMaterials: true)` も中間素材を一緒に数えていたため、
作れる個数を 0 になるまで下げていた。

### 対処

`PlanMaterial.CanCoverFromBag()` を足し、判定を 1 か所にまとめた。

| 状態 | 用意できるか |
|---|---|
| 足りている | ○ |
| 足りないが、自分で作れて、その素材が鞄にある | ○（先に作る） |
| 足りず、作れない／素材も足りない | × |

`GoalRunner` は「取り出しが要るもの（`shortfalls`）」と
「製作を妨げるもの（`blocking`）」を分けて持つ。

- リテイナーへ行くかどうか、止まるかどうかは `blocking` で決める
- 取り出しを頼む中身は `shortfalls`（完成品を先に探し、無ければ素材へ切り替える）

先に作る素材がある場合は記録に残す。「足りないのに進んだ」ように見せない。

```
先に作る素材: 黒麦粉×133
```

## F-41 クリスタルがリテイナーから取り出せない

### 症状

2026-09-14。ウォータークリスタルを全部リテイナーに預けた状態でプリセットを有効にすると、
必要数は正しく出る（「ウォータークリスタル があと 536」）のに 1 個も取り出せず、
「リテイナーから取り出しても足りませんでした」で止まる。

### 原因

取り出しのメニューをこう選んでいた。

```csharp
var useAll = take >= available;
var index = useAll ? indexAll : indexQuantity;

if (index < 0)
{
    failure = "「個数を指定して取る」が見つかりません";
    return false;   // ← ここで諦めていた
}
```

**クリスタルには「リテイナーから受け取る（個数指定）」が出ない。**
必要数（536）より持っている数のほうが多いため個数指定を選ぼうとし、
メニューに無いので諦めて次の相手へ進んでいた。

Artisan の実装が同じ分岐を持っている。

```csharp
// Artisan/Tasks/TaskSelectRetainer.cs  OpenItemContextMenu
if (item->Quantity == 1 || item->ItemId <= 19)
{
    Callback.Fire(contextMenu, true, 0, indexOfRetrieveAll, 0, 0, 0);
}
else
{
    Callback.Fire(contextMenu, true, 0, indexOfRetrieveQuantity, 0, 0, 0);
}
```

`ItemId <= 19` はシャード・クリスタル・クラスター。
**これらは「すべて取る」しか使えない。**

### 対処

- `RestockRequest.RetrieveAll` を足し、クリスタルには「すべて取る」を使う。
  判定は品目の分類（`PlanMaterial.IsCrystal`）から渡す。番号は埋め込まない
- **望んだほうが無ければ、もう一方へ倒す。** 探して見つからないからと諦めると、
  目の前にあるのに取り出せずに次の相手へ進んでしまう
- 個数の入力欄が出るかどうかは、実際にどちらを選んだかで決める
- 品を探すとき、入れ物が読み込み済みかどうかで飛ばさない。
  クリスタルの入れ物がそう報告しないことがある。Artisan もここは見ていない

要るぶんより多く受け取ることになるが、クリスタルは鞄の枠を使わないため害がない。

## F-42 取り出し中にサブメニューが数秒ちらつく

### 症状

2026-09-14。リテイナーからの自動取り出し中、マウスの位置に
アイテムを右クリックしたときのメニューが突然出て、3 秒ほどで消える。
1 回の取り出しで 4〜5 回起きた。

### 原因

メニューを**開いた同じフレームで探していた**。

```csharp
context->OpenForItemSlot(inventory, slot, 0, retainerAgent->GetAddonId());

if (!TryGetAddonByName<AtkUnitBase>("ContextMenu", out var contextMenu) ||
    !IsAddonReady(contextMenu))
{
    failure = "メニューが出ませんでした";
    return false;      // ← 諦めて次の品へ
}
```

アドオンは撃った次のフレーム以降に出る。同じフレームでは必ず見つからない。
そのため**毎回ここで諦め**、1 テンポ遅れて出たメニューは誰にも閉じられずに残った。
数秒後に消えていたのは、次の操作でリテイナーの画面が切り替わったため。

**これは見た目だけの問題ではない。**
諦めた品はそのリテイナーでは飛ばされるので、**持っているのに取り出せていなかった**。

Artisan は同じ書き方だが、失敗したら関数ごと呼び直す仕組みのうえで動いている。
2 回目の呼び出し時には 1 回目に開いたメニューが出ているため結果的に通る。
こちらは 1 回の失敗で品を飛ばすため、通らなかった。

### 対処

開く段と選ぶ段を分けた（`RestockStep.OpenContextMenu` を新設）。

```
Withdraw       品を見つける → 開く対象を控えて次の段へ
OpenContextMenu  1 度だけ開く操作を撃つ
                 → 出たら「受け取る」を選ぶ
                 → 出なければ待つ（15 秒）
                 → それでも出なければ閉じて諦める
```

**開いたら必ず片づける。** 選べずに諦めるときも `Close(true)` を通す。
終わるときにも開きかけを閉じる。

**自分で開く前に、出ているメニューへ触らない。**
利用者が右クリックで開いたものに撃つと、意図しない操作になる。
