
## F-30 リムサとグリダニアの交換窓口が候補に出ない

### 症状

ロネークの乳（ItemId 49231・橙貨 15）の交換窓口一覧に、リムサ・ロミンサが出ない。

### 調べ方

Dalamud 同梱の Lumina でゲームデータを直接読み、
この品を出す SpecialShop に到達できる NPC を全て洗い出した。

```
出している SpecialShop: 1770783（1 件のみ）
到達できる InclusionShop: 3801094 / 3801096 / 3801097 / 3801099 / 3801101 / 3801103
この品を扱う NPC: 18 体
```

18 体のうち 6 体が Level シートに座標を持っていなかった。
その 6 体を配置ファイルから探した結果:

| ENpc | 場所 | 配置ファイル |
|---|---|---|
| 1003077 | グリダニア：旧市街 | **planner.lgb** |
| 1003633 | リムサ・ロミンサ：下甲板層 | **planner.lgb** |

| 1037307 | ラザハン | planevent.lgb |
| 1049085 | ソリューション・ナイン | planevent.lgb |

リムサとグリダニアの窓口は `planner.lgb` にしか置かれていないため座標が取れない。

弾いた旨はどこにも出ないため、**無言で消えていた**。

片方しか読まないと、その NPC が無言で候補から落ちる」と既に書かれていたが、
配列が 1 つのままだった。

### 対処

`LayerFileNames` に `planner.lgb` を足した。

### 教訓

**候補から外すときは、外した理由が見える形にすべき。**
今回は「出ない」以外の手がかりが無く、ゲームデータを直接読むまで原因が分からなかった。

## F-31 NPC の手前で 5 秒ほど棒立ちになる

### 症状

スクリップ取引窓口の少し手前で停止し、5 秒ほど何もせず立ち尽くす。
放置すると再び動き出して NPC へ近寄り、交換を完了する。

### 原因

`NavigationService.Reissue` が `vnavmesh.TryStop()` を呼んでから
経路を出し直していた。

NPC が視界に入ると、配置ファイル由来の座標と実際の位置が 3 ヤルム以上
ずれている場合に経路を引き直す作りになっている。その引き直しで止めていた。

vnavmesh の実装（`AsyncMoveRequest.cs`）を読むと、止める必要はない。

```csharp
public bool MoveTo(Vector3 dest, bool fly, float range = 0)
{
    if (_pendingTask != null) { ... return false; }
    _pendingTask = _manager.QueryPath(...);   // 探索を積むだけ
    return true;
}

public void Update()
{
    if (_pendingTask != null && _pendingTask.IsCompleted)
        _follow.Move(_pendingTask.Result, ...);   // 完了時に初めて差し替え
}
```

`MoveTo` は経路探索を積むだけで、`_follow` の経路には触らない。
差し替わるのは探索が終わってから。**探索中も元の経路を歩き続ける。**

こちらで止めていたため、探索が終わるまでの数秒が棒立ちになっていた。

### 対処

`Reissue` から `TryStop()` を外した。
元の目的地へ歩きながら、探索が終わった時点で新しい経路へ移る。

あわせて、引き直しに失敗したときに移動が失敗扱いになる穴を塞いだ。
`BeginMove` は入口で `moveIssued` を倒すため、`MoveTo` が false を返すと
移動していない状態になり、`Tick` が `Failed` を返して交換ごと中止になっていた。
実際には元の経路を歩いているので、失敗時は元の状態へ戻す。

### 教訓

**外部プラグインの非同期 API は、止めてから出し直す必要があるとは限らない。**
実装を読めば、止めない方が滑らかに繋がる作りになっていた。

## F-32 NPC の手前で 15 秒ちょうど棒立ちになる

### 症状

納品窓口の少し手前で 15 秒ほど停止。放置すると動き出し、
NPC へ最接近して即座に納品を始める。

### 原因

`NavigationService` のスタック判定。

```csharp
private static readonly TimeSpan StuckWindow = TimeSpan.FromSeconds(15);
```

到着判定は `idle && distance <= range + 2f`。
vnavmesh が走り終わっても、目的地まで 5 ヤルムを超えて残っていると到着にならない。

**この状態から放置しても vnavmesh は二度と動かない。**
経路は完了しており、次の指示を待っているだけ。
15 秒後にスタック判定が経路を引き直して、ようやく動き出していた。

報告された 15 秒は `StuckWindow` の値そのもの。

### なぜ届かないのか

納品窓口はカウンターの内側に立っている。
その座標はナビメッシュの外にあるため、vnavmesh は近づけるところまで行って終わる。
**目的地に届かないこと自体は異常ではない。**

### 対処

`MoveStatus.ShortOfTarget` を足した。
走り終わったのに届いていない状態はその場で分かるので、15 秒待たない。

届かなくても話しかけられる距離には入っていることが多い。
そこで失敗にはせず、話しかける段階へ進める。
話しかけられなければ、そちらが近づき直しを試み、それでも駄目なら失敗する。

**距離ではなく「話しかけられるか」で判断する。**

## F-34 エーテライトの無いエリアへ行けない（ウルダハ）

ウルダハの納品窓口へ「窓口へ移動してまとめて納品する」を押しても無反応。

group 2 の親 = Aetheryte 2（グリダニア：新市街）
  └ Aetheryte 26〜30（グリダニア：旧市街）

親へテレポートしてから `Lifestream.AethernetTeleportById` で網を使う。
`AethernetTransfer` 段階を足した。

`TickSelectMenu` は選択に成功すると即 return する。

同じものを延々と選び直す。メニューは開いたままなので

道具強化の窓口のように、選択肢の先がさらに会話メニューだったり、
条件を満たしておらず元の一覧へ戻される場合にこうなる。

### 対処（続き）

選択そのものに上限を設けた。

- 同じ選択肢を続けて 3 回選んだら中止
- 1 回の移動で合計 8 回選んだら中止（多段のメニューがあるため 1 回では足りない）

中止時に**実際の選択肢を並べて出す**。
何を選ぶべきだったのかが分かるようにする。

### F-35 続き 2 — 抜けられなかった本当の理由

利用者に画面写真を撮っていただき、デニスの会話メニューが判明した。

```

スカイスチールツール第3段階への改良   → アイテム交換
スカイスチールツールの購入            → ショップ（ギル 80,000）

話す

```

**探していた「改良用部材の交換：クラフター」がどこにもない。**
CollectablesShop 3866625 は、この会話メニューからは辿り着けない。

そして記録の `Fire(5)` は**利用者が押したキャンセル**だった（2 秒間隔＝手動操作）。
プラグインが撃っていたのではない。

**一致しないと分かった時点で止めるべきだった。**

入っていないため作り直す。

2 回目以降の起動は保存済みを読むだけなので、背景走査も起きない。

## F-36 「いま 1 回だけ交換する」が 1 回目の押下で動かない

### 症状

状況タブの「いま 1 回だけ交換する」を 1 回押しても無反応。

## F-37 作り終えた収集品が 0 個と数えられ、「素材が足りない」と誤って止まる

### 症状

19:00:32  収集用のタコス・カルネ・アサーダ の製作が始まりました

## F-42 取り出し中にサブメニューが数秒ちらつく

### 症状

2026-09-14。リテイナーからの自動取り出し中、マウスの位置に
アイテムを右クリックしたときのメニューが突然出て、3 秒ほどで消える。
1 回の取り出しで 4〜5 回起きた。

### 原因

メニューを**開いた同じフレームで探していた**。

```csharp
context->OpenForItemSlot(inventory, slot, 0, retainerAgent->GetAddonId());

if (!TryGetAddonByName<AtkUnitBase>("ContextMenu", out var contextMenu) ||
    !IsAddonReady(contextMenu))
{
    failure = "メニューが出ませんでした";
    return false;      // ← 諦めて次の品へ
}
```

アドオンは撃った次のフレーム以降に出る。同じフレームでは必ず見つからない。
そのため**毎回ここで諦め**、1 テンポ遅れて出たメニューは誰にも閉じられずに残った。
数秒後に消えていたのは、次の操作でリテイナーの画面が切り替わったため。

**これは見た目だけの問題ではない。**
諦めた品はそのリテイナーでは飛ばされるので、**持っているのに取り出せていなかった**。

Artisan は同じ書き方だが、失敗したら関数ごと呼び直す仕組みのうえで動いている。
2 回目の呼び出し時には 1 回目に開いたメニューが出ているため結果的に通る。

```

OpenContextMenu  1 度だけ開く操作を撃つ
                 → 出たら「受け取る」を選ぶ
                 → 出なければ待つ（15 秒）
                 → それでも出なければ閉じて諦める
```

**開いたら必ず片づける。** 選べずに諦めるときも `Close(true)` を通す。
終わるときにも開きかけを閉じる。

**自分で開く前に、出ているメニューへ触らない。**
利用者が右クリックで開いたものに撃つと、意図しない操作になる。

「取り出せませんでした」と記録し、次の相手でも同じ品を試してまた 15 秒待つ。
`skippedHere` は相手ごとに消えるため、9 人 × 数種類ぶん繰り返し、
全体の制限時間（5 分）を使い切る。

しかも記録される理由が「取り出せませんでした」なので、
**鞄が一杯だとは分からない。**

### 対処

撃つ前に空きを確かめる。同じ品をすでに持っていれば山に積めるので、
空き枠が 0 でも進める。クリスタルは鞄を使わないので判定から外す。

空きが無ければ、その場で理由を出して終わる。

## F-53 装備品の確認ダイアログを一度も押せていなかった

利用者の報告:「数理が貯まって AutoDuty が自動停止したが、交換されていなかった」。

### 記録

```
02:54:14 交換を実行します: キングダムテール・レンジャートライコーン × 1
         （コスト 495 / index 4 / Shop 1770911）
02:54:29 交換できませんでした。所持数が動いていません。この品は以後飛ばします  ← 15 秒後
02:54:29 次の品へ進みます
02:54:31 BlockingAddonPresent: SelectYesno が開いています

```

### 原因

`TryFindConfirmDialog` は、確認ダイアログの本文に**通貨名とコストの両方が
含まれること**を必須にしていた。

```csharp
if (!body.Contains(currencyName) || !body.Contains(cost)) continue;
```

一方 `docs/05` には「装備品では確認がもう 1 枚出た」という実測が別に残っていた。
**装備品の本文は一度も実機を通っていない。**

しかも押せなかったことが記録に残らない。警告を出す分岐は本文照合を通った先にあり、
弾かれた場合は無言で見送る。報告からも追えなかった。

### 崩れ方

1 品目で 15 秒待って誤診断 → その品を恒久的に除外 → **ダイアログを開いたまま**次の品へ
→ 発火直前の P-5 が阻害アドオンとして弾いて失敗 → 残り 8 品は一度も試されない。

### 対処

- 本文照合を 1 段目に残し、2 段目として「**撃った直後に自分が開かせた**もの」を採る
  - `AddonOwnershipTracker.TryGetOwnedSince` を追加（記録を延長しない）
  - 発火から 10 秒以内に限る（実測では確認まで約 1 秒）
  - 捨て / 破棄 / 削除 / 分解 / 精製 / 売却 / ログアウト / タイトル / トレード を
    含む本文は押さずに拒む
- 採用しなかった本文を必ず記録する
- 品を飛ばす前に、残ったダイアログを閉じてから次へ進む

**所有権だけでは足りない。** `IsClaiming` は移動も会話も含めた交換の全区間で立っており、
その間に利用者が出した確認まで「自分のもの」になる。時刻の絞りが要る。

## F-54 抑制を握ったまま無期限に待つ

### 原因

リテイナーの処理は数分かかる。それより長く、かつ有限にする。

## F-57 交換候補の索引が一度壊れると二度と作り直されない

利用者の報告:「プリセットを有効にしても AD 周回が始まらない」
「コンテンツが終わってループ間処理は走るが、交換を行わず再びコンテンツへ入る」

### 原因

`MonitorService.TryStart` の索引ラッチが**一方向**だった。

```csharp
if (this.buildingForPreset != preset.Id) { /* 一度だけ BeginBuild */ }
return;
this.buildingForPreset = Guid.Empty;   // 解除はここだけ。構築が完走しないと到達しない
```

索引は **1 通貨ぶんしか持てない**。通貨の違うプリセットが並んでいると
互いに横取りし合い、作りかけが捨てられる。一度捨てられると
二度と頼み直されず、プラグインを読み込み直すまで回復しない。

閾値を超えていても `TryStart` が早期 return し続けるため、交換は一度も始まらない。
そこへ `AutoDutyKeeper` が周回を再開させ、コンテンツへ戻る。

**画面に「この通貨の交換候補を読み込む」ボタンが出ていること自体が、この状態の証跡。**
そのボタンが唯一の回復手段になっていたが、それと分かる術が無かった。

### 対処

ラッチを撤廃し、索引側の実状態（`TargetCurrencyItemId` と `Stage`）で判断する。
45 秒進まなければやり直す。`Stage == Failed` のときは 5 分空ける
（構築は 6 万行近い走査で、そのあいだ他の処理が全部止まる。撃ち直し続けると固まる）。

画面に進行段階と進捗率を出す。「構築しています」で固定すると、
止まっているのか進んでいるのかが読めない。

## F-58 周回の維持がプリセットを見ていない

`AutoDutyKeeper` は `Plugin.C.Presets` を **1 行も参照していなかった。**
チェックを全部外しても、プリセットを消しても、周回だけが回り続ける。

さらに `EmergencyStop` が止めていたのは `GoalRunner` と `ExchangeExecutor` だけで、
`AutoDutyKeeper` にも AutoDuty 本体にも触れていなかった。

利用者から見ると「オートコレクターを無効にしても止まらない。
AutoDuty を無効にして初めて止まった」。

- `Suspend(reason)` を新設し、停止操作から通す
- 有効なプリセットが 1 件も無ければ維持しない
- 利用者が押した停止では、走っている周回も止める

### ゲートの置き場所で 1 度踏んだ

最初、ゲートを**状態観測より前**に置いた。止めているあいだ AD の状態を見ないため
値が古いまま残り、有効へ戻した 1 回目の Tick が「前に見た停止の続き」として扱われ、
その場でコンテンツへ突入する。

観測は必ず通し、止めるのは「再開させるかどうか」だけにする。
保留に入るときは覚えている途中経過を捨てる。

## F-59 アンロードで相手の周回を巻き添えに止めてはいけない

停止処理に `AutoDuty.TryStop()` を足したところ、`Dispose` からも `EmergencyStop` が
呼ばれるため、**こちらを更新・再読み込みしただけで相手の周回が止まる**状態になった。

AutoDuty の `Stop` は `TaskManager.Abort` まで通るため、ダンジョン後に積まれた
ループ間処理（リテイナー・GC 納品・修理）の**予約ごと消える**。
Dalamud の自動更新でも起きる。

CLAUDE.md の「外部プラグインを強制停止しない」に正面から反する。

### 対処

`EmergencyStop(reason, stopExternalAutomation)` に分け、アンロード経路では相手に触れない。
止めるのは利用者がボタンやコマンドで押したときだけ。

## F-60 止めるときに立てた旗を、戻す側が全部下ろしていない

停止は **2 つの旗**を立てる。

| 旗 | 立てる場所 |
|---|---|
| 周回の維持 | `AutoDutyKeeper.Suspended` |
| 交換の封鎖 | `ExchangeExecutor` の `aborted` |

戻す側が維持しか見ていなかった。しかも `ClearAbort()` は
**呼び出し元が 0 件**で、`ResetAfterError()` は `Step == Error` のときしか通らない。

交換が動いていないときに止めると `aborted = true` / `Step = Idle` になり、
**画面のどこからも戻せない組み合わせ**になる。

その状態で周回を始めると、閾値に達しても `Request` が「停止中です」で弾き続ける。
周回だけが回り、交換は一度も起きない。**直したはずの F-57 がそのまま再現する。**

### 対処

`Plugin.ResumeAfterStop()` に一本化し、復帰の 4 経路すべてをそこへ通す。

```csharp
internal void ResumeAfterStop()
{
    this.AutoDutyKeeper?.Resume();
    this.ExchangeExecutor?.ClearAbort();
}
```

**止めるときに立てる旗と、戻すときに下ろす旗は、必ず 1 か所で対応させる。**

## F-63 納品ボタンが現れないと、納品そのものが行えなくなる

### 症状（2026-09-20 実機）

クラフター一連流れのプリセットで、呼び鈴から素材を出し、製作まで通った。
そのあと納品窓口へ移動して納品画面も開くが、**1 個も納品しない。**
画面を開いては閉じるのを 4 回繰り返して自動停止した。

記録に残っていたのは次の 4 回だけで、いずれも同じ形だった。

```
14:36:31.648 CollectablesShop Fire(11)        画面が開いた（ゲーム側）
14:36:31.780 Fire(12, 0u)                     行 0（タコス）を選ぶ
14:36:34.142 Fire(-2) ×2                      画面を閉じた
```

**`Fire(15, 0u)`（納品）が 1 度も出ていない。**
2026-09-13 に通した記録では `Fire(12, 0u)` の 86〜109 ミリ秒後に必ず出ていた。

### 原因

`CollectableDeliveryRunner` は納品ボタン（node 51）が
「見えている かつ 押せる」になるのを待ってから押していた。
このボタンが現れないまま 20 回（＝2 秒）待って諦めていた。

閉じるまでの 2.36 秒は、呼び出し間隔 100 ミリ秒 × 20 回と一致する。

問題は**待ち方ではなく、何を合図にしていたか**である。
ボタンの可視状態は「選択が効いた」ことの代わりに見ていたにすぎない。
代わりのものが読めなくなると、選択が効いていても納品まで進めない。

さらに `IsTradeReady` は例外を握りつぶして `false` を返していた。
ボタンを掴む経路（`GetComponentButtonById`）だけが引けなくなっても、
「まだ押せる状態ではない」としか見えず、原因を追えない形になっていた。

### 対処

**選択そのものを読む。** 一覧（node 28）の選択位置から行を引き、
そこに入っている行番号（`UIntValues[1]`）が狙いの行と一致することを確かめる。
一致したら、実測で確定している `Fire(15, 0u)` をそのまま渡す。

- ボタンが押せるようになればこれまでどおりそちらを合図にする（1 回目で決まる）
- 1 秒待っても現れなければ、選択を確かめて納品へ進む
- どちらも駄目なら、ボタンと選択の状態を理由に入れて止める

ボタンの押下を模す方法（ECommons の `ClickAddonButton`）は使わない。
ノードのイベント列の先頭をそのまま使うため、ボタンが隠れている間に
何が起きるかを説明できない。ゲームが受け取っていた値が分かっている以上、
そちらを直接渡すほうが説明できる。

### 取り違えへの備え

撃つ前に手持ちの収集品を控え、撃ったあとに
**狙っていない品が減っていないか**を見る。減っていれば取り違えなので、
やり直さずに止める。読み取りが 1 件も返らなかった場合は判断しない。

### 併せて直したもの

納品側が途中で止まっても、外からは「納品を終えました（0 個）」としか見えなかった。
`deliveryFailure`（開始できなかったときだけ入る）しか見ていなかったため。
止まった理由と、0 個で終わった理由を、そのまま外へ出すようにした。

### 選んだあとの画面を残す

自動で取っている納品画面のダンプは**画面が開いた瞬間**のもので、
選ぶ前の姿しか残らない。今回の 3 枚も全て選ぶ前のもので、
選択が効いていたのかどうかを判別できなかった。

ボタンが現れないときは、選んだあとの画面も 1 度だけ書き出す。
ファイル名と見出しに「開いた直後」「選んだあと」を入れて取り違えを防ぐ。

## F-64 収集価値が下限に届かない品を納品対象に数えていた

納品を受け付ける収集価値の下限は `CollectablesShopRefine` にある。
`CollectableRewardService` は報酬（`CollectablesShopRewardScrip`）だけを読み、
この下限を読んでいなかった。

下限に届かない品を持っていると、窓口まで移動して画面を開き、
選んでから納品できずに戻る、を繰り返すことになる。

### 対処

下限を索引に入れ、3 か所で門番にする。

| 場所 | 効果 |
|---|---|
| `GoalRunner.HasDeliverable` | 納品へ向かわない |
| `CollectableCycleRunner.CountDeliverable` | 往復を始めない。理由を出して終わる |
| `CollectableDeliveryRunner.TickSelect` | 画面まで来ていても選ばない |

判断は手持ちのうち**一番高い**収集価値で行う。低いほうで判断すると、
渡せる品を持っているのに諦めることになる。

下限が引けない品（シートに無い・0 行目を指している）では判断しない。
読めない値を根拠に品を捨てるほうが害が大きい。

### 実データ（2026-09-20、シートを直接読んで確認）

| ItemId | 品 | 収集価値 低/中/高 | 報酬 低/中/高 |
|---|---|---|---|
| 44232 | 収集用のタコス・カルネ・アサーダ | 660 / 900 / 1140 | 120 / 134 / 144（橙貨） |
| 44231 | 収集用のスタッフドピーマン | 627 / 855 / 1083 | 165 / 181 / 198（紫貨） |
| 44230 | 収集用のサーモンジャーキー | 583 / 795 / 1007 | 143 / 157 / 171（紫貨） |
| 44229 | 収集用のトラルパイナップルケーキ | 539 / 735 / 931 | 131 / 144 / 157（紫貨） |
| 44228 | 収集用のバナナパンズケーキ | 495 / 675 / 855 | 119 / 130 / 142（紫貨） |
| 44227 | 収集用のボイルド・アルパカステーキ | 451 / 615 / 779 | 107 / 117 / 128（紫貨） |

**今回の不具合はこれが原因ではない。** 手元のタコスは収集価値 1200 で、
高（1140）を超えている。納品できる品を納品できなかったのが F-63 である。
